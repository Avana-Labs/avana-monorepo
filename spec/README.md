# Avana Protocol Specification

The specification of the Avana protocol: how the contracts fit together, what each contract and operation does, the invariants that must always hold, the attacks the design defends against, the external dependencies it relies on, every design decision, and how each rule is verified. Contracts in [`contracts/`](../contracts/) are written from these pages; when the code and a page disagree, the page is changed first through change control and the code follows.

Every contract page has the sections Purpose, Inputs, Outputs, Storage, Functions, Permissions, Dependencies, Events, Restrictions and Failure Conditions, plus contract-specific sections such as Formulas, Settlement math or Price states. Every operation page has Objective, Initiator, Inputs, Preconditions, Execution Steps, Contract Interactions, State Changes, External Calls, Events, Failure Conditions, Postconditions and Related. Each contract page is authoritative for its own function, event and error names; the role table in 2.15 is authoritative for roles (`Q-228`). Parameters are referred to by name everywhere and their values appear only in 1.5.

## ID conventions

Every rule, formula, step, invariant, decision and check has a stable ID, so tests, proofs, code and findings can point at the exact behaviour they concern.

| Kind | Format | Example | Defined in |
|---|---|---|---|
| Architecture requirement | `REQ-ARCH-NNN` | `REQ-ARCH-004` | 1.1, 1.2 |
| Per-chain requirement | `REQ-CHAIN-NNN` | `REQ-CHAIN-001` | 1.1, 1.5 |
| AMM integration rule | `REQ-AMM-CORE-NNN` (the interface every integration meets), `REQ-AMM-<P>-NNN` with `<P>` one of `V3`, `SLIP`, `V2`, `CURVE`, `BAL`, `V4` | `REQ-AMM-SLIP-001` | 2.2 and the integration pages |
| Flash-source rule | `REQ-FLASH-NNN` | `REQ-FLASH-001` | 2.11 |
| Role requirement | `REQ-ROLE-NNN` | `REQ-ROLE-002` | 1.4 |
| Contract requirement | `REQ-<CONTRACT>-NNN` | `REQ-VAULT-064` | 2.x |
| Formula or math rule | `SPEC-<AREA>-NNN` | `SPEC-HUB-001` | The page that states the formula |
| Role | `<NAME>` constant of `AvanaRoles` or the AvanaTimelock | `APPLICATION_ADMIN` | 1.4, 2.15 |
| Trust boundary | `TB-NNN` | `TB-020` | 1.3 |
| Operation | `FLOW-NNN` | `FLOW-005` | 3.x page title |
| Operation step | `<FLOW>-NNN` | `DEP-003` | 3.x |
| Operation failure | `<FLOW>-F-NNN` | `LIQ-F-004` | 3.x |
| Operation postcondition | `<FLOW>-POST-NNN` | `WDR-POST-001` | 3.x |
| Global invariant | `INV-NNN` | `INV-022` | 4.1 |
| Attack scenario | `ATTACK-NNN` | `ATTACK-107` | 4.2 |
| External dependency | `EXT-NNN` | `EXT-001` | 4.3 |
| Design decision | `Q-NNN` | `Q-149` | 4.4 |
| Z3 check | `MATH-<GROUP>-NN` (`UO` units and oracle, `AR` Aave risk, `ST` settlement, `CH` per-chain parameters) | `MATH-AR-03` | `05-verification/z3/` |
| SymPy check | `SYM-NN` | `SYM-05a` | `05-verification/sympy/` |
| Quint invariant or scenario | `QNT-NN`, `QNT-TNN` | `QNT-07`, `QNT-T01` | `05-verification/quint/` |
| Hypothesis property | `HYP-NN` | `HYP-44` | `05-verification/hypothesis/` |
| Simulation result | `SIM-NNX` | `SIM-04A` | `05-verification/simulation/` |
| Implementation test | `TEST-NNN` | `TEST-140` | 5.1 |
| Formal property | `PROP-NNN` | `PROP-043` | 5.2 |
| Audit finding | `FINDING-NNN` | `FINDING-063` | 5.3 |

**Contract codes:** `HUB` (2.1), `VAULT` (2.2), `COLL` (2.3), `VTOKEN` (2.4), `PROXY` (2.5; rules moved with their content keep their ID on 2.6), `ADAPTER` (2.6; borrow-side checks keep their ID on 2.7), `RISK` (2.7; cap values and setters keep their ID on 2.9), `CONFIG` (2.8 and 2.9, rules kept where their content now lives), `MREG` (2.8), `PSTORE` (2.9), `ORACLE` (2.10), `SWAP` (2.11), `ROUTE` (2.12), `BUDGET` (2.13), `FLR` (2.14), `ACCESS` (2.15), `LOCK` (2.16), `LENS` (2.17), `ESCROW` (2.18). A rule keeps its ID when its content moves to another page.

**Formula areas:** `HUB` (2.1), `BACK` backing (2.3), `UNIT` units (2.4), `PROXY` (2.5, 2.6), `CAP` caps and `CF` collateral factor (2.7), `BRK` circuit breakers (2.7 conditions, 2.8 latched counters), `ORC` oracle, LPPriceMath and DebtOracle (2.10), `LIQ` liquidation settlement and SettlementMath (2.11), `SET` settlement budget (2.13), `FLR` First-Loss Reserve (2.14), `GOV` governance timing (2.15), `CHAIN` per-chain parameters (1.5), `AMM-CORE` and `AMM-<P>` AMM integrations.

**Flow codes:** `DEP` deposit, `BOR` borrow, `REP` repay, `WDR` withdraw, `LIQ` liquidation, `EMG` emergency, `FEE` collect fees, `MKT` market lifecycle, `DEF` deficit coverage.

Rules:

- An ID is defined once, as the first backticked token of a list item, table row or heading; the rest of that line is its text.
- IDs are never reused or renumbered. A step inserted between `DEP-003` and `DEP-004` is `DEP-003a`.
- Pages cross-reference by ID, not by section heading.
- Each requirement line ends with `(Source: …)`, naming the decisions (`Q-…`) and approved defaults it comes from.

## Requirement language

**MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** have their RFC 2119 meanings. A sentence without one of them is explanation. Each ID carries one requirement, and every action names its actor: a contract, a role (an `AvanaRoles` or AvanaTimelock role constant), or "any address".

## Units

| Quantity | Unit |
|---|---|
| Ratios, health factor | WAD (1e18); `HF = 1.10` is `1.1e18` |
| Interest indices, deficit amounts | RAY (1e27) |
| Collateral factor, bonuses, tolerances, fees | Basis points (1e4 = 100%) |
| Oracle prices | 8 decimals, USD per whole token (Aave's format) |
| Exposure caps and USD charges | USD with 8 decimals |
| Aave value | `amount × price × 10^(18 − decimals)`, 26 decimals (1e26 = $1) |
| GHO | 18 decimals; GHO debt priced at a fixed $1; a stable debt asset when the Aave DAO approves it, with USDC, USDT and the like |
| Other debt assets | The asset's own decimals (USDC and USDT 6, WETH 18); priced by the asset's DebtOracle, the Aave oracle source of the reserve, 8 decimals |
| Vault tokens | Per-market decimals 6–18; one base unit = one credited unit of the market's AMM integration (liquidity for concentrated liquidity, a pool share for share-based pools) |
| Times and delays | Seconds (`uint48` timestamps, `uint32` delays) |

Every number in a requirement states its unit and precision, and every rounding step states its direction.

## Traceability and change control

[`05-verification/trace.py`](05-verification/trace.py) builds the matrix requirement → checks → implementation and writes it to [`traceability.md`](05-verification/traceability.md). It runs in `run_all.sh`.

- **Requirements** are `REQ-…`, `SPEC-…`, `INV-…`, `ATTACK-…`, flow steps (`DEP-001`, `LIQ-F-002`, `WDR-POST-001` …) and decisions `Q-…`, defined in `01-architecture/` to `04-security/`.
- **Checks** link to requirements with a tag in the check's file, in any comment style: `MATH-AR-03 verifies: SPEC-HUB-001, Q-126`. Foundry tests use `TEST-…`, formal properties `PROP-…`. Solidity links with NatSpec: `/// @custom:spec REQ-VAULT-001`. A spec rule can also cite the checks that verify it (`Checked by: MATH-AR-03, QNT-07`); `trace.py` links each cited check to that rule and fails if a cited check ID is not defined in any model file.
- **Change control:** [`traceability.lock.json`](05-verification/traceability.lock.json) stores a hash of each requirement's text and the checks accepted for it. When the text changes, `trace.py` fails until the linked checks are rerun and the change is accepted with `trace.py --accept <ID>` (or `--accept-all`).
- `trace.py` fails on duplicate IDs, links to undefined IDs and unaccepted text changes. `--strict` also fails on coverage gaps: a requirement with no spec-stage check, and, for `REQ-…`, `SPEC-…` and `INV-…` once `contracts/src` holds Solidity, no implementation test or property and no `@custom:spec` link.

Each matrix row has a status: **Unverified** (no check), **Modelled** (spec-stage checks only), **Verified** (spec-stage checks plus a Foundry test or formal property), or **Changed — re-verify** (text differs from the accepted hash).

```
REQ / SPEC / flow step ──► INV ──► TEST / PROP ──► FINDING
          ▲                                            │
          └──────────── fix updates the spec ◄─────────┘
```

Every failed check becomes a `FINDING-…` in 5.3 that cites the requirement, step or invariant it affects. A fix changes the page first, then the code, and the changed requirement is accepted only after its checks pass again.

## Page status

Each page opens with a status line, for example `> **Status:** In review · **Owner:** Avana Labs · **Last reviewed:** 2026-11-09`.

| Status | Meaning |
|---|---|
| Draft | Content written; review not started |
| In review | Under security and engineering review; rules are complete and traced, and changes go through change control |
| Approved | Reviewed and final; code is written against it |
| Superseded | Replaced; the page links to its replacement |
