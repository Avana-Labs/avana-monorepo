# 2.21 Aerodrome Slipstream Integration

> **Status:** In review · **Owner:** Avana Labs · **Last reviewed:** 2026-11-10
>
> **Requirement prefix:** `REQ-AMM-SLIP-NNN` · **Math prefix:** `SPEC-AMM-SLIP-NNN`

## Purpose

The Slipstream integration is Avana's code for Aerodrome Slipstream concentrated-liquidity positions on Base (chain ID 8453): one immutable Slipstream LPVault that implements the AMM integration interface ([2.19](19-amm-integration-interface.md)) with `AMM_PROTOCOL() = keccak256("AERODROME_SLIPSTREAM")` and the `INTEGRATION_ID` registered for it in Base's VaultTokenFactory (`ISlipstreamIntegration`, `contracts/src/amm/slipstream/`), and the Slipstream pricing library that the LPVault and the Slipstream LPOracle implementation ([2.10](10-lp-oracle.md)) compile in.

Slipstream reuses the Uniswap v3 tick and liquidity math unchanged, so every rule of the Uniswap v3 integration ([2.20](20-uniswap-v3-integration.md)) applies to Slipstream as written, with the position manager and factory of the market's pinned generation in place of the v3 NFPM and factory: custody (`REQ-VAULT-147`, `REQ-VAULT-148`, `REQ-VAULT-011`), removal and release with a principal-capped collect (`REQ-VAULT-149`, `REQ-VAULT-161`, `REQ-VAULT-057`, `REQ-VAULT-058`, `SPEC-BACK-008`), live liquidity (`REQ-VAULT-162`), fee collection (`REQ-VAULT-065`), stray NFTs (`REQ-VAULT-078`, `REQ-VAULT-079`, `REQ-VAULT-080`, `REQ-VAULT-124`), the pool and exact-range checks (`REQ-VAULT-008`, `REQ-VAULT-009`, `SPEC-BACK-001`) and the composition at the clamped oracle price (`SPEC-AMM-V3-001`). This page states only where Slipstream differs and the rules those differences require (`AMMN-FLOW-10`).

## Differences from Uniswap v3

| Area | Uniswap v3 | Slipstream | Rule |
|---|---|---|---|
| Pool lookup | `factory.getPool(tokenA, tokenB, uint24 fee)` | `CLFactory.getPool(tokenA, tokenB, int24 tickSpacing)` | `REQ-AMM-SLIP-002` |
| `positions(tokenId)` field 5 | `uint24 fee` | `int24 tickSpacing` | `REQ-AMM-SLIP-003` |
| `slot0()` | 7 fields, `unlocked` is field 7 | 6 fields (no `feeProtocol`), `unlocked` is field 6 | `REQ-AMM-SLIP-004` |
| Swap fee | Fixed by the fee tier | Per pool, set by fee modules and changeable at any time | `REQ-AMM-SLIP-005` |
| Position managers on the chain | One NFPM | Four generations, each with its own factory and NFT contract | `REQ-AMM-SLIP-006`, `REQ-AMM-SLIP-007` |
| Staking | None | A gauge can hold the NFT and earn AERO instead of fees | `REQ-AMM-SLIP-009`, `REQ-AMM-SLIP-010` |
| Fees of unstaked positions | All of the LP share of the swap fee | Reduced by the staked share and by `unstakedFee` | `REQ-AMM-SLIP-011`, `SPEC-AMM-SLIP-002` |
| Tick spacings | 1, 10, 60, 200 by fee tier | Any spacing up to 6,931 that the factory enables (1, 50, 100, 200, 2000 and others) | `REQ-AMM-SLIP-008`, `REQ-AMM-SLIP-014` |

## Requirements

- `REQ-AMM-SLIP-001` — The Slipstream LPVault MUST apply every rule of [2.20](20-uniswap-v3-integration.md) that names the NFPM, the factory or the pool, with the position manager and factory of the market's pinned generation substituted, and MUST call a custodied NFT only on the position manager of the generation encoded in the high byte of its `positionKey`, `bytes32((uint256(generation) << 248) | tokenId)` (`SPEC-AMM-CORE-002`), which `receivePosition` required to equal the market's pinned generation. A key whose generation byte is at or above `generationCount()` names no allowlisted manager: every function that resolves it, including `positionOwner`, `validatePosition`, `receivePosition` and `returnStray`, reverts with `UnsupportedNft`, and `positionKeyOf(index, tokenId)` reverts with `UnsupportedNft` for `index >= generationCount()` or `tokenId >= 2^248`, so the generation bits are never overwritten. A key of another allowlisted generation reverts with `PoolMismatch`: `receivePosition` and `validatePosition` compare the key's position manager with the market's pinned one at the pool check, so the refusal does not rest on what that generation's factory returns for the position's pair and spacing. The Slipstream `decreaseLiquidity` and `collect` parameter structs are the same as Uniswap v3's, so the principal-capped collect of `SPEC-BACK-008` runs unchanged. Why: one LPVault holds positions of four NFT contracts whose `tokenId`s overlap, so the contract a call goes to must come from the key, never from a separate argument. (Source: Q-291, Q-292, Q-301)
- `REQ-AMM-SLIP-002` — Pool identity MUST be derived as `CLFactory.getPool(token0, token1, tickSpacing)` on the market's pinned factory, with `token0`, `token1` and `tickSpacing` read from the position, and `receivePosition` MUST revert with `PoolMismatch` unless the result is non-zero and equals `market.pool`. A call shaped for Uniswap v3, passing a fee where Slipstream expects a tick spacing, resolves a different pool: `getPool(t0, t1, 100)` returns the fee-100 pool on a v3 factory and the spacing-100 pool on a Slipstream factory. (Source: Q-293, Q-301)
- `REQ-AMM-SLIP-003` — `positions(tokenId)` MUST be decoded with the Slipstream layout `(uint96 nonce, address operator, address token0, address token1, int24 tickSpacing, int24 tickLower, int24 tickUpper, uint128 liquidity, uint256 feeGrowthInside0LastX128, uint256 feeGrowthInside1LastX128, uint128 tokensOwed0, uint128 tokensOwed1)`. Field 5 is a signed tick spacing, not a fee; the Slipstream library has its own decoder and shares none with the Uniswap v3 library. Why: decoding field 5 as `uint24 fee` and passing it to `getPool` would check the wrong pool, and a negative spacing read as unsigned would never match. (Source: Q-301, Q-305)
- `REQ-AMM-SLIP-004` — The pool lock MUST be read from the 6-field `slot0()` `(uint160 sqrtPriceX96, int24 tick, uint16 observationIndex, uint16 observationCardinality, uint16 observationCardinalityNext, bool unlocked)`, and every custody, removal and quote MUST revert with `PoolLocked` while `unlocked == false`. The Slipstream LPOracle implementation is deployed with `slot0Words = 6` and reads only `unlocked` (word 5) and `observationCardinality` (word 3) from this layout ([2.10](10-lp-oracle.md#concentrated-liquidity-pricing-uniswap-v3-and-aerodrome-slipstream)). Why: the Uniswap v3 `slot0` has 7 fields with `uint8 feeProtocol` before `unlocked`, so a v3 decoder reads the wrong word for `unlocked` on a Slipstream pool and would let a removal run inside a swap callback. Example: during a Slipstream swap callback `slot0()` returns `unlocked = false` in word 6; a v3 decoder reads word 6 as `feeProtocol` and word 7 past the return data, and reverts or misreads. (Source: Q-144, Q-305)
- `REQ-AMM-SLIP-005` — Avana MUST NOT derive a Slipstream pool's swap fee from its tick spacing. Wherever Avana uses the fee (the TWAP tolerance bound of the LPOracle, swap-route cost estimates, the Lens), it MUST read it live from `pool.fee()`, which reflects the factory's fee modules (`CLFactory.getSwapFee(pool)`), and MUST read `pool.unstakedFee()` for the unstaked fee share. Pricing, credited units and removal never depend on the fee. Why: a dynamic fee module can change the fee at any block, so a fee fixed at listing can be wrong by the next block. (Source: Q-301, Q-305)
- `REQ-AMM-SLIP-006` — **Generation allowlist (`AMMN-RT-15`).** The constructor MUST take the four (position manager, factory) pairs of the table above as immutables, in index order, and MUST revert with `InvalidDeployment` unless every one of the eight addresses is non-zero, has code, differs from the other seven and from the four Avana bindings, and each manager's `factory()` equals its paired factory; the deployment check MUST compare every address with Aerodrome's published deployment list. No function adds, removes or changes a pair. A later Slipstream generation is a new AMM integration with its own LPVault and `integrationId`, registered through the VaultTokenFactory ([2.19](19-amm-integration-interface.md) `REQ-AMM-CORE-002`). Why: a copied configuration can pair one generation's position manager with another's factory, or a Slipstream manager with a Uniswap v3 factory on the same chain; fixing the pairs in immutable code means a market can only name a pair that exists. (Source: Q-291, Q-301)
- `REQ-AMM-SLIP-007` — `bindMarket` MUST pin one allowlisted generation per market, decoded from `integrationData = abi.encode(uint256 generation, uint256 price0, uint256 price1)` (exactly 96 bytes; `price0`, `price1` are the listing valuation prices of [2.20](20-uniswap-v3-integration.md) `REQ-AMM-V3-008`, 8 decimals), and revert with `InvalidPool` unless the data has that length, the index is below `generationCount()`, the generation's NPM equals `pool.nft()`, and `SPEC-AMM-SLIP-001` holds for `pool`. The code check of `SPEC-AMM-SLIP-001` runs before any call to `pool`, so a pool address that is not a clone of the pinned factory's implementation reverts with `InvalidPool` before its own code can run. A pledge of an NFT from any other manager, including another allowlisted generation, reverts with `PoolMismatch` because the key's generation differs from the market's. (Source: Q-293, Q-301)
- `REQ-AMM-SLIP-008` — `bindMarket` MUST read `s = pool.tickSpacing()`, revert with `InvalidPool` unless `0 < s ≤ 6,931` and `CLFactory.tickSpacingToFee(s) != 0` on the pinned factory (6,931 is the largest spacing with `maxLiquidityPerTick(s) ≤ 2^120 − 1`: `1.324 × 10^36` at 6,931 and `1.334 × 10^36` at 6,932, so `REQ-AMM-SLIP-014` holds for every listed pool), and require the range by `SPEC-BACK-001`: `tickLower < tickUpper`, signed `int24` `tickLower % s == 0` and `tickUpper % s == 0`, and both inside the usable ticks `[⌈MIN_TICK / s⌉ · s, ⌊MAX_TICK / s⌋ · s]`. Alignment MUST never be checked on a `uint24` cast. Example: for `s = 2000` the usable ticks are `[−886,000, 886,000]`; tick −1,216 is misaligned (`−1,216 % 2000 = −1,216`), yet `uint24(−1,216) = 16,776,000` is a multiple of 2000, so a cast check would accept it; for `s = 100`, tick −116 fails the signed check and passes the cast check (`16,777,100 % 100 = 0`). Checked by: MATH-AMM-V3-PRICE-05, AMM-A5a, AMM-A5b, AMM-A5c, AMM-A5e, HYP-AMM-05. (Source: Q-293)
- `REQ-AMM-SLIP-009` — **Unstaked positions only (`AMMN-GAS-14`).** `receivePosition` and `validatePosition` MUST revert with `PositionEncumbered`, before any transfer, when the position's owner is the market pool's gauge: `g = pool.gauge()` is non-zero and `ownerOf(tokenId) == g`. The gauge is read with a static call whose failure counts as "no gauge", and Avana MUST NOT call the voter's `isGauge`: on the Aero generation the factory's voter is a leaf voter whose `isGauge(address)` reverts, so a pledge that called it would revert for every position of that generation. The ownership check of `REQ-VAULT-147` runs first and is what refuses a staked NFT for its staker, since the gauge owns it; the gauge check refuses a call naming the gauge itself as owner, and a failed gauge read can neither block an unstaked NFT nor admit a staked one. `isStaked(marketId, tokenId)` reports the same condition and returns false when either read fails. Why: the gauge holds a staked NFT and pays its fees to voters, so Avana could neither take custody of it nor remove its liquidity without a gauge `withdraw` in the seizure path, which a killed or paused gauge could block. (Source: Q-301)
- `REQ-AMM-SLIP-010` — The Slipstream LPVault MUST NOT call `approve` or `setApprovalForAll` on any position manager, MUST NOT call any gauge, and MUST NOT stake a custodied NFT. ERC-721 clears a token's per-token approval on transfer, and the LPVault grants no operator, so once pledged a position cannot be staked by anyone, and every custodied position stays unstaked until it returns to its depositor. A custodied position therefore earns no AERO emissions: it earns the unstaked fee share of `SPEC-AMM-SLIP-002`, which `collectFees` pays to the depositor of record, and the LPVault never claims, holds or forwards AERO. The LPVault also never calls `mint` or `increaseLiquidity`, both of which end in a refund of the position manager's whole ETH balance to the caller; liquidity added to a custodied NFT comes from its depositor or a third party directly on the position manager and is credited only by a re-credit (`REQ-VAULT-077`). (Source: Q-301)
- `REQ-AMM-SLIP-011` — The Slipstream LPVault MUST collect fees through `collectFees` exactly as `REQ-VAULT-065`, paying every amount owed to the depositor of record; the amount is the unstaked LP share of `SPEC-AMM-SLIP-002`. Fees are never collateral (`REQ-AMM-CORE-010`), so the unstaked fee share changes only the borrower's yield, which the Lens reports per market from `pool.fee()`, `pool.unstakedFee()` and `pool.stakedLiquidity()`. (Source: Q-009, Q-011, Q-301)
- `REQ-AMM-SLIP-012` — `composition` MUST compute `SPEC-AMM-V3-001` unchanged: the amounts of [2.10](10-lp-oracle.md#concentrated-liquidity-pricing-uniswap-v3-and-aerodrome-slipstream) `SPEC-ORC-006` at the oracle sqrt price clamped to the market's range, rounded down, then reported reduced by 1 raw unit for display (the LPOracle's own composition returns them unreduced and `lpPrice` takes the unit off once, `SPEC-ORC-008`), with uncollected fees excluded. The tick math and `LiquidityAmounts` of Slipstream are the Uniswap v3 code. Checked by: MATH-AMM-V3-PRICE-01, MATH-AMM-V3-PRICE-03, MATH-AMM-V3-PRICE-04, AMM-A1a, AMM-A3f, AMM-A4a, HYP-AMM-01, HYP-AMM-02, HYP-AMM-03, HYP-AMM-04. (Source: Q-293)
- `REQ-AMM-SLIP-013` — `riskStatus` MUST report `depthUnits` as the harmonic-mean in-range liquidity from `pool.observe` over `window`, the same consult as Uniswap v3, with `depthAvailable = false` when the pool's observations do not cover the window. The LPOracle sizes the window and its buffer for Base's 2-second blocks (`AMMN-RT-08`) and applies Base's sequencer-uptime feed `0xBCF85224fc0756B9Fa45aA7892530B47e10b6433` with its grace period ([2.10](10-lp-oracle.md)). (Source: Q-295, Q-305)
- `REQ-AMM-SLIP-014` — Credited liquidity of one Slipstream market MUST stay below `MAX_CREDITED_LIQUIDITY = 2^120 − 1`. Every position of a market references the same `tickLower`, whose gross liquidity the pool caps at `maxLiquidityPerTick(s)`, at most `3.8 × 10^35` for `s = 2000` and at most `2^120 − 1` for every spacing `bindMarket` accepts (`s ≤ 6,931`, `REQ-AMM-SLIP-008`); from `s = 6,932` on the per-tick bound exceeds `2^120 − 1` (`8,000` gives `1.54 × 10^36`), so such pools are refused at listing. Checked by: MATH-AMM-V3-PRICE-05, AMM-A5d, AMM-A5e. (Source: Q-293)

## Math

Units: ticks as `int24`; fees in pips (`10^6` = 100%); token amounts in USD for the example.

- `SPEC-AMM-SLIP-001` — **Pool identity.** A pool is accepted for a market with pinned pair `(npm, factory)` iff all hold: `npm.factory() == factory`; `pool.factory() == factory`; `factory.getPool(pool.token0(), pool.token1(), pool.tickSpacing()) == pool`; and `keccak256(pool.code) == keccak256(0x363d3d373d3d3d363d73 ‖ factory.poolImplementation() ‖ 0x5af43d82803e903d91602b57fd5bf3)`, the 45-byte EIP-1167 clone of the factory's pool implementation. Why: Slipstream factories deploy pools as minimal clones, so the code check proves the pool runs the factory's implementation and not a fork that shares the interface; the `getPool` and `factory()` checks prove it is the factory's registered pool for that pair and spacing, and the manager check ties the market's NFTs to the same factory. Units: addresses and code hashes. Rounding: none. Bounds: none. Example: a market naming the Gauges V3 manager `0xe1f8…8b53` and a USDC/USDT pool of spacing 1 passes when the pool's `factory()` is `0xf8f2…61Ef` and `getPool(USDC, USDT, 1)` returns it; the same pool listed with the Initial manager `0x8279…5b72` fails `npm.factory() == factory` and `bindMarket` reverts `InvalidPool`; a fork pool with identical functions but its own bytecode fails the code check and reverts `InvalidPool`. Checked by: listing fork test on Base per generation. (Source: Q-301)
- `SPEC-AMM-SLIP-002` — **Unstaked fee share.** For a swap paying fee `F = amountIn × fee / 10^6` while the pool has in-range liquidity `liq` of which `staked` is staked: `toGaugeStaked = F × staked / liq`; `unstakedPart = F − toGaugeStaked`; `toGaugeUnstaked = unstakedPart × unstakedFee / 10^6`; `toUnstakedLPs = unstakedPart − toGaugeUnstaked`; an unstaked position with liquidity `L_p` earns `toUnstakedLPs × L_p / (liq − staked)`. Why: Slipstream sends the staked share of every fee and `unstakedFee` of the rest to the gauge for voters, so a pledged position, which is always unstaked, earns less than a v3 position of the same share; the borrower sees the rate before pledging. Units: token amounts; fees in pips. Rounding: Slipstream's own, down in fee growth. Bounds: `unstakedFee ≤ 10^6`. Example: pool fee 100 pips, `unstakedFee = 100,000` (10%), `staked = 60%` of `liq`, a $1,000,000 swap: `F = $100`, `toGaugeStaked = $60`, `unstakedPart = $40`, `toGaugeUnstaked = $4`, `toUnstakedLPs = $36`; a pledged position holding 1% of `liq` is 2.5% of the unstaked liquidity and earns $0.90, against $1.00 for the same share on Uniswap v3. Checked by: fork test on Base comparing `tokensOwed` growth with this formula. (Source: Q-301)

## Permissions

As for every LPVault ([2.19](19-amm-integration-interface.md) Permissions): custody and removal functions only from Collateralization while the AaveAdapter or LPVaultSwap holds the Lock, and `collectFees` only while the AaveAdapter holds it; `bindMarket` only from the MarketRegistry; `returnStray` only from the AvanaTimelock. No role can change the generation allowlist or a stored market.

## Dependencies

| Dependency | Type (internal / external) | Calls made | Why |
|---|---|---|---|
| Slipstream position managers (four generations) | External | `ownerOf`, `positions`, `transferFrom`, `decreaseLiquidity`, `collect`, `factory` | Custody, removal, fees, generation check |

| Collateralization, VaultTokenFactory, Lock, AvanaTimelock | Internal, immutable | As [2.2](02-lp-vault.md) | Callers and the Lock |

## Events

The Slipstream LPVault emits the events of [2.2](02-lp-vault.md) and [2.19](19-amm-integration-interface.md). `MarketBound(marketId, pool, poolId, tickLower, tickUpper)` carries no generation; an indexer reads a market's pinned position manager and factory from `clMarket(marketId)`, written once by `bindMarket`, and a position's generation from the high byte of its `positionKey`.
