# 2.19 AMM Integration Interface

> **Status:** In review · **Owner:** Avana Labs · **Last reviewed:** 2026-11-10
>
> **Requirement prefix:** `REQ-AMM-CORE-NNN` · **Math prefix:** `SPEC-AMM-CORE-NNN`

## Purpose

An AMM integration is Avana's code for one AMM protocol on one chain: one immutable LPVault ([2.2](02-lp-vault.md)) that holds every pledged position of that AMM protocol, plus the pricing library that the LPVault and the AMM protocol's LPOracle implementation ([2.10](10-lp-oracle.md)) both compile in. Every integration implements the interface below, and the AMM-neutral core (Collateralization, [2.3](03-collateralization.md); the vault tokens, [2.4](04-vault-tokens.md); the AaveAdapter, [2.6](06-aave-adapter.md); LPVaultSwap, [2.11](11-lpvaultswap.md); the LPOracle base) depends only on it. Adding an AMM protocol therefore adds one LPVault, one pricing library and one LPOracle implementation; the ledger, the Lock, the Adapter and LPVaultSwap stay as they are (`Q-291`).

The interface has five parts:

| Part | Functions | Used by |
|---|---|---|
| Custody | `bindMarket`, `receivePosition`, `validatePosition`, `topUpPosition`, `returnPosition`, `returnStray` | MarketRegistry at listing; Collateralization on pledge, re-credit and exit; the RiskModule and the Lens before a pledge; the AvanaTimelock for stray positions |
| Composition | `composition` | LPOracle (through the shared pricing library), LPVaultSwap's minimum-recovery checks, the Lens |
| Unwind | `unwind`, `releaseToDepositor`, `unitsOf` | Collateralization on seizure, reconciliation, repay with collateral and partial removal |
| Fees | `collectFees`, `capabilities().feeMode` | Collateralization, for the depositor of record, through the Adapter |
| Risk metadata | `riskMetadata`, `riskStatus`, `checkReadSafe`, `consistencyDeviation` | RiskModule (range status, pool depth for the pool-share cap), LPOracle (pool lock, consistency check), the Lens |

Implemented by: Uniswap v3 on Ethereum ([2.20](20-uniswap-v3-integration.md)) and Aerodrome Slipstream on Base ([2.21](21-aerodrome-slipstream-integration.md)). The interface also supports Uniswap v2, Curve StableSwap-NG, Balancer weighted and stable pools and Uniswap v4; [2.22](22-amm-integration-readiness.md) gives each one's pricing model, custody shape and the guards it must pass before its first market is listed.

## Terms

| Term | Meaning |
|---|---|
| AMM protocol | A DEX family whose positions Avana accepts: Uniswap v3, Aerodrome Slipstream, Uniswap v2, Curve, Balancer, Uniswap v4, Sushi |
| AMM integration | Avana's code for one AMM protocol on one chain, identified by `integrationId` (`uint32`, assigned once per chain at `registerIntegration`, never 0) and tagged by `AMM_PROTOCOL()` (`keccak256` of the protocol name, for example `keccak256("UNISWAP_V3")`) |
| Market | One (chain, AMM protocol, pool, exact position shape), listed as one collateral reserve on one CDP Spoke. For concentrated liquidity the shape is the exact `[tickLower, tickUpper]` range; for pools whose LP share is fungible, the shape is the whole pool |
| `pool`, `poolId` | The pool's identity inside its AMM protocol: `pool` is the pool address for protocols keyed by address (Uniswap v2 and v3, Slipstream, Curve) with `poolId = bytes32(0)`; `poolId` is the identifier inside a singleton for protocols keyed by ID (Balancer pool id, Uniswap v4 `PoolId`) with `pool = address(0)` (`capabilities().poolKeying`) |
| `marketId` | The MarketRegistry's identifier of a market (`uint256`, sequential, below `2^32`). Every integration function names a market by `marketId`, bound once by `bindMarket` |
| `marketKey` | The VaultTokenFactory's key of a market's shape, `keccak256(abi.encode(block.chainid, integrationId, pool, poolId, shape.kind, shape.tickLower, shape.tickUpper))` (`SPEC-AMM-CORE-002`); one vault token per key ([2.4](04-vault-tokens.md) `REQ-VTOKEN-021`) |
| `positionKey` | A position's identity inside its integration (`bytes32`). Avana keys every record, event and index by (`integrationId`, `positionKey`), never by a bare NFT `tokenId` (`Q-292`) |
| Unit | One credited unit of a position: liquidity for concentrated liquidity, LP-token base units for fungible LP shares. One unit backs one vault-token base unit ([2.4](04-vault-tokens.md) `SPEC-UNIT-002`) |
| Swap route | A swap path LPVaultSwap uses to convert unwound tokens into the debt asset ([2.12](12-settlement-routes.md)); the AMM protocol of the collateral and the swap route are independent choices |

## Functions

Every array of token amounts or prices has one entry per pool token of the market, in the pool order `marketOf(marketId)` returns, which never changes; a wrong length reverts `LengthMismatch(expected, actual)`. `prices[i]` is the USD price of one whole token `i` with 8 decimals, the vector the LPOracle serves. Every LPVault implements `IAmmIntegration` and `IAmmIntegrationHooks` (`contracts/src/amm/`); a hook that does not apply to its AMM protocol returns its neutral value, so no caller branches on the AMM protocol.

| Function | Description | Caller (role / contract) | Requirements |
|---|---|---|---|
| `bindMarket(uint256 marketId, address pool, bytes32 poolId, PositionShape shape, bytes integrationData) returns (address[] tokens, uint8 unitDecimals)` | Validates a market's pool and exact shape against the AMM protocol and stores them write-once under `marketId` | MarketRegistry, inside `listCollateralMarket` | `REQ-AMM-CORE-003`, `REQ-AMM-CORE-004` |
| `receivePosition(uint256 marketId, address owner, bytes32 positionKey) returns (uint128 units)` | Takes custody of a position from its owner, checks its pool and shape are exactly the market's, and returns the units it holds | Collateralization in `pledge`, Lock held | `REQ-AMM-CORE-005`, `REQ-AMM-CORE-006` |
| `validatePosition(uint256 marketId, address owner, bytes32 positionKey) returns (uint128 units)` (view) | Runs every check of `receivePosition` without moving anything and returns the units, or reverts with the error `receivePosition` would raise | RiskModule `previewPledge`, the Lens | `REQ-AMM-CORE-005` |
| `topUpPosition(bytes32 positionKey, address owner, bytes topUp) returns (uint128 unitsAdded)` | Adds units to a custodied position whose AMM protocol has no public way to do it (fungible LP shares) | Collateralization in `recredit`, Lock held | `REQ-AMM-CORE-011` |
| `returnPosition(bytes32 positionKey) returns (address depositor)` | Returns the whole position to its depositor of record | Collateralization when it closes a record, Lock held | `REQ-AMM-CORE-007` |
| `unwind(bytes32 positionKey, uint128 units, uint256[] minAmounts, address recipient) returns (uint256[] amounts)` | Removes exactly `units` and sends only their principal to an Avana recipient | Collateralization on seizure, reconciliation and deleverage release, Lock held | `REQ-AMM-CORE-008` |
| `releaseToDepositor(bytes32 positionKey, uint128 units, uint256[] minAmounts) returns (uint256[] amounts)` | Removes exactly `units` and sends only their principal to the depositor of record | Collateralization on partial removal, Lock held | `REQ-AMM-CORE-008` |
| `unitsOf(bytes32 positionKey) returns (uint128)` | Live units of a custodied position | Collateralization (re-credit), anyone while the Lock is free | `REQ-AMM-CORE-009` |
| `collectFees(bytes32 positionKey, address depositor) returns (uint256[] amounts)` | Collects accrued fees to the depositor of record | Collateralization, inside the Adapter's `collectFees` | `REQ-AMM-CORE-010` |
| `composition(uint256 marketId, uint256 units, uint256[] prices) returns (uint256[] amounts, bool exact)` | Token amounts `units` units hold at the price vector, from oracle prices only | Anyone (view) | `SPEC-AMM-CORE-001`, `REQ-AMM-CORE-012` |
| `riskMetadata(uint256 marketId, bytes32 positionKey) returns (RiskMetadata)` | Range status, pool lock, Avana's units and pool share, the named position's units | Anyone (view) | `REQ-AMM-CORE-013` |
| `riskStatus(uint256 marketId, uint32 window) returns (RiskStatus)` | Time-weighted pool depth in the market's units over `window` | RiskModule (pool-share cap and concentration gate), anyone (view) | `REQ-AMM-CORE-013` |
| `checkReadSafe(uint256 marketId)` (view) | Reverts `PoolLocked` while the pool is inside its own reentrancy lock | Collateralization before every custody, read and removal; the LPOracle before every quote | `REQ-AMM-CORE-018` |
| `consistencyDeviation(uint256 marketId, uint32 window, uint256[] prices) returns (uint256 deviationBps, bool available)` | Deviation between the AMM protocol's time-weighted price and the oracle vector; a consistency check only | LPOracle | `REQ-AMM-CORE-014` |
| `rateProviders(uint256 marketId)`, `wrappedNative()`, `isAllowedPoolHook(address hooks)`, `effectiveSupply(uint256 marketId)` | Hooks for rate tokens, native ETH, Uniswap v4 hooks and fungible-share supply | LPOracle, MarketRegistry at listing | `REQ-AMM-CORE-004`, `REQ-AMM-CORE-012` |
| `capabilities() returns (IntegrationCapabilities)`, `AMM_PROTOCOL()` | Fixed description: pool keying, fee mode, pricing mode, shape kind, TWAP, reentrancy guard, native token, rate tokens | Anyone | `REQ-AMM-CORE-001` |
| `marketOf(uint256 marketId) returns (address pool, bytes32 poolId, PositionShape shape, address[] tokens)`, `marketOfPosition(bytes32 positionKey) returns (uint256 marketId)`, `depositorOf(bytes32 positionKey) returns (address)`, `isInCustody(bytes32 positionKey) returns (bool)` | Stored market; the market and depositor of a custodied position | Anyone while the Lock is free; Collateralization while it is held | `REQ-AMM-CORE-009` |
| `returnStray(bytes32 positionKey, address recipient)` | Returns a position the LPVault holds with no record | AvanaTimelock (normal delay), Lock free | [2.2](02-lp-vault.md) `REQ-VAULT-165` |
| `INTEGRATION_ID()`, `COLLATERALIZATION()`, `MARKET_REGISTRY()`, `LOCK()`, `TIMELOCK()` | Constructor immutables | Anyone | [2.2](02-lp-vault.md) `REQ-VAULT-155` |

`PositionShape` fields: `kind` (`enum ShapeKind {None, TickRange, FullPool}`), `tickLower`, `tickUpper` (`int24`, 0 for `FullPool`). `RiskMetadata` fields: `inRange` (`bool`, false when the pool price lies outside the market's range; always true for `FullPool`), `readSafe` (`bool`, false while the pool lock is held), `avanaUnits` (0: an LPVault keeps no unit counter, [2.2](02-lp-vault.md) Storage; Avana's credited units in a market are Collateralization's `getTotalCredited(vaultToken)`, which the RiskModule reads), `poolUnits` (pool units the share is measured against), `poolShareBps = ⌊avanaUnits × 10^4 / poolUnits⌋` (so 0), `positionUnits` (units of the named position, 0 when none is named). `RiskStatus` fields: `depthUnits` (`uint256`, the pool's time-weighted depth over `window` in the market's units), `depthAvailable` (`bool`, false when the AMM protocol keeps no history covering the window). `IntegrationCapabilities` fields: `poolKeying` (`Address` or `Id`), `feeMode` (`Separate` or `RolledIn`), `pricingMode` (`ClosedForm` or `LowerBound`), `shapeKind`, `hasTwap`, `reentrancyGuarded`, `nativeToken`, `rateTokens`.

## Requirements

- `REQ-AMM-CORE-001` — Every AMM integration MUST implement the functions above with these signatures, and the AMM-neutral core MUST call an AMM protocol only through them: Collateralization, the vault tokens, the Adapter and LPVaultSwap make no call to a position manager, factory, pool or AMM vault. Each AMM protocol's rules (pool derivation, the shape check, the liquidity read, the pool lock, removal and fee calls) live in its integration page, so a later AMM protocol is added without changing the immutable ledger or the vault-token factory. (Source: Q-291, Q-292)
- `REQ-AMM-CORE-002` — Each chain MUST have at most one LPVault per AMM protocol, registered write-once in the VaultTokenFactory as `lpVaultOf(integrationId)` by `registerIntegration(integrationId, lpVault)`, an AvanaTimelock operation at the normal delay ([2.4](04-vault-tokens.md) `REQ-VTOKEN-044`); the registration requires `integrationId != 0` and the LPVault's `INTEGRATION_ID()`, `COLLATERALIZATION()` and `LOCK()` to equal the expected values (`InvalidIntegration`). Collateralization takes an integration's LPVault only from a validated vault token's `integration()`, which the factory set from that registry, and the MarketRegistry's `integrationOf(integrationId)` must name the same LPVault (drift check, [2.8](08-market-registry.md)). Why: the ledger is immutable and serves every AMM protocol on the chain, so the binding from `integrationId` to its custodian must come from an immutable, write-once source. Blast radius of a hostile registration: only markets of that new `integrationId`, bounded by their Hub caps; positions held by any other LPVault are untouched. (Source: Q-291, Q-374)
- `REQ-AMM-CORE-003` — `bindMarket(marketId, pool, poolId, shape, integrationData)` MUST revert with `NotMarketRegistry` unless `msg.sender == MARKET_REGISTRY` and with `MarketBinding(marketId)` if `marketId` is already bound; it MUST require exactly one of `pool` and `poolId` per `capabilities().poolKeying`, validate the pool against the AMM protocol's pinned factory or singleton (`InvalidPool`) and the shape (`InvalidShape`: for `TickRange`, `tickLower < tickUpper`, both aligned with signed `int24` `tick % tickSpacing == 0` as [2.10](10-lp-oracle.md) `REQ-ORACLE-105` checks, inside the usable ticks), run every listing guard of that AMM protocol in its integration page (token count, per-token flags, rate providers, hook allowlist), read the tokens, decimals and pool settings on-chain, store them write-once under `marketId`, emit `MarketBound(marketId, pool, poolId, tickLower, tickUpper)` and return `(tokens, unitDecimals)`. A bound market's pool, shape and tokens never change. The MarketRegistry calls it inside `listCollateralMarket`, in the same timelock batch as `VaultTokenFactory.deployVaultToken`, and requires the token's `marketId()`, `integrationId()` and `decimals()` to match. Why: the shape every pledge is matched against must be fixed by the immutable integration at listing, not passed in by an upgradeable caller at pledge time (`Q-293`). (Source: Q-291, Q-293, Q-371)
- `REQ-AMM-CORE-004` — A market MUST have between 2 and `MAX_POOL_TOKENS = 8` tokens, each an ERC-20 with no transfer hook, no rebasing and no fee on transfer at listing. Native ETH is never a market token: an AMM protocol that pays native ETH has its integration wrap it into WETH inside the same call and list WETH, and the LPVault accepts ETH only while the Lock is held and only from that AMM protocol's pool or vault. A rate token (ERC-4626 share or a token priced through a rate oracle) is allowed only when `rateProviders(marketId)[i]` is an approved, capped rate feed of the LPOracle; otherwise `bindMarket` reverts `InvalidPool`. A native ETH leg is reported by `capabilities().nativeToken` and carried as `wrappedNative()`. Why: the core moves and values tokens as plain ERC-20s; a native-ETH payout would run the recipient's code mid-settlement, and a self-reported rate can be raised by a donation inside one transaction (`AMMN-RT-07`). (Source: Q-297, Q-302)
- `REQ-AMM-CORE-005` — `receivePosition(marketId, owner, positionKey)` MUST revert with `NotCollateralization` unless `msg.sender == COLLATERALIZATION`, with `LockNotHeld` unless the Lock is held by the AaveAdapter or LPVaultSwap, with `MarketBinding(marketId)` unless `marketId` is bound, with `PoolLocked` while the AMM protocol reports the pool mid-operation, with `NotTokenOwner` unless `owner` is the position's current owner and is not the LPVault itself, and with `PositionEncumbered` for a position whose owner of record is a staking or gauge contract; it MUST take the position from `owner` without running a receiver hook on the LPVault, require the LPVault to own it afterwards, set `depositorOf(positionKey) = owner` and `marketOfPosition(positionKey) = marketId`, read the units it now holds (`ZeroUnits` at 0), emit `PositionReceived` and return `units`. `units` is read after custody, so no code of the owner runs between the read and the record. `validatePosition(marketId, owner, positionKey)` runs the same checks as a view and moves nothing. (Source: Q-224, Q-258, Q-291, Q-292)
- `REQ-AMM-CORE-006` — **Exact shape at pledge (`AMMN-RT-01`).** `receivePosition` MUST revert with `PoolMismatch` unless the position's pool equals the market's pool, derived through the market's pinned factory, and with `RangeMismatch(tickLower, tickUpper)` unless its shape equals the market's stored shape exactly: for concentrated liquidity, `tickLower == market.tickLower` and `tickUpper == market.tickUpper`. Collateralization repeats the check independently by requiring `marketOfPosition(positionKey) == vaultToken.marketId()` after custody (`ShapeMismatch`) ([2.3](03-collateralization.md) `REQ-COLL-024`). Why: one unit of concentrated liquidity is worth a different amount in every range, and the market's LPOracle prices units of the market's range only; a position one tick each side of the price, credited at the value of a wider market range, would be overvalued many times over (`SPEC-AMM-CORE-001` example). Checked by: MATH-AMM-V3-PRICE-06 (AMM-A6a–A6c), AMM-A5a, AMM-A5b, HYP-AMM-05 (alignment of the stored range). (Source: Q-293)
- `REQ-AMM-CORE-007` — `returnPosition(positionKey)` MUST revert with `NotCollateralization` unless `msg.sender == COLLATERALIZATION`, with `LockNotHeld` unless the Lock is held by the AaveAdapter or LPVaultSwap, and with `NotInCustody` unless `depositorOf(positionKey) != address(0)`; it MUST delete the custody entry before the position leaves, send the whole position, with every live unit and every fee owed to it, to `depositorOf(positionKey)` without running a receiver hook, and return that depositor. It takes no recipient. (Source: Q-009, Q-067, Q-105, Q-224)
- `REQ-AMM-CORE-008` — `unwind(positionKey, units, minAmounts, recipient)` and `releaseToDepositor(positionKey, units, minAmounts)` MUST revert with `NotCollateralization`, `LockNotHeld`, `NotInCustody` or `PoolLocked` as `receivePosition` does, revert with `InvalidRecipient` if `recipient` is `address(0)` or the LPVault, revert with `LengthMismatch` unless `minAmounts.length` equals the market's token count, and then remove exactly `units` from the position and send only the principal of that removal (never a fee owed to the position) to `recipient`, or to `depositorOf(positionKey)` for `releaseToDepositor`, returning the `n` amounts the AMM protocol reports, with each `amounts[i] ≥ minAmounts[i]` or a revert. The AMM call and its payout run back to back inside one call under the Lock, so no fee collection can run between them. A removal whose amounts are all 0 skips the payout and still debits the units. Collateralization passes zero minimums to `unwind` (LPVaultSwap applies an oracle-derived minimum on every swap leg, [2.11](11-lpvaultswap.md)) and the depositor's minimums to `releaseToDepositor`. Why zero minimums are safe for seizure: at any pool state, the tokens a pro-rata removal returns are worth at least the fair-composition value at oracle prices, so moving the pool before a removal shifts value to Avana, not from it; this holds for every pricing model of `SPEC-AMM-CORE-001` and fails only for AMM protocols whose removal runs third-party code, which [2.22](22-amm-integration-readiness.md) excludes. Checked by: MATH-AMM-V3-PRICE-01, MATH-AMM-V2-PRICE-01, MATH-AMM-V2-PRICE-02, MATH-AMM-V2-PRICE-03, MATH-AMM-BAL-PRICE-01, MATH-AMM-CURVE-PRICE-01, AMM-A1a, AMM-B1a, AMM-B2d, AMM-B3d, AMM-C1a, AMM-C2c, HYP-AMM-01, HYP-AMM-06, HYP-AMM-10, HYP-AMM-11. (Source: Q-061, Q-131, Q-217, Q-271, Q-297)
- `REQ-AMM-CORE-009` — `unitsOf(positionKey)` MUST return the position's live units in the AMM protocol and revert with `NotInCustody` for a position without a custody entry. Live units may exceed the units Collateralization credits (liquidity anyone adds) and never fall below them, because the LPVault removes only units Collateralization debits. `unitsOf`, `depositorOf`, `marketOfPosition` and `isInCustody` revert with `Locked` while the Lock is held unless `msg.sender == COLLATERALIZATION`. (Source: Q-066, Q-067, Q-119, Q-254)
- `REQ-AMM-CORE-010` — **Fees.** Where the AMM protocol keeps fees apart from principal (`capabilities().feeMode == Separate`: Uniswap v3, Slipstream, Uniswap v4), `collectFees(positionKey, depositor)` MUST revert with `NotCollateralization` unless called by Collateralization while the Lock is held and with `NotDepositor` unless `depositor == depositorOf(positionKey)`, change no unit of the position, read no pause, breaker, price or policy, and pay every fee and every amount owed to the position to the depositor of record only. Where fees compound into the position (`feeMode == RolledIn`: Uniswap v2, Curve, Balancer), `collectFees` MUST revert with `FeesRolledIn`; the fees raise the value of each unit instead, and the depositor receives them when the position returns. No integration counts uncollected fees in `composition`. (Source: Q-009, Q-011, Q-030, Q-218, Q-297)
- `REQ-AMM-CORE-011` — **Top-up hook.** Collateralization's `recredit` takes a `bytes topUp` argument and calls `topUpPosition` only when `topUp` is non-empty. An integration whose positions anyone can add to directly (an NFT position's `increaseLiquidity`) MUST revert `topUpPosition` with `TopUpNotSupported`, so its re-credit passes an empty `topUp` and credits the live units above `credited`. An integration of fungible LP shares MUST implement `topUpPosition(positionKey, owner, topUp)` by pulling exactly the LP amount encoded in `topUp` from `owner`, who must be the position's depositor of record, into the same position, and return the units added, measured as the LPVault's own LP balance delta. Why: an account holds at most 16 records per market (`REQ-COLL-025`), so adding collateral must not require a new record. (Source: Q-254, Q-294, Q-297)
- `REQ-AMM-CORE-012` — `composition(marketId, units, prices)` MUST compute the amounts per `SPEC-AMM-CORE-001` from `prices`, `units` and stored market data only, MUST NOT read a pool's spot price, reserves or balances except the invariant inputs the integration page names, and MUST return `exact = false` when the AMM protocol has no closed form at an oracle price (Curve), in which case the amounts are a lower bound of the fair amounts. A revert of any pool read it makes counts as a price failure for the market. The LPOracle's pricing module computes its `composition(units, prices)` with the same function ([2.10](10-lp-oracle.md) `REQ-ORACLE-103`): `composition(units, priceVector)` returns raw amounts rounded down, and for concentrated liquidity it is [2.10](10-lp-oracle.md) `SPEC-ORC-006` (clamp the oracle sqrt price to `[sqrtRatio(tickLower), sqrtRatio(tickUpper)]`, then `getAmountsForLiquidity`, floor). (Source: Q-293, Q-302, Q-321, Q-325)
- `REQ-AMM-CORE-013` — `riskMetadata(marketId, positionKey)` MUST report `inRange` from the pool's current price against the market's range (true for `FullPool` markets), `readSafe` from the AMM protocol's own reentrancy state, `avanaUnits`, `poolUnits` and `poolShareBps` as defined under [Functions](#functions), and the named position's units. `riskStatus(marketId, window)` MUST report `depthUnits` as the pool's time-weighted depth over `window` in the market's own units (for concentrated liquidity the harmonic-mean in-range liquidity of the `observe` buffer; for fungible shares the effective LP supply of `effectiveSupply`), with `depthAvailable = false` when the AMM protocol keeps no history that covers the window. The RiskModule passes the market's `twapWindow`, compares `vaultToken.totalSupply() + L` with `depthUnits` for the pool-share cap ([2.7](07-risk-module.md) `SPEC-CAP-005`), and treats `depthAvailable = false` as a share above the cap. (Source: Q-295, Q-371)
- `REQ-AMM-CORE-014` — **Quote-change cap.** The LPOracle implementation of every AMM protocol MUST cap the change of its per-unit quote between two blocks at `maxQuoteChangeBps` of the market (for example 100, 1%) and serve a larger move as Cached until a later block confirms it ([2.10](10-lp-oracle.md)). Why: even with fair composition, a fungible-share quote reads invariant inputs from the pool, and one block of swaps or donations can raise it (v2 by up to 0.1503% per swap, StableSwap virtual price by up to 27% after a large imbalancing swap); the cap keeps any one-block move from reaching borrowing power. Checked by: MATH-AMM-V2-PRICE-02, MATH-AMM-V2-PRICE-06, MATH-AMM-CURVE-PRICE-02, MATH-AMM-BAL-PRICE-02, AMM-B2b, AMM-B11, AMM-C3, AMM-C6, HYP-AMM-07. (Source: Q-302)
- `REQ-AMM-CORE-015` — **Unwind size.** A market MUST NOT be listed unless the gas of its worst-case seizure, `seizureBaseGas + MAX_RECORDS_PER_ACCOUNT_MARKET × perRecordUnwindGas`, measured on a fork of its chain at listing, stays at or below 8,000,000 (under half of the 16,777,216 per-transaction gas cap). For fungible-LP AMM protocols, an integration MAY unwind through a single-token exit (`remove_liquidity_one_coin`, a Balancer single-token exit); LPVaultSwap then applies its oracle-derived minimum to the one output token. Why: Aave's dust rule seizes the last chunk of an account whole, so every record of an account may need to unwind in one transaction (`AMMN-GAS-01`), and each extra token adds a removal leg and a swap route (`AMMN-GAS-13`). Example: a v3 seizure costs about 1,310,000 gas plus about 240,000 per record (1,550,000 for one record), so 16 records cost 5,150,000; a proportional exit of an 8-token pool costs about 3,000,000 per record, which would not fit 16 records and is listed only with a single-token exit (about 1,300,000). (Source: Q-294, Q-297)

## Math

Units: `prices[i]` in USD per whole token, 8 decimals; `amounts[i]` in raw units of token `i` with `dec_i` decimals; `units` in the market's units. Rounding uses OpenZeppelin `Math.mulDiv` (v5.1.0).

- `SPEC-AMM-CORE-001` — **Fair composition.** For a market `m`, a price vector `p` and `u` units: `(a_1 … a_n, exact) = composition(m, u, p)`, where each integration computes the amounts the `u` units would hold if the pool traded exactly at the price ratio implied by `p`, over the market's exact shape. For concentrated liquidity, the oracle price ratio is clamped to the market's range before the amounts are read. Each `a_i` is rounded down and then reduced by 1 raw unit when positive. The value is `value8 = Σ_i mulDiv(a_i, p_i, 10^dec_i, Floor)`. Never: spot reserves or `slot0` amounts, an assumed 50/50 split, or pool weights × price. Why: the pool's own state can be moved inside one transaction, while the amounts at the oracle ratio cannot; for every pool type the fair value at oracle prices is the minimum of the redeemable value over all pool states the attacker can reach, so a manipulated pool can only make Avana's collateral worth more on removal than the quote, never less. Rounding down and subtracting one raw unit keeps the quote at or below the exact fair value even where the oracle square root itself is floored. Units: USD, 8 decimals. Rounding: down at every step. Bounds: `n ≤ 8`; each product below `2^256` for `a_i < 2^128` and `p_i < 2^96`. Example: a USDC/USDT market on the range `[−50, 50]` (tick spacing 10, 6 decimals each) at `p = (100,000,000, 100,000,000)`: `10^9` units hold `(2,496,752, 2,496,752)` raw, reduced to `(2,496,751, 2,496,751)`, worth `499,350,200` ($4.99). With USDT at `p_1 = 64,000,000` the clamped ratio is above the range, so the same units hold `(0, 4,999,754)` and are worth $3.19. A position on `[−1, 1]` with $10,000 of tokens has about `1.0001 × 10^14` units; credited in this market at its per-unit value it would be worth $499,388, ×49.9 its real value, which is why `REQ-AMM-CORE-006` refuses it. Checked by: MATH-AMM-V3-PRICE-01, MATH-AMM-V3-PRICE-03, MATH-AMM-V3-PRICE-04, MATH-AMM-V2-PRICE-01, MATH-AMM-BAL-PRICE-01, MATH-AMM-CURVE-PRICE-01, AMM-A1a, AMM-A1b, AMM-A3a, AMM-A3f, AMM-A4a, AMM-B1a, AMM-C1a, AMM-C2c, HYP-AMM-01, HYP-AMM-03, HYP-AMM-04, HYP-AMM-10, HYP-AMM-11. (Source: Q-293, Q-302)
- `SPEC-AMM-CORE-002` — **Keys.** `marketKey = keccak256(abi.encode(block.chainid, integrationId, pool, poolId, shape.kind, shape.tickLower, shape.tickUpper))`, computed by the VaultTokenFactory's `marketKeyOf`; two ranges of one pool are two markets with two keys, and the same pool and range under another integration is another market. `positionKey` is the integration's encoding of its position: Uniswap v3 `bytes32(tokenId)` ([2.20](20-uniswap-v3-integration.md)); Slipstream `bytes32((uint256(generation) << 248) | tokenId)` with `tokenId < 2^248`, the generation naming one of the four position manager and factory pairs on Base ([2.21](21-aerodrome-slipstream-integration.md)); fungible LP shares `keccak256(abi.encode(marketId, depositor, nonce))` with a per-LPVault nonce that never repeats. Records, events and indexes use `(chainId, Collateralization, integrationId, positionKey)`. Why: `tokenId`s collide across position managers (Slipstream has four on Base) and across chains; keying by the integration and encoding the generation in the key keeps every key unique and reversible, so the LPVault decodes the manager and the token from the key alone. Units: none. Rounding: none. Bounds: a position manager's token IDs grow by one per mint, so `2^248` is never reached. Example: Slipstream NFT 1,234,567 of generation 2 has `positionKey = 0x02000000…0012d687` (`2 << 248 | 0x12d687`); the same `tokenId` of generation 0 has `0x00000000…0012d687`, a different key. (Source: Q-292, Q-370)
