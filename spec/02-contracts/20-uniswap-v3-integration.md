# 2.20 Uniswap v3 Integration

> **Status:** In review · **Owner:** Avana Labs · **Last reviewed:** 2026-11-10
>
> **Requirement prefix:** `REQ-AMM-V3-NNN`, and the custody rules that keep their `REQ-VAULT-NNN` IDs · **Math prefix:** `SPEC-AMM-V3-NNN`, and `SPEC-BACK-001`, `SPEC-BACK-008`, which keep their IDs

## Purpose

The Uniswap v3 integration is Avana's code for Uniswap v3 concentrated-liquidity positions on Ethereum (chain ID 1): one immutable Uniswap v3 LPVault that implements the AMM integration interface ([2.19](19-amm-integration-interface.md)) with `AMM_PROTOCOL() = keccak256("UNISWAP_V3")` and the `INTEGRATION_ID` registered for it in the chain's VaultTokenFactory (`IUniswapV3Integration`, `contracts/src/amm/uniswap-v3/`), and the concentrated-liquidity pricing library that the LPVault and the Uniswap v3 LPOracle implementation ([2.10](10-lp-oracle.md)) compile in. It holds every rule that names the NonfungiblePositionManager (NFPM), an NFT `tokenId` or a tick. The AMM-neutral custody rules are on [2.2](02-lp-vault.md) and the ledger rules on [2.3](03-collateralization.md).

A Uniswap v3 market is one (pool, `tickLower`, `tickUpper`): an exact range, which can be the full usable range or a bounded one. Units are Uniswap v3 liquidity (`uint128`), one unit per vault-token base unit. A position is an NFPM NFT; its `positionKey` is `bytes32(tokenId)`, unique because the LPVault accepts positions of one NFPM only (`SPEC-AMM-CORE-002`, `REQ-AMM-V3-001`).

## Requirements

### Integration and markets

- `REQ-AMM-V3-001` — The Uniswap v3 LPVault MUST take `NFPM` and `FACTORY` from its constructor and revert deployment with `InvalidDeployment` unless `NFPM.factory() == FACTORY` and neither address is zero or one of the Avana bindings; it accepts positions of that NFPM only, never another ERC-721 contract or a Uniswap v3 fork, because the custody logic is immutable and a fork's position data cannot be trusted. The deployment check verifies both addresses against the chain's manifest. (Source: Q-226, Q-291, Q-305)
- `REQ-AMM-V3-002` — `bindMarket(marketId, pool, bytes32(0), PositionShape(TickRange, tickLower, tickUpper), integrationData)` MUST revert with `InvalidPool` unless `pool.factory() == FACTORY`, `FACTORY.getPool(pool.token0(), pool.token1(), pool.fee()) == pool` and `pool` equals the CREATE2 address `FACTORY` derives from `keccak256(abi.encode(token0, token1, fee))` and `POOL_INIT_CODE_HASH`; with `InvalidPool` unless `pool.tickSpacing()` is the spacing of a standard fee tier (fee 100 → 1, 500 → 10, 3,000 → 60, 10,000 → 200); and with `InvalidShape` unless the range satisfies `SPEC-BACK-001`. `integrationData` is `abi.encode(uint256 price0, uint256 price1)`, the listing valuation prices of `token0` and `token1` (8 decimals), and `unitDecimals` is [2.10](10-lp-oracle.md) `SPEC-ORC-005` at those prices over this market's composition (`SPEC-AMM-V3-001`): the smallest `d` in `[6, 18]` with `price8(10^d) ≥ 10^8`, as [2.4](04-vault-tokens.md) `SPEC-UNIT-001` defines it. It reverts with `InvalidPool` when `integrationData` is not 64 bytes, a listing price is 0 or above `MAX_ROUTE_ANSWER`, no `d` in `[6, 18]` passes, or a token has no `decimals()` or more than 18; with `MarketBinding(0)` for `marketId = 0`, which `marketOfPosition` reserves for "not in custody"; with `InvalidPool` for a non-zero `poolId`; and with `InvalidShape` for any kind other than `TickRange`. It stores `(pool, token0, token1, fee, tickSpacing, tickLower, tickUpper)` with the NFPM, the factory, `maxLiquidityPerTick(tickSpacing)` and both token decimals, returns tokens `[token0, token1]` and `unitDecimals`, and emits `MarketBound`. Example: USDC/USDT (6, 6) at $1 each gives `unitDecimals = 9` on `[−50, 50]` of the 0.05% pool and 6 on the full range of the 0.3% pool; MarketRegistry then requires the vault token's `decimals()` to equal it. Why each pool check: a copied configuration can pair an NFPM with the wrong factory, and a pool that only looks canonical can be a thin attacker-seeded fork (`AMMN-RT-15`); deriving the address from the init code hash proves the pool runs Uniswap v3's code. (Source: Q-043, Q-177, Q-293, Q-305)
- `REQ-AMM-V3-003` — Every read of `pool.slot0()` MUST decode the Uniswap v3 layout of 7 fields, `(uint160 sqrtPriceX96, int24 tick, uint16 observationIndex, uint16 observationCardinality, uint16 observationCardinalityNext, uint8 feeProtocol, bool unlocked)`, and every read of `NFPM.positions(tokenId)` the 12-field layout `(uint96 nonce, address operator, address token0, address token1, uint24 fee, int24 tickLower, int24 tickUpper, uint128 liquidity, uint256 feeGrowthInside0LastX128, uint256 feeGrowthInside1LastX128, uint128 tokensOwed0, uint128 tokensOwed1)`. The LPVault reverts with `PoolLocked` while `slot0().unlocked == false`, checked before every `receivePosition`, `unwind`, `releaseToDepositor` and `unitsOf` read made under the Lock, so no NFPM call and no liquidity read runs while the pool is inside a swap or flash callback; fee collection relies on the pool's own reentrancy lock instead (`REQ-VAULT-066`). Why fixed layouts: Slipstream's `slot0` has 6 fields, and decoding it with the v3 ABI reads the wrong word for `unlocked` ([2.21](21-aerodrome-slipstream-integration.md)). The LPOracle's concentrated-liquidity implementation fixes the layout the same way at deployment (`slot0Words = 7` here, 6 on Slipstream) and reads only `unlocked` (the last word) and `observationCardinality` (word 3), never the price or tick ([2.10](10-lp-oracle.md#concentrated-liquidity-pricing-uniswap-v3-and-aerodrome-slipstream)). (Source: Q-085, Q-128, Q-144, Q-305)
- `REQ-AMM-V3-004` — The Uniswap v3 LPVault MUST make every state-changing NFPM call on pledged NFTs (`transferFrom`, `decreaseLiquidity`, `collect`) and MUST NOT grant any NFPM approval or operator, call `setApprovalForAll`, call `NFPM.burn` or `safeTransferFrom` out of custody. No other contract can therefore move a custodied NFT, its liquidity or its fees. (Source: Q-030, Q-061, Q-224)
- `REQ-AMM-V3-005` — `composition` MUST follow `SPEC-AMM-V3-001` and read no pool state: the price input is the oracle price vector only, and uncollected fees (`tokensOwed`, fee growth) are never counted. Out of range the position is one token and is valued as that token alone. Checked by: MATH-AMM-V3-PRICE-01, MATH-AMM-V3-PRICE-03, MATH-AMM-V3-PRICE-04, AMM-A1a, AMM-A3f, AMM-A4a, HYP-AMM-01, HYP-AMM-04. (Source: Q-293, Q-302)
- `REQ-AMM-V3-006` — `riskMetadata(marketId, positionKey)` MUST report `inRange` as `tickLower ≤ slot0().tick < tickUpper`, `readSafe = slot0().unlocked`, `poolUnits = ⌊pool.liquidity() / 10^k⌋`, `avanaUnits = 0` and `poolShareBps = 0` (the LPVault keeps no unit counter, [2.2](02-lp-vault.md) Storage; Avana's units in a market are Collateralization's credited total, which the RiskModule reads for `SPEC-CAP-005` and `SPEC-BRK-002`), and `positionUnits` as the named position's live `⌊NFPM.positions(tokenId).liquidity / 10^k⌋` (0 for `bytes32(0)`); `riskStatus(marketId, window)` MUST report `depthUnits` as Uniswap v3-periphery `OracleLibrary.consult(pool, window)`'s `harmonicMeanLiquidity` (time-weighted in-range liquidity, floor) divided by `10^k`, floor, with `depthAvailable = false` when `observe` cannot cover the window; `checkReadSafe` reverts `PoolLocked` while `slot0().unlocked == false`. In-range liquidity is in the same unit for every range of the pool and `k` is one value per pool, so the RiskModule compares the pool's credited units plus the pledge with it ([2.7](07-risk-module.md) `SPEC-CAP-005`). The consistency check needs `⌈W / BLOCK_TIME⌉ + 1` observations (`REQ-AMM-V3-012`): 151 on Ethereum and 901 on Base for a 1,800 s window ([2.10](10-lp-oracle.md) `SPEC-ORC-022`). (Source: Q-054, Q-295, Q-326)
- `REQ-AMM-V3-007` — The Uniswap v3 liquidity bound MUST hold for every market: credited liquidity on one range is at most `maxLiquidityPerTick(s) = type(uint128).max / numTicks(s)`, which is about `1.92 × 10^32` for `s = 1` and `3.83 × 10^34` for `s = 200`, both below `MAX_CREDITED_UNITS = 2^120 − 1`. Checked by: MATH-AMM-V3-PRICE-05, AMM-A5d, MATH-UO-04. (Source: Q-066, Q-191)
- `REQ-AMM-V3-012` — The Uniswap v3 LPVault MUST take the chain's minimum block interval `BLOCK_TIME` (seconds) from its constructor and expose it; the constructor MUST revert with `InvalidDeployment` for 0, for a value above 12, and on a chain whose interval Avana knows for any other value: 12 on Ethereum (chain 1) and Sepolia (11155111), 2 on Base (8453), Base Sepolia (84532) and OP Mainnet (10). `consistencyDeviation` sizes the required observation cardinality with it (`⌈W / BLOCK_TIME⌉ + 1`, [2.10](10-lp-oracle.md) `SPEC-ORC-022`). Why: Uniswap v3 runs on chains with 12 s and 2 s blocks, and a fixed 12 s would under-size the buffer six times on Base, so a busy pool's `observe` would fail and the TWAP second source fall away exactly when activity is high; the chain check refuses a deployment with the wrong interval, which the deployment check also compares with the ParameterStore's `CHAIN_BLOCK_TIME`. Example: on Base with `BLOCK_TIME = 2`, a 1,800 s window needs a cardinality of 901; a constructor given 12 on Base reverts. (Source: Q-371)

### Custody (rules moved from 2.2)

- `REQ-VAULT-147` — The Uniswap v3 `receivePosition(marketId, owner, positionKey)`, with `tokenId = uint256(positionKey)`, MUST run every check before it writes or moves anything, in this order: revert with `NotCollateralization` unless `msg.sender == COLLATERALIZATION`, with `LockNotHeld` unless the Lock is held by the AaveAdapter or LPVaultSwap, with `MarketBinding(marketId)` unless `marketId` is bound, with `PoolLocked` while `slot0().unlocked == false` (`REQ-AMM-V3-003`), with `NotTokenOwner` if `owner == address(this)` or unless `NFPM.ownerOf(tokenId) == owner`, and with `PoolMismatch` or `RangeMismatch(tickLower, tickUpper)` unless the position passes `REQ-VAULT-008` and `REQ-VAULT-009`. It then sets `depositorOf(positionKey) = owner` and `marketOfPosition(positionKey) = marketId`, calls `NFPM.transferFrom(owner, address(this), tokenId)` (never `safeTransferFrom`, so no receiver hook runs and Safes without one work), requires `NFPM.ownerOf(tokenId) == address(this)`, reads `liquidity` per `REQ-VAULT-162` (`ZeroUnits` at 0), emits `PositionReceived(positionKey, marketId, owner, liquidity)` and returns `liquidity`. The custody entry is written before the pull (checks-effects-interactions) and the units are read after it, so no code of the owner runs between the read and the record; any later failure reverts the whole call, entry included. The owner's per-token approval (or NFPM `permit`) to the LPVault is what makes the pull succeed; the LPVault accepts no signature itself. Why: requiring the owner here, in the contract that holds the NFT, means the depositor of record is always the wallet the NFT came from, whatever wallet the upgradeable Adapter names; refusing the LPVault itself as owner means a stray NFT it holds, for which the ownership check would pass and a transfer to itself would succeed, can never become a record. (Source: Q-067, Q-073, Q-224, Q-258, Q-292)
- `REQ-VAULT-148` — The Uniswap v3 `returnPosition(positionKey)` MUST revert with `NotCollateralization`, `LockNotHeld` or `NotInCustody` per [2.19](19-amm-integration-interface.md) `REQ-AMM-CORE-007`; then read `depositor = depositorOf(positionKey)`, delete the custody entry, call `NFPM.transferFrom(address(this), depositor, tokenId)`, emit `PositionReturned(positionKey, depositor)` and return `depositor`. The NFT goes only to the depositor of record, with all its live liquidity (including donated liquidity) and all uncollected fees. (Source: Q-009, Q-067, Q-105, Q-224)
- `REQ-VAULT-149` — The Uniswap v3 `unwind(positionKey, units, minAmounts, recipient)` MUST pass the checks of `REQ-AMM-CORE-008` and `REQ-AMM-V3-003`; then call `(a0, a1) = NFPM.decreaseLiquidity({tokenId, liquidity: units · 10^k, amount0Min: minAmounts[0], amount1Min: minAmounts[1], deadline: block.timestamp})` and immediately `NFPM.collect({tokenId, recipient, amount0Max: a0, amount1Max: a1})` per `SPEC-BACK-008`, skipping the `collect` when `a0 = a1 = 0`, emit `UnitsUnwound(positionKey, units, recipient, [a0, a1])` and return `[a0, a1]`. The two NFPM calls run back to back inside one call under the Lock, so nothing can collect fees between them, and the cap keeps every accrued fee owed to the NFT. Collateralization passes zero minimums: at any pool price the tokens a removal returns are worth at least their fair-composition value at oracle prices (`SPEC-AMM-V3-001`), so moving the pool price before a removal shifts value to Avana, not from it, and the minimums that protect value are the oracle-derived ones on every swap leg of LPVaultSwap; the outer LPVaultSwap or Adapter call carries the caller's deadline. The recipient is LPVaultSwap for a seizure and a deleverage release and Collateralization for a reconciliation; each measures what it receives by balance delta (`Q-271`). Checked by: MATH-AMM-V3-PRICE-01, AMM-A1a, HYP-AMM-01. (Source: Q-061, Q-085, Q-131, Q-216, Q-217, Q-224, Q-250, Q-255, Q-271)
- `REQ-VAULT-161` — The Uniswap v3 `releaseToDepositor(positionKey, units, minAmounts)` MUST pass the checks of `REQ-AMM-CORE-008` and `REQ-AMM-V3-003`; then call `(a0, a1) = NFPM.decreaseLiquidity({tokenId, liquidity: units · 10^k, amount0Min: minAmounts[0], amount1Min: minAmounts[1], deadline: block.timestamp})` and immediately `NFPM.collect({tokenId, recipient: depositorOf(positionKey), amount0Max: a0, amount1Max: a1})` per `SPEC-BACK-008`, skipping the `collect` when `a0 = a1 = 0`, emit `UnitsReleased(positionKey, units, depositor, [a0, a1])` and return `[a0, a1]`. It takes no recipient, so the principal of a partial removal goes only to the depositor of record. The NFPM enforces the depositor's minimums (its `Price slippage check` error passes through), which bound what a pool price moved before inclusion can cost the depositor. Example: Collateralization debits 1,000,000,000 units from NFT 42 for alice and calls `releaseToDepositor(key42, 1,000,000,000, [995,000,000, 995,000,000])`; at a pool price of 1 on a full-range USDC/USDT market the removal returns about 1,000 USDC and 1,000 USDT, both above the minimums, which the pool sends straight to alice while the NFT's 12.40 USDC of fees stay owed. (Source: Q-061, Q-105, Q-217, Q-224, Q-254)
- `REQ-VAULT-162` — The Uniswap v3 `unitsOf(positionKey)` MUST revert with `NotInCustody` without a custody entry and otherwise return `⌊NFPM.positions(tokenId).liquidity / 10^k⌋`, `k` the market's unit exponent ([2.10](10-lp-oracle.md) `SPEC-ORC-005`, `unitExponent(marketId)`); it reverts with `Locked` per [2.2](02-lp-vault.md) `REQ-VAULT-151`. Collateralization reads it in `recredit` to credit exactly the live units above `credited`. (Source: Q-224, Q-254)
- `REQ-VAULT-065` — The Uniswap v3 `collectFees(positionKey, depositor)` MUST require `depositor == depositorOf(positionKey)` (`NotDepositor`), call `NFPM.collect({tokenId, recipient: depositorOf(positionKey), amount0Max: type(uint128).max, amount1Max: type(uint128).max})` and nothing else on the NFPM: no `decreaseLiquidity`, no change to the NFT's liquidity, and MUST emit `FeesCollected(positionKey, depositor, [amount0, amount1])`. A zero result pays 0 and does not revert. The NFPM pays every owed amount of the NFT, so principal owed at pledge (`tokensOwed0`, `tokensOwed1` left by a `decreaseLiquidity` the depositor made before pledging and never collected) is paid here to the depositor along with fees: it was never credited (`REQ-VAULT-147` credits only `liquidity`), the LPOracle never values it, and removals collect only the principal their own `decreaseLiquidity` returned (`SPEC-BACK-008`). Example: an NFT pledged with 50 USDC of owed principal and 3 USDC of uncollected fees is credited only its liquidity; a later fee collection pays all 53 USDC to the depositor. (Source: Q-011, Q-030, Q-105, Q-218)

### Pool and range checks at pledge (rules moved from 2.3)

- `REQ-VAULT-008` — The Uniswap v3 `receivePosition` MUST read `(token0, token1, fee, tickLower, tickUpper)` from `NFPM.positions(tokenId)`, derive `pool = FACTORY.getPool(token0, token1, fee)`, and revert with `PoolMismatch` unless `pool != address(0)` and `pool == markets[marketId].pool`. A caller-supplied pool is never used. (Source: Q-054, Q-075, Q-119, Q-226, Q-293)
- `REQ-VAULT-009` — The Uniswap v3 `receivePosition` MUST revert with `RangeMismatch(tickLower, tickUpper)` unless `tickLower == markets[marketId].tickLower` and `tickUpper == markets[marketId].tickUpper` (`SPEC-BACK-001`), compared by exact equality (`AMMN-RT-01`). A position whose range differs from the market's by any number of ticks, wider or narrower, is never credited. (Source: Q-017, Q-119, Q-293)
- `REQ-VAULT-011` — The borrower MUST grant the per-token `NFPM.approve(LPVault, tokenId)` or an NFPM `permit` before a pledge; app-built calldata never uses `setApprovalForAll`, and the NFT approval goes to the immutable LPVault, which moves an NFT only on Collateralization's instruction. Collateralization and the LPVault accept no permit or other signature. (Source: Q-073, Q-119, Q-144, Q-224)

### Removal (rules moved from 2.3)

- `REQ-VAULT-057` — For each record debited for a seizure with debit `take > 0`, the Uniswap v3 removal MUST call `NFPM.decreaseLiquidity({tokenId, liquidity: take, amount0Min: 0, amount1Min: 0, deadline: block.timestamp})` (`REQ-VAULT-149`); there are no per-token minimums, and the floors are LPVaultSwap's oracle-derived per-leg minimums. The deadline is `block.timestamp` because the outer LPVaultSwap call already carries the caller's deadline. (Source: Q-085, Q-131, Q-216)
- `REQ-VAULT-058` — Immediately after the `decreaseLiquidity`, the LPVault MUST call `NFPM.collect({tokenId, recipient, amount0Max: amount0, amount1Max: amount1})` with the amounts `decreaseLiquidity` returned (`SPEC-BACK-008`), so only principal leaves and fees stay owed to the NFT. If both returned amounts are 0 (a take too small to return a raw unit of either token), the `collect` is skipped, because the NFPM rejects a `collect` whose two caps are both zero. (Source: Q-061, Q-217)

### Stray NFTs (rules moved from 2.2)

- `REQ-VAULT-078` — `onERC721Received` MUST revert with `UnsupportedNft` unless `msg.sender == NFPM`; for the canonical NFPM it MUST record nothing, emit `StrayReceived(positionKey, from, operator)` and return the ERC-721 receiver selector. Only a pledge through the Adapter and Collateralization creates custody for a record, so an NFT pushed to the LPVault is never credited. (Source: Q-104, Q-144, Q-224)
- `REQ-VAULT-079` — A stray NFT is a canonical-NFPM token with `NFPM.ownerOf(tokenId) == address(this)` and no custody entry for its `positionKey`. Only stray NFTs can be returned; an NFT in custody for an open record, credited or at 0 credited units, MUST never be moved by the stray path. (Source: Q-104, Q-134)
- `REQ-VAULT-080` — The Uniswap v3 `returnStray(bytes32(tokenId), recipient)` MUST pass the checks of [2.2](02-lp-vault.md) `REQ-VAULT-165`, revert with `NotStray` unless the stray condition of `REQ-VAULT-079` holds at execution, and then call `NFPM.transferFrom(address(this), recipient, tokenId)` and emit `StrayReturned(positionKey, recipient)`. (Source: Q-104, Q-228, Q-296)

## Math

Units: liquidity units (`uint128`); `prices` in USD per whole token, 8 decimals; Q64.96 square-root prices. Rounding uses Uniswap's `FullMath` and OpenZeppelin `Math.mulDiv` (v5.1.0).

- `SPEC-BACK-001` — **Exact range check.** With `s = pool.tickSpacing()`, `MIN_TICK = −887272`, `MAX_TICK = 887272`, and `%` the signed `int24` remainder (Solidity truncates toward zero): at `bindMarket` a range is accepted iff `tickLower % s == 0`, `tickUpper % s == 0`, `⌈MIN_TICK / s⌉ · s ≤ tickLower < tickUpper ≤ ⌊MAX_TICK / s⌋ · s`; at pledge a position is accepted iff `tickLower == market.tickLower` and `tickUpper == market.tickUpper`. The full usable range is the special case `tickLower = −⌊887272 / s⌋ · s`, `tickUpper = ⌊887272 / s⌋ · s`. Why: each market is priced over one range, and a unit of liquidity on a narrower range holds far more value per unit, so only exact equality keeps the credited units worth what the LPOracle says (`AMMN-RT-01`); the alignment test must run on the signed tick, because a test on `uint24(tick) % s` disagrees with alignment for negative ticks. Units: ticks. Rounding: none. Bounds: all values fit `int24`. Example: `s = 60` gives full-range bounds `−887220`, `887220`; `s = 1`, `10`, `200` give `±887272`, `±887270`, `±887200`. A USDC/USDT market at `s = 10` on `[−50, 50]` accepts a position on `[−50, 50]` and refuses one on `[−40, 50]` or `[−60, 50]` with `RangeMismatch`. A listing on `[−516, 500]` at `s = 10` reverts `InvalidShape`, because `−516 % 10 = −6`; the `uint24` cast `16,776,700 % 10 = 0` would have accepted it. Checked by: MATH-AMM-V3-PRICE-05, MATH-UO-04, SYM-24, AMM-A5a, AMM-A5b, AMM-A5c, HYP-AMM-05; a fork test of spacings 1, 10, 60 and 200. (Source: Q-017, Q-119, Q-293)
- `SPEC-BACK-008` — **Principal-capped collect** (executed by `unwind` and `releaseToDepositor`). `(a0, a1) = NFPM.decreaseLiquidity(tokenId, take, min0, min1, block.timestamp)` with `min0 = min1 = 0` for a seizure, reconciliation and deleverage release and the depositor's minimums for a partial removal; `(c0, c1) = NFPM.collect(tokenId, recipient, uint128(a0), uint128(a1))` with `recipient = LP_VAULT_SWAP` for a seizure and a deleverage release, Collateralization for a reconciliation and the depositor of record for a partial removal; then `c0 = a0`, `c1 = a1`, and the depositor's owed amount after the call equals owed before plus fees accrued. The recipient receives `r0 ≤ c0` and `r1 ≤ c1` (less only if the token charges a transfer fee) and every later step uses the received amount measured by balance delta ([2.3](03-collateralization.md) `SPEC-BACK-015`). Why: capping `collect` at the removal amounts keeps every accrued fee with the depositor of record, and measuring receipts keeps settlement working at the reduced amounts if an issuer switches on a transfer fee. Units: raw token units of `token0`, `token1`. Rounding: Uniswap rounds removal amounts down, losing less than 1 raw unit per leg per removal. Bounds: owed plus principal plus fees below `2^128` per NFT. Example: on a full-range USDC/USDT market with USDT depegged to $0.64, the pool price is 1.5625 USDT per USDC (`√P = 1.25`); removing 1,575,000,000 units returns `a0 = 1,259,999,999` (1,259.999999 USDC) and `a1 = 1,968,749,999` (1,968.749999 USDT), worth $2,520, while 12.40 USDC of owed fees stay with the NFT; had USDT a 10 bps transfer fee, a reconciliation would book `r1 = 1,966,781,250` USDT raw units. Checked by: MATH-ST-32, MATH-ST-33, MATH-ST-34, MATH-ST-35, MATH-ST-36, MATH-UO-08, HYP-28, QNT-11, QNT-T17. (Source: Q-061, Q-131, Q-201, Q-254, Q-271)
- `SPEC-AMM-V3-001` — **Composition at the clamped oracle price.** The floored amounts here are exactly those of [2.10](10-lp-oracle.md#concentrated-liquidity-pricing-uniswap-v3-and-aerodrome-slipstream) `SPEC-ORC-006`, computed with the same math, which the LPOracle compiles into its pricing module (`REQ-ORACLE-103`); the LPVault's `composition` view then reports each positive amount reduced by one raw unit, for display. The pricing module's own composition returns the floored amounts before that reduction and `LPPriceMath.lpPrice` takes the one raw unit off each (`SPEC-ORC-008`); the oracle never feeds this view's reduced amounts into `lpPrice`, so the unit is deducted once; at the same units and valuation prices this view's value (`SPEC-AMM-CORE-001`) equals the sum of `SPEC-ORC-008` before its `max(1, ·)`. For a market with ticks `(tL, tU)`, token decimals `(d0, d1)` and prices `(p0, p1)`: `sO = isqrt(mulDiv(p0 · 10^d1, 2^192, p1 · 10^d0))` (the oracle square-root price in Q64.96, floored); `sa = getSqrtRatioAtTick(tL)`, `sb = getSqrtRatioAtTick(tU)`; `sC = min(max(sO, sa), sb)`; `(a0, a1) = LiquidityAmounts.getAmountsForLiquidity(sC, sa, sb, units)` (each floored); then each positive amount is reduced by 1 raw unit. Value per `SPEC-AMM-CORE-001`. Why: the amounts at the oracle ratio are the minimum, over every spot price, of what the units hold when valued at oracle prices, so `slot0` never feeds the quote; clamping to the range makes an out-of-range market all `token0` below and all `token1` above, valued as that token alone; flooring the square root can overstate the amounts by at most `units / (sO · 2^96)` raw `token1`, which the one-unit reduction absorbs for `units ≤ 2^128` and `sO ≥ 2^32`. Units: raw token units. Rounding: down, then −1. Bounds: `mulDiv` handles the 512-bit products; `sO` fits `uint160` within the listing price bounds. Example: full-range USDC/USDT (`s = 60`), `units = 5,000,000,000`, both legs at $1: `(4,999,999,999, 4,999,999,999)` floored, `(4,999,999,998, 4,999,999,998)` after the reduction, worth $9,999.99; with USDT at $0.64 the clamped ratio is 1.5625 and the amounts are `(3,999,999,998, 6,249,999,998)`, worth $7,999.99. On the bounded range `[−50, 50]`, `10^9` units hold `(2,496,751, 2,496,751)` at peg and `(0, 4,999,754)` with USDT at $0.99, because the ratio 1.0101 lies above the range. ## Permissions

As [2.19](19-amm-integration-interface.md) and [2.2](02-lp-vault.md); additionally `onERC721Received` accepts calls only from `NFPM`.

## Dependencies

| Dependency | Type (internal / external) | Calls made | Why |
|---|---|---|---|
| Uniswap v3 NFPM | External | `ownerOf`, `positions`, `transferFrom`, `decreaseLiquidity`, `collect`, `factory` | Custody, live liquidity, removal, fees, deployment check |
| Uniswap v3 factory | External | `getPool` | Pool identity at listing and pledge |
| Uniswap v3 pool | External | `slot0`, `tickSpacing`, `fee`, `token0`, `token1`, `factory`, `observe` | Pool lock, listing checks, time-weighted depth |
| Pool tokens | External | None directly (the NFPM calls the pool, which pays the recipient) | Removal and fee payments |
