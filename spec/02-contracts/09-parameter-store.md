# 2.9 Parameter Store

> **Status:** In review · **Owner:** Avana Labs · **Last reviewed:** 2026-11-11
>
> **Requirement prefixes:** `REQ-PSTORE-NNN`; rules kept from the earlier configuration contract and the RiskModule cap rules keep their `REQ-CONFIG-NNN` and `REQ-RISK-NNN` IDs

## Purpose

The ParameterStore is the upgradeable store of every Avana risk parameter on one chain, with the hard bounds, liquidation-liveness bounds and change direction of each. Each chain (Ethereum, Base) runs one ParameterStore behind its own Timelock. Every value is keyed by the narrowest scope it governs: per chain, per Hub, per market, per token within a Hub, per feed or per debt reserve (`Q-317`). It is responsible for:

- per-chain parameters: the chain's block time `CHAIN_BLOCK_TIME` (immutable), its L2 sequencer-uptime check (`sequencer`: feed and grace period), the flash-fee ceiling `maxFlashFeeBps` (applied to `deleverage` and the flash liquidation helper; `liquidate` takes no flash loan), and the chain-level global values (oracle windows, USD band, grace, Avana's surplus share and its recipient, the breaker recovery window `gateRecoverySeconds`, the first-loss coverage ratio `coverageRatioBps`, `maxShortfallBps`, and `poolShareMaxBps`, the chain default of the pool-share cap and concentration gate of `Q-399` (10,000 bps, off, unless a pool's listing sets a cap, `Q-403`), which a pool's override `poolShareMaxBpsOf(poolKey)` may lower for that pool, `Q-383`); there is no opening health factor, in-kind or idle parameter (`Q-396`, `Q-398`, `Q-401`);
- per-Hub parameters: the token exposure cap `tokenUsdCap(hub, token)` and the per-depositor cap `depositorUsdCap(hub)`, so adding a CDP Spoke or a market under a Hub never adds cap room;
- per-market parameters: consistency-check window and tolerance (with the observation count the chain's block time requires), slippage allowance and its liveness floor, pool risk factor, `minPledgeUsd`, exposure caps (`marketUsdCap`, `topUpSliceUsd`), the optional hard health-factor floor `hardHealthFloor` (off by default, `Q-398`), the stress floor `stressFloorUsd`, and the depth threshold of each swap-route slot;
- per-token parameters: the collateral-factor input `tokenCollateralFactorBps`, the feed-agreement tolerance and the independent second price source `secondSource`;
- per-feed definitions: pinned decimals and bounds, the feed's own published heartbeat and its freshness margin `heartbeatMargin`, deviation threshold, heartbeat drift and the borrow and liquidation age limits, for every LPOracle leg and every DebtOracle leg;
- per-debt-asset parameters: the stress rise `debtStressRiseBps`, the recovery-floor rounding allowance `floorRoundingAllowance(asset)` and the deficit threshold `breakerDeficitMax(hub, asset)` of the deficit freeze;
- per-Spoke parameters: the Aave liquidation configuration Avana's sizing assumes (`aaveTargetHealthFactor`, `minLiquidationBonus`), which the drift check compares with the live one;
- the liquidation-liveness check of every (market, debt reserve) pair (`liquidationLivenessHolds`) and the loosening step limits;
- the oracle configuration each LPOracle reads on every evaluation (`getOracleInputs`) and checks at listing (`getOracleConfig`).

It is **not** responsible for: Hub, CDP Spoke, market, token, debt-reserve and swap-route records, breaker latches or the pause state of each Hub (MarketRegistry, [2.8](08-market-registry.md)); enforcing any value (RiskModule, [2.7](07-risk-module.md); LPOracle, [2.10](10-lp-oracle.md); LPVaultSwap, [2.11](11-lpvaultswap.md); the IFlashSource implementation; the flash liquidation helper); delays and the timelock ([2.15](15-governance-and-timelock.md)); any Aave-side value (collateral factors, Hub caps and Spoke settings belong to the Aave DAO).

Global invariants are defined in [4.1 Global Invariants](../04-security/01-global-invariants.md); in words, no allowed parameter value can stop liquidations from running, every value stays inside the hard bounds of the deployed implementation, no value changes except through a timelock operation or, for a tightening and for Avana's fee share within its bound, a call of the Joint Configuration Safe (`APPLICATION_RISK_STEWARD`), and no value is read by repay, debt-free withdrawal, fee collection or pending settlement. Every setter below preserves these: tightenings only make new activity stricter, every loosening is bounded in size and spaced one normal delay apart, and each setter that can affect liquidation re-checks the liveness bounds at execution.

## Outputs

- View functions returning every parameter to the RiskModule, MarketRegistry, LPOracle, DebtOracle, LPVaultSwap, the IFlashSource implementation, the flash liquidation helper, Lens, app and monitoring.
- One event per change, naming the parameter, its scope, the old and new value and, where the event has a `caller` field, `msg.sender`: the timelock, the Joint Configuration Safe for a tightening or a fee-share change, or a guardian for a standby second-source switch.
- No token or position movement ever originates in the ParameterStore.

## Storage

All mutable storage sits in one ERC-7201 namespace (`avana.storage.ParameterStore`). Implementation immutables and constants (changed only by an upgrade at the normal delay): `TIMELOCK`, `MARKET_REGISTRY`, `CHAIN_BLOCK_TIME` (12 s on Ethereum, 2 s on Base), `HAS_SEQUENCER` (false on Ethereum, true on Base), the five logic contracts (below), `MAX_QUOTE_CHANGE_BPS` (100, the `maxQuoteChangeBps` every `OracleConfig` carries), the USD-cap ceiling `2¹²⁸ − 1`, the hard bounds of every parameter (the Bounds column of [1.5](../01-architecture/05-parameters.md)), the liveness bounds `graceHealthFactorMin` (0.90), `graceDurationMax` (7,200 s) and `consistencyToleranceMinBps` (10), the freshness-margin bound `MAX_HEARTBEAT_MARGIN` (3,600 s), and the loosening steps `LOOSEN_HEALTH_FACTOR_STEP` (0.03e18), `LOOSEN_CAP_STEP_BPS` (15,000, that is 1.5 times) and `LOOSEN_SLIPPAGE_STEP_BPS` (25). The store holds no Hub immutable: every Hub-scoped value is keyed by the Hub address the MarketRegistry records for the market, Spoke or debt reserve (`Q-317`).

Code layout. The whole surface does not fit the 24,576-byte code limit in one contract, so the implementation behind the proxy serves every view but two and checks every setter's role itself, then delegatecalls one of five immutable logic contracts with the unchanged calldata: tighten setters, loosen setters, listing setters (with `setLiquidationExpectations`, `setSequencer` and `setCoverageRatioBps`), oracle structural setters (with the two setters checked against liquidation liveness, `setSlippageAllowanceMinBps` and `setMaxFlashFeeBps`) and risk structural setters (with the second sources and the parameter checks of `initialize`). Each logic contract shares the ERC-7201 layout, holds no state any contract reads, starts every setter body and view body with a delegated-only check (`address(this)` must not be its own address, else `NotDelegated`), so it cannot be called directly, and reports its kind and the four immutables through `logicConfig()`; the implementation constructor reverts `OutOfBounds` unless all five match its own. A setter's state, events and `msg.sender` are therefore the proxy's, and a new logic contract is part of a new implementation that waits the normal delay of `upgradeToAndCall`. The two views built in a logic contract are `getOracleConfig`, read at listing and by the setters' `checkConfig` re-runs, and `liquidationLivenessHolds`, read by the MarketRegistry's `activateMarket` and `enableDebtReserve`: the implementation runs the view's calldata in the oracle structural logic by delegatecall and ends the call with that logic's return data, so the implementation keeps room for `getOracleInputs`, which every LPOracle evaluation reads. Each logic view body writes nothing and makes only static calls, so the view stays read-only; the delegatecall adds about 3,000 gas to a liveness read, which only governance operations make.

## Functions

Every setter requires `APPLICATION_ADMIN`; "short" is the 12-hour delay and "normal" the timelock's `normalDelay()` (5 days at launch, never below the 4-day `MIN_NORMAL_DELAY`) ([2.15](15-governance-and-timelock.md)). Every setter marked "Short" and `setAvanaFeeShareBps` also accept `APPLICATION_RISK_STEWARD`, held by the Joint Configuration Safe, which calls them at once with the same checks (`REQ-PSTORE-002`); `useStandbySecondSource` takes `APPLICATION_PAUSE_GUARDIAN` instead. Each setter emits its event with `caller = msg.sender`.

## Permissions

Role identifiers, holders and the short-delay list are defined in [2.15](15-governance-and-timelock.md). Each chain's ParameterStore answers only to that chain's timelock.

| Class | Delay | Setters | Cancel |
|---|---|---|---|
| Tighten | Short delay (12 hours) | Every `tighten…` setter, the ParameterStore entries of the timelock's immutable `SHORT_ELIGIBLE`; each accepts only a strictly safer value within the hard and liveness bounds | Any `CANCELLER_ROLE` holder |
| Risk steward | Immediate | The same 20 `tighten…` setters and `setAvanaFeeShareBps` within `[0, 5,000]`, called by `APPLICATION_RISK_STEWARD` (the Joint Configuration Safe) with every check of the timelock path | Not applicable (nothing is queued) |
| Guardian | Immediate | `useStandbySecondSource`, called by `APPLICATION_PAUSE_GUARDIAN` (the Emergency Guardian or the Aave Protocol Guardian) | Not applicable |

Outside the timelock, two holders act on the ParameterStore. The Emergency Guardian and the Aave Protocol Guardian hold `APPLICATION_PAUSE_GUARDIAN` here for `useStandbySecondSource` only: it puts a second source reviewed at the normal delay in force and changes no parameter value; they otherwise contain an incident with the per-Hub pause state, manual breaker trips, address freezes and standby route switches ([2.8](08-market-registry.md)). The Joint Configuration Safe holds `APPLICATION_RISK_STEWARD` for the tighten setters and `setAvanaFeeShareBps`: a tightening only makes new activity stricter (`REQ-PSTORE-002`), and the fee share moves only within its hard bound. No keeper or other account holds a ParameterStore function, and every loosening, structural change, listing write, second-source record, upgrade and role change stays on the timelock.

## Restrictions

### Form

- `REQ-PSTORE-001` — The ParameterStore of each chain MUST sit behind one fixed ERC-1967 proxy address using the UUPS pattern, whose `_authorizeUpgrade` requires `APPLICATION_ADMIN`; `initialize(timelock, params, initialDepositorUsdCap, initialPoolShareMaxBps)` runs once, atomically with the proxy deployment, grants `DEFAULT_ADMIN_ROLE` and `APPLICATION_ADMIN` to that chain's timelock only, makes `APPLICATION_ADMIN` the admin of `APPLICATION_PAUSE_GUARDIAN` and `APPLICATION_RISK_STEWARD`, and writes every global value within its hard bounds. The implementation MUST use ERC-7201 storage diffed in CI, call `_disableInitializers()` in its constructor, run any `reinitializer(n)` atomically in the same `upgradeToAndCall`, and link no external libraries. It MUST NOT hold or approve any token or position and MUST make no state-changing external call; it calls only the views in [Dependencies](#dependencies) and, for setter bodies and the views `getOracleConfig` and `liquidationLivenessHolds`, delegatecalls its five logic contracts ([Storage](#storage)), each of which reverts `NotDelegated` for any setter body or view called directly rather than by that delegatecall. It MUST hold no Hub immutable: every Hub-scoped value is keyed by the Hub address the MarketRegistry records, so a Hub added on the chain (Stable LP, Correlated LP or Volatile LP tier) needs no ParameterStore upgrade. `_grantRole` MUST revert `AdminRoleOnlyTimelock(role, account)` when `role` is `DEFAULT_ADMIN_ROLE` or `APPLICATION_ADMIN` and `account != TIMELOCK`, an implementation immutable, and `initialize` reverts the same way unless its `timelock` argument is `TIMELOCK`. A role grant is an operation only the Aave DAO can cancel; if it could name another account, that account could upgrade the store at once with no delay, so admin power is fixed to the timelock in code and a move to a new timelock is an upgrade at the normal delay that every canceller can cancel. Example: an executed `grantRole(APPLICATION_ADMIN, governanceSafe)` reverts `AdminRoleOnlyTimelock(APPLICATION_ADMIN, governanceSafe)`; `ParameterStoreTightenLogic.tightenMarketUsdCap(1, 1)` sent to the logic contract's own address reverts `NotDelegated`. Checked by: TEST-242, TEST-062, PROP-070. (Source: Q-226, Q-228, Q-240, Q-259, Q-317)
- `REQ-PSTORE-002` — Every setter MUST require `APPLICATION_ADMIN`, so every value is the value an executed timelock operation set, with two exceptions: `useStandbySecondSource` requires `APPLICATION_PAUSE_GUARDIAN` (`REQ-PSTORE-029`), and the 20 `tighten…` setters and `setAvanaFeeShareBps` also accept `APPLICATION_RISK_STEWARD`, held by the chain's Joint Configuration Safe (2-of-3: one Avana Labs, one Aave Labs and one LlamaRisk signer), which calls them at once with every check of the timelock path; a caller with neither role reverts `AccessControlUnauthorizedAccount(caller, APPLICATION_ADMIN)`. The steward can therefore only make a parameter stricter, or move Avana's fee share within `[0, 5,000]`; every loosening, structural change, listing write, second-source record, upgrade and role change stays on the timelock, and the timelock grants and revokes the steward role with a role-change operation. The ParameterStore entries of the timelock's immutable `SHORT_ELIGIBLE` set ([2.15](15-governance-and-timelock.md) `REQ-ACCESS-155`) MUST be exactly its `tighten…` selectors: those of the market, Hub, cap, feed, tolerance and route parameters, `tightenMaxFlashFeeBps`, `tightenFloorRoundingAllowance`, `tightenHardHealthFloor`, `tightenBreakerDeficitMax`, `tightenGateRecoverySeconds`, `tightenMaxShortfallBps` and `tightenDebtStressRiseBps`. Only those can ever be put on the short-delay list; every other ParameterStore selector, including every `set…`, `setInitial…` and `loosen…` setter and `upgradeToAndCall`, needs the normal delay. A tighten setter can only make its parameter stricter (`REQ-CONFIG-051`), which is why 12 hours is enough for it: the worst a tightening does is stop new pledges or borrows sooner, trip a breaker on new activity sooner, narrow the slippage a shortfall top-up can buy, refuse a `deleverage` or flash liquidation helper loan whose premium rose (a caller funding the debt from its own balance is unaffected, and `liquidate` takes no flash loan), or count Expired debt at a higher stress price, which can only bring liquidation of fresh reserves forward; none loosens a risk limit or blocks an exit. The same reasoning lets the Joint Configuration Safe call them at once: two of three independent organisations must sign, and the worst a compromised quorum can do through them is stop new activity sooner, which the timelock's loosen setters reverse at the normal delay. Checked by: TEST-062, TEST-063, PROP-034. (Source: Q-228, Q-241, Q-251, Q-261, Q-262, Q-317, Q-404)
- `REQ-PSTORE-003` — The blast radius of a faulty or hostile ParameterStore implementation is: it can return any value its code chooses and so misprice gates, block pledges and borrowing, or stop liquidation (a reverting `getOracleConfig` makes every LPOracle failed); it cannot move tokens, NFTs or debt, because it holds none and calls no state-changing function. Its upgrades wait the normal delay with independent cancellers, and repay, fee collection and debt-free withdrawal never read it, so borrowers can leave inside the delay. (Source: Q-223, Q-226, Q-228)

### Change classes and bounds

- `REQ-CONFIG-049` — Each parameter's change class MUST match [1.5](../01-architecture/05-parameters.md), with these directions: `hardHealthFloor` tighten = raise or enable (short), loosen = lower or disable (normal); `gateRecoverySeconds` tighten = raise (short), loosen = lower (normal); `coverageRatioBps` any change at the normal delay; `slippageAllowanceBps` and `floorRoundingAllowance(asset)` tighten = lower (short), raise is normal; `marketUsdCap`, `topUpSliceUsd`, `poolShareMaxBps` (the chain default and each pool's `poolShareMaxBpsOf(poolKey)`), `tokenUsdCap(hub, token)` and `depositorUsdCap(hub)` tighten = lower (short), loosen = raise (normal); `minPledgeUsd` tighten = raise (short), loosen = lower (normal); `maxFlashFeeBps` tighten = lower (short), raise is normal; a swap route's depth threshold tighten = raise (short), loosen = lower (normal); `consistencyToleranceBps`, `feedAgreementToleranceBps`, `borrowPriceMaxAge` and `poolRiskFactor` tighten = lower (short, within the liveness bounds), any other change is structural (normal); `avanaFeeShareBps` and `feeRecipient` any change at the normal delay; `cachedWindow`, `disagreementPauseMax`, `twapWindow`, `usdBandLow`, `usdBandHigh`, `liquidationPriceMaxAge`, `feedMaxAge`, `graceDuration`, `graceHealthFactor`, `feedAgreementMarginBps`, `slippageAllowanceMinBps`, `heartbeat`, `heartbeatMargin`, `feedDeviationThresholdBps`, `heartbeatDriftBps`, `secondSource`, the sequencer configuration, token collateral factors, and `stressFloorUsd` are structural (normal); `graceHealthFactorMin`, `graceDurationMax`, `consistencyToleranceMinBps` and `CHAIN_BLOCK_TIME` change only by an implementation upgrade (normal); the Spoke liquidation expectations are structural (normal); `breakerDeficitMax`, `maxShortfallBps` and `debtStressRiseBps` follow `REQ-PSTORE-016`, `REQ-PSTORE-018` and `REQ-PSTORE-020`. `usdBandLow`, `usdBandHigh`, `graceDuration`, `graceHealthFactor` and the sequencer grace period change only at the normal delay in both directions and have no tighten setter: a narrower band can hold markets Drifting, and a longer grace or lower grace health factor delays liquidation after an outage while a shorter grace or higher grace health factor exposes borrowers to liquidation on the first fresh price, so neither direction is uniformly safer. (Source: Q-048, Q-091, Q-139, Q-228, Q-230, Q-235, Q-241, Q-246, Q-248, Q-251, Q-261, Q-317, Q-398, Q-399, Q-401)
- `REQ-CONFIG-050` — Every setter MUST enforce the hard-coded minimum and maximum of the ParameterStore implementation, which equal the Bounds column of [1.5](../01-architecture/05-parameters.md), and the liveness bounds below (error `OutOfBounds` or `LivenessBound`); the risk service providers propose values within them. `hardHealthFloor` MUST be 0 (off) or within `[1e18, 1.25e18]` in WAD. `floorRoundingAllowance(asset)` MUST stay at most a value worth $1 at the asset's price when set, in asset base units (exact integer comparison `v × price8 ≤ 10⁸ × 10^decimals`, evaluated as `v ≤ ⌊10⁸ × 10^decimals / price8⌋`); there is no SettlementBudget cap to bound it (`Q-397`). The price is the largest `latestAnswer()` of the price sources of the asset's approved debt reserves on every CDP Spoke (a reverting or non-positive answer counts as unbounded, so the setter fails closed); `setDebtAssetParams` and `loosenFloorRoundingAllowance` revert `TokenNotListed(asset)` while no approved debt reserve uses the asset, so the listing batch enables the reserve first, and `OutOfBounds` for 0. Aave V4's dust rule can raise the repayment needed to finish a liquidation by up to two debt-asset units beyond the debt it priced the seizure from; the caller sizes `debtToCover` for that amount up front and funds it in the debt asset (LPVaultSwap takes no flash loan, `Q-404`), and any rounding gap at final settlement comes out of the caller's payout or its shortfall top-up, so the allowance only keeps the recovery-floor test from refusing a dust liquidation over rounding. The allowance is per debt asset because each asset has its own decimals. Example: `loosenFloorRoundingAllowance(GHO, 1e18)` passes and `1e18 + 1` reverts `OutOfBounds`; the USDC allowance may reach `1e6` base units. Where 1.5 bounds a value on one side only, the implementation closes the other: `cachedWindow > 0`; `consistencyToleranceBps`, `feedAgreementToleranceBps` and `feedAgreementMarginBps` at most 10,000; `slippageAllowanceBps < 10,000`; a route depth threshold above 0 and `kind ≤ 1`; `tokenCollateralFactorBps` within `[1, 9,999]` for a listed token. Checked by: TEST-246. (Source: Q-018, Q-072, Q-119, Q-198, Q-236, Q-267, Q-317, Q-397, Q-398, Q-404)
- `REQ-CONFIG-051` — A two-direction parameter MUST have separate tighten and loosen (or structural) setters; the tighten setter MUST revert with `NotStricter` unless the new value is strictly safer than the current value and within bounds, and only tighten setters are on the short-delay list. (Source: Q-114, Q-119, Q-228)
- `REQ-CONFIG-052` — Liquidation-liveness bounds: no setter MAY take `slippageAllowanceBps` below `slippageAllowanceMinBps` (per market), `graceHealthFactor` below `graceHealthFactorMin` (and it stays below 1e18), `graceDuration` above `graceDurationMax`, `consistencyToleranceBps` below `consistencyToleranceMinBps`, `feedAgreementToleranceBps` below its `REQ-CONFIG-024` lower bound, `liquidationPriceMaxAge` below `heartbeat + heartbeatMargin`, `disagreementPauseMax` above its registry bound, or any (Active or Offboarding market, enabled debt reserve) pair outside the liquidation inequality of `REQ-PSTORE-021`, which a raise of `setSlippageAllowanceMinBps` and a raise of `setMaxFlashFeeBps` re-check on-chain. Every allowed value therefore still lets liquidations run. The keeper floor lives in LPVaultSwap. Examples with the registry values (`consistencyToleranceMinBps = 10`, `graceHealthFactorMin = 0.90`, `graceDurationMax = 7,200` s): from the launch tolerance of 50 bps, `tightenConsistencyToleranceBps(m, 10)` succeeds and `tightenConsistencyToleranceBps(m, 9)` reverts `LivenessBound`, because a consistency band narrower than normal pool noise would keep the market Drifting; `setGraceHealthFactor(0.90e18)` from the launch 0.95 is accepted and `setGraceHealthFactor(0.89e18)` reverts `LivenessBound`, because during grace an account is liquidatable only below `graceHealthFactor`, and the floor keeps an account that Aave already counts as liquidatable from sitting more than 10% below health factor 1 unliquidated; `setGraceDuration(7,200)` from the launch 1,800 is accepted and `setGraceDuration(7,201)` reverts `LivenessBound`, so after an outage no account waits more than two hours for liquidation; with `slippageAllowanceMinBps = 30` a tightening of `slippageAllowanceBps` to 30 succeeds and to 29 reverts. Checked by: MATH-ST-13, HYP-36, QNT-36, TEST-245. (Source: Q-139, Q-159, Q-162, Q-184, Q-209, Q-210, Q-261)
- `REQ-CONFIG-053` — Loosen setters MUST run only through the timelock at the normal delay, cancellable by any `CANCELLER_ROLE` holder while queued. Their selectors are outside the timelock's immutable `SHORT_ELIGIBLE`, so no operation can ever move them to the short delay, and each step-limited loosening also obeys the step and spacing of `REQ-PSTORE-017`. (Source: Q-228, Q-246, Q-262)
- `REQ-CONFIG-054` — Structural setters MUST run only through the timelock at the normal delay; new price sources and any change to how a price is computed (feed definitions, `usdBandLow`/`usdBandHigh`, `twapWindow`) are structural, and so is raising a tolerance. (Source: Q-091, Q-228)
- `REQ-CONFIG-055` — Setting `usdBandLow`/`usdBandHigh` MUST require `usdBandLow < 10^8 < usdBandHigh` (8-decimal USD levels per 1 USD of value at peg; launch values 0.90 = 90,000,000 and 1.02 = 102,000,000); a breach makes the market Drifting with reason `USD_BAND`, which blocks borrowing and withdraw-with-debt; pledges stay open, and liquidation continues when both Chainlink routes are fresh and agree. (Source: Q-176, Q-195, Q-206)
- `REQ-CONFIG-057` — No temporary override of any parameter exists: the LPOracle applies the stored `feedAgreementToleranceBps` and `consistencyToleranceBps` exactly, and a stricter tolerance during an incident is a short-delay tighten operation or an immediate tightening by the Joint Configuration Safe (`REQ-PSTORE-002`). When faster containment is needed the guardians use the Hub's `freeze` or `pause` ([2.8](08-market-registry.md)), which change no parameter. (Source: Q-227, Q-228)
- `REQ-CONFIG-058` — No account MAY set, restore or override a parameter outside a timelock operation, except the Joint Configuration Safe's immediate tightenings and fee-share changes (`REQ-PSTORE-002`): there is no recovery role, no zero-delay loosening, structural or listing setter and no restore function for a parameter value, and the guardians hold one ParameterStore selector, `useStandbySecondSource`, which puts a second source recorded at the normal delay in force and changes no parameter value. (Source: Q-227, Q-228)
- `REQ-CONFIG-071` — Each parameter MUST have one stored value, the value the last executed timelock operation or risk-steward call (`REQ-PSTORE-002`) set; there is no approved and live pair and no restore. A value tightened during an incident returns through loosen or structural operations at the normal delay, one step per `normalDelay` for a step-limited parameter (`REQ-PSTORE-017`). Example: `slippageAllowanceBps` of market 4 is tightened from 100 to 40 bps by an operation that executes 12 hours after scheduling; raising it back to 100 bps takes `loosenSlippageAllowanceBps(4, 65)`, then `(4, 90)` and `(4, 100)`, each executing at least one normal delay after the previous one, so the full return takes at least 15 days at the launch delay. (Source: Q-228, Q-246)

### Market parameters

- `REQ-PSTORE-004` — `setInitialMarketParams(marketId, params)` MUST revert with `NotInListing` unless the MarketRegistry has the market `Registered`, and MUST check every field before writing: when the market's AMM protocol offers a time-weighted price, `twapWindow > 0`, the pool holds at least `twapMinObservations(marketId)` observations (`REQ-PSTORE-027`) and the integration's time-weighted read over `[twapWindow, 0]` succeeds; when it offers none (Curve StableSwap-NG, Balancer), `twapWindow == 0` and the consistency check uses the token's second source; `consistencyToleranceMinBps ≤ consistencyToleranceBps` within its hard bound; `slippageAllowanceMinBps ≤ slippageAllowanceBps` within bounds; `0 < poolRiskFactor ≤ 4,000`; `minPledgeUsd ≤ 100_000e8`; `hardHealthFloor == 0` or within its bounds; the listing margin [SPEC-CF-004](07-risk-module.md#collateral-factor-math) with these values; and `LPOracle.checkConfig(getOracleConfig(lpOracle)) == 0` for the market's LPOracle (`OracleConfigRejected`). The time-weighted checks read the integration: `capabilities().hasTwap` decides whether a window is required; for a `TickRange` market with a pool address the pool's `slot0()` observation cardinality must reach `twapMinObservations`; and `riskStatus(marketId, twapWindow).depthAvailable` must be true; any failure reverts `OutOfBounds`. The listing margin covers every recorded route of every pool token, the standby included, since a guardian can put it in either slot at once; it uses every pool token's `tokenCollateralFactorBps`, which must already be set (`> 0`, so the listing batch writes `setTokenCollateralFactorBps` first), and reverts `OutOfBounds`. Once a market's parameters are written (`poolRiskFactor > 0`) and while it is Registered, Active or Offboarding, every change that thins its margin re-checks it: a raise by `setPoolRiskFactor`, a raise of a pool token's factor by `setTokenCollateralFactorBps`, and a `setFeed` that raises `feedDeviationThresholdBps + heartbeatDriftBps` of a feed in any recorded route of one of its tokens. Batch order: a listing or change batch writes `setFeedAgreementToleranceBps` before a `setFeed` that raises a deviation threshold the tolerance must cover, `setTokenCollateralFactorBps` before `setInitialMarketParams`, `setSecondSource` with an oracle-network source before the first `tightenDebtStressRiseBps` of a DebtOracle asset, which comes before `enableDebtReserve`, `enableDebtReserve` before `setDebtAssetParams`, and `tightenTopUpSliceUsd` before a `tightenMarketUsdCap` below the slice; each setter checks the state the earlier calls of the same batch wrote. Range failures revert `OutOfBounds` (`consistencyToleranceBps ≤ 10,000`, `slippageAllowanceBps < 10,000`) and the liveness floors `LivenessBound`. It can run again while the market is `Registered`, and `activateMarket` requires it to have run. (Source: Q-113, Q-139, Q-230, Q-240, Q-317, Q-399)
- `REQ-CONFIG-015` — `poolRiskFactor` per market MUST be stored in bps, > 0 and ≤ the launch ceiling bound in [1.5](../01-architecture/05-parameters.md); its initial value comes from the Aave V4 risk service providers in the listing operation and is used only for `SPEC-CF-001` checks; the Spoke collateral factor itself is set by the Aave DAO by AIP. (Source: Q-020, Q-110, Q-143, Q-186, Q-197)
- `REQ-CONFIG-041` — `slippageAllowanceMinBps` for the market MUST be set at listing (`setInitialMarketParams`) to at least the largest, over the market's pool tokens and the debt assets enabled against it, of the swap route's fee plus expected price impact at the route's depth threshold, with the threshold sized to the full position value of a one-sided unwind at either range edge (`REQ-CONFIG-070`); it is changed only by `setSlippageAllowanceMinBps` at the normal delay, and `slippageAllowanceBps` MUST stay ≥ it. Example: on a USDC/USDT Uniswap v3 market with GHO debt, the USDT→GHO route costs 5 bps of fee plus 25 bps of impact at its threshold and the USDC→GHO route 5 + 20 bps, giving a minimum of 30 bps; a launch allowance of 100 bps may be tightened to 30 bps but not to 29. Checked by: MATH-ST-13. (Source: Q-139, Q-159, Q-209)
- `REQ-PSTORE-005` — `minPledgeUsd` MUST be stored per market in 8-decimal USD within `[0, 100_000e8]` and launch at $10 (`10e8`) for every market; `tightenMinPledgeUsd` (short delay) MUST revert `NotStricter` unless the value is strictly higher, and `loosenMinPledgeUsd` (normal delay) `NotLooser` unless strictly lower; each emits `MinPledgeUsdSet`. The RiskModule compares it with the pledge value `pledgeUsd = mulDiv(L, price8, 10^d, Floor)` (credited liquidity `L`, the served LPOracle price `price8` per whole vault token, vault-token decimals `d`) on every pledge and top-up and reverts `BelowMinPledge(pledgeUsd, minPledgeUsd)` below it; rounding down means a pledge just under the floor never passes. Exits never read it. Example: on USDC/USDT (`d = 6`) at `price8 = 199,986,998`, a pledge of `L = 5,000,000` units is worth `⌊5×10^6 × 199,986,998 / 10^6⌋ = 999,934,990` ($9.9993) and reverts against `minPledgeUsd = 1,000,000,000`, while `L = 5,001,000` is worth 1,000,134,976 and passes. (Source: Q-169, Q-194, Q-230)

### Caps

- `REQ-RISK-041` — Initial `marketUsdCap`, `topUpSliceUsd`, `stressFloorUsd` (per market) and `tokenUsdCap(hub, token)` (per pool token newly exposed under the market's Hub) MUST be written only for a market the MarketRegistry has `Registered` (or a Hub-token pair with no cap yet), in the market's `listCollateralMarket` batch at the normal delay, with cap values and `poolRiskFactor` supplied by the Aave V4 risk service providers; otherwise the setter reverts `NotInListing`. A repeated `setInitialMarketCaps` while the market is `Registered` emits `CapLoosened` for a cap it raises, `CapTightened` for one it lowers and nothing for one it leaves unchanged. The Hub is the one the MarketRegistry records for the market's CDP Spoke. A second market of the same token under the same Hub shares the existing `tokenUsdCap(hub, token)`, so listing more markets or more CDP Spokes never adds token room; the same token under another Hub has its own cap, because each Hub carries its own suppliers' risk. (Source: Q-114, Q-197, Q-240, Q-310, Q-317)
- `REQ-RISK-042` — Each cap MUST have a tighten setter that reverts with `NotStricter` unless the new value is strictly lower than the current value and that runs at the short delay; caps are 8-decimal USD (`poolShareMaxBps` in bps). `poolShareMaxBps` is a chain default with a per-pool override (`Q-383`, `Q-399`): `poolShareMaxBps()` returns the default, `initialize` writes it (launch 10,000 bps, no limit, `Q-403`; `0 < poolShareMaxBps ≤ 10,000`), and `tightenPoolShareMaxBps(v)` / `loosenPoolShareMaxBps(v)` change it. `tightenPoolShareMaxBpsOf(marketId, v)` writes the override of the market's pool, `poolKey = keccak256(abi.encode(integrationId, pool, poolId))` from the market's MarketRegistry definition, which every market (range) of that pool shares; it requires `0 < v < poolShareMaxBpsOf(poolKey)` (`NotStricter`, `OutOfBounds`) and runs at the short delay, so a risk provider can set a per-pool cap at listing or later. `loosenPoolShareMaxBpsOf(marketId, v)` raises the override, requires `poolShareMaxBpsOf(poolKey) < v ≤ poolShareMaxBps()` (`NotLooser`, `OutOfBounds`) and runs at the normal delay. `poolShareMaxBpsOf(poolKey)` returns `min(override, poolShareMaxBps())` when an override is set and `poolShareMaxBps()` otherwise, so lowering the default lowers every pool and no pool's value ever exceeds the default. Example: default 10,000, override 1,000 → 1,000; default lowered to 500 → 500; no override → the default (10,000, no limit). The RiskModule compares each pool's combined Avana share with `poolShareMaxBpsOf(poolKey)` ([2.7](07-risk-module.md) `SPEC-CAP-005`). No per-market value exists: every range of one pool shares the pool's value. Lowering a cap leaves existing records untouched and only stops new pledges and first borrows sooner. (Source: Q-048, Q-119, Q-228, Q-240, Q-310, Q-383, Q-399, Q-403)
- `REQ-RISK-043` — Each cap MUST have a loosen setter that reverts with `NotLooser` unless the new value is strictly higher, executed only through the timelock at the normal delay. (Source: Q-119, Q-228, Q-240)
- `REQ-RISK-044` — Every cap setter MUST enforce the hard-coded minimum and maximum of [1.5](../01-architecture/05-parameters.md) (error `OutOfBounds`); the Aave V4 risk service providers propose values within them. `loosenMarketUsdCap` and `loosenTopUpSliceUsd` MUST revert with `AddCapTooSmall` unless the `addCap` of the market's Hub still satisfies [SPEC-CAP-006](07-risk-module.md#cap-math) with the new value. A Hub-scoped setter MUST revert `UnknownHub(hub)` unless `hub` is non-zero and the MarketRegistry records it (`isRecordedHub`). Every USD cap and the stress floor are within `(0, 2¹²⁸ − 1]`, `topUpSliceUsd ≤ marketUsdCap` (so `tightenMarketUsdCap` below the market's slice reverts `OutOfBounds`, and a batch lowers the slice first), and `poolShareMaxBps` within `(0, 10,000]`. `SPEC-CAP-006` is checked for an Active or Offboarding market (a zero stress floor, which no setter writes, reverts `AddCapTooSmall` before the division) with `addCap = getSpokeConfig(hubAssetId, spoke).addCap` of its Hub and `R`, `S` from Collateralization's `getCounters(vaultToken, address(0))`; a Registered market has no Hub asset yet and `activateMarket` checks it. (Source: Q-072, Q-119, Q-175, Q-197, Q-240, Q-317)
- `REQ-RISK-045` — `setStressFloorUsd` MUST run at the normal delay; it MAY lower the floor only if [SPEC-CAP-006](07-risk-module.md#cap-math) holds with the new floor (`AddCapTooSmall`), and MAY raise it only while the market's vault-token supply is 0 (`SupplyNotZero`), so every live record was booked at a price at least the current floor. (Source: Q-175, Q-240)

### Tokens and feeds

- `REQ-CONFIG-019` — Each pool token MUST carry `tokenCollateralFactorBps`, recorded with its source and written with `setTokenCollateralFactorBps` in the listing batch: the token's Aave V4 Core Hub collateral factor at listing when the Core Hub lists it as collateral, otherwise an explicit value > 0 chosen by the Aave V4 risk service providers with the methodology recorded in the listing (`REQ-CONFIG-020`). Recalibration is manual, with no automatic link. (Source: Q-020, Q-119)
- `REQ-CONFIG-020` — A token with no Core Hub collateral factor, or one Avana must not inherit, MUST carry an explicit `tokenCollateralFactorBps` > 0 chosen at listing by the Aave V4 risk service providers: a debt asset that is also a pool token (GHO in a GHO/USDC pool, where GHO's Core Hub collateral factor reflects a different use), a tokenized stock, and a governance token the Core Hub does not list as collateral. It is stored in the same `tokenCollateralFactorBps` slot and is never 0, so every listed pool token has a defined collateral-factor input and no AMM protocol or token class is excluded by the absence of a Core Hub value. (Source: Q-188, Q-317)
- `REQ-CONFIG-022` — For every feed, `setFeed` MUST read `decimals` on-chain and pin it, and read `minAnswer` and `maxAnswer` on-chain from the feed's aggregator, each as one raw 32-byte word bounded by `type(int192).max = 2¹⁹¹ − 1`, the type of the aggregator's own bounds: a failed or short read of `minAnswer`, or a word outside `[1, 2¹⁹¹ − 1]`, reverts `InvalidFeed(feed, "minAnswer")`, and a failed or short read of `maxAnswer`, or a word above `2¹⁹¹ − 1` (a negative `int192` included), reverts `InvalidFeed(feed, "maxAnswer")`, so a malformed aggregator answer is refused by name and never by an ABI decoding error or an overflow (`minAnswer × 10^(8 − decimals) < 2¹⁹¹ × 10⁷ < 2²⁵⁶`); the normalised minimum `minAnswer × 10^8 / 10^decimals` (floor, or `minAnswer × 10^(8 − decimals)` when `decimals < 8`) MUST be ≥ 1, so a valid answer never normalises to 0 (`InvalidFeed(feed, "minAnswer")`). A feed whose decimals no longer match the pinned value is invalid on every read. `setFeed` also reverts `InvalidFeed(feed, "decimals")` unless `1 ≤ decimals ≤ 18`, `InvalidFeed(feed, "maxAnswer")` unless `maxAnswer > minAnswer`, and `OutOfBounds` unless `feedDeviationThresholdBps > 0`. Example: an 18-decimal feed with `minAnswer = 10^9` normalises to `⌊10^9 × 10^8 / 10^18⌋ = 0` and is rejected; with `minAnswer = 10^10` it normalises to 1 and passes. The pinned `maxAnswer` is `min(aggregator().maxAnswer(), def.maxAnswerCap)`, Avana's own bound recorded in the definition at listing ([2.10](10-lp-oracle.md) `REQ-ORACLE-049`): its largest value when the aggregator's bound already keeps every route value within `MAX_ROUTE_ANSWER`, and the bound that does for an aggregator deployed with a sentinel `maxAnswer`; a cap at or below `minAnswer` reverts `InvalidFeed(feed, "maxAnswer")`. Example: an 8-decimal stable feed whose aggregator reports `maxAnswer = 2¹⁷⁶ − 1`, listed with `maxAnswerCap = 10¹²`, is pinned at `10¹²`. Checked by: MATH-UO-15, TEST-250. (Source: Q-091, Q-119, Q-191)
- `REQ-CONFIG-023` — Each feed MUST carry its own published `heartbeat`, a freshness margin `heartbeatMargin`, `feedMaxAge`, `feedDeviationThresholdBps`, `heartbeatDriftBps`, `borrowPriceMaxAge` and `liquidationPriceMaxAge`, with `heartbeat < feedMaxAge ≤ liquidationPriceMaxAge`, `0 < heartbeatMargin ≤ MAX_HEARTBEAT_MARGIN` (3,600 s) and `borrowPriceMaxAge ≤ liquidationPriceMaxAge`. `heartbeat` is the value the feed's own configuration publishes, entered per feed and never a global constant: Chainlink stablecoin feeds publish 82,800 to 86,400 s, ETH/USD 3,600 s. `setFeed` MUST require `borrowPriceMaxAge == heartbeat + heartbeatMargin` (`OutOfBounds` otherwise) and stores `min(stored borrowPriceMaxAge, heartbeat + heartbeatMargin)` for a feed that already has one, so a borrow age lowered by a tightening during an incident is not undone by a later definition change; `setBorrowPriceMaxAge` accepts any value in `(0, feedMaxAge]` and `tightenBorrowPriceMaxAge` only a lower non-zero one, which blocks borrowing sooner and never touches liquidation; `setLiquidationPriceMaxAge` and `setFeedMaxAge` accept only `heartbeat + heartbeatMargin` (below it `LivenessBound`, above it `OutOfBounds`), so they re-derive the stored value after a definition change. Units: seconds, exact integers. Why: a feed publishes a round only after its heartbeat has elapsed plus block and network delay, so an age limit equal to the heartbeat refuses valid borrows for a few minutes of every heartbeat; the margin closes that gap. A single cap tied to an hourly heartbeat would make every 24-hour stablecoin feed stale for most of the day and refuse borrowing during that time. A day-old price is safe for a borrow only together with the deviation trigger (a new round within `feedDeviationThresholdBps` of any move) and the independent second source that a borrow or withdrawal also requires (`REQ-PSTORE-028`). The same definition serves each leg of a DebtOracle route, whose ages the RiskModule and LPVaultSwap apply ([2.10](10-lp-oracle.md)). Example: USDC/USD on Ethereum (heartbeat 82,800 s, margin 1,800 s) gets `borrowPriceMaxAge = 84,600` and `feedMaxAge = liquidationPriceMaxAge = 84,600`; ETH/USD (3,600 s, margin 1,800 s) gets 5,400; a `setFeed` for USDC/USD with `borrowPriceMaxAge = 5,400` reverts `OutOfBounds`; an answer 84,000 s old passes the borrow check, one 84,601 s old does not. Checked by: TEST-250. (Source: Q-056, Q-119, Q-139, Q-182, Q-238, Q-248, Q-274, Q-317)
- `REQ-CONFIG-024` — Feed-agreement tolerance lower bound: for each token, `feedAgreementToleranceBps ≥ max(dev(P) + dev(A), dev(S) + dev(A), dev(P) + dev(S)) + feedAgreementMarginBps`, where `P`, `A` and `S` are the token's recorded primary, alternate and standby routes in the MarketRegistry and `dev(route)` is the sum of `feedDeviationThresholdBps` over the route's feeds. The three pairs are every pair a guardian's `useStandbyRoute` can put in force at once (the standby in place of the primary or of the alternate, [2.8](08-market-registry.md) `REQ-MREG-027`), so no standby switch can leave the token below its bound and no short-delay setter is later blocked by a bound the switch broke. Enforced by every tolerance setter, by `setFeed` for every token whose recorded routes use the feed, by `setFeedAgreementMarginBps` for every token, and by the MarketRegistry's `setPriceSource`, as a hard lower bound, and exposed as `feedAgreementToleranceMinBps(token)` (saturated at `2¹⁶ − 1`, which no stored tolerance meets). The LPOracle applies the tolerance as `|p − b| × 10^4 ≤ T × min(p, b)` (cross-multiplied, never floor division). Example: USDC primary 25 bps, alternate USDC/ETH 100 bps × ETH/USD 50 bps, standby 25 bps, margin 50 bps: the bound is `max(175, 175, 50) + 50 = 225` bps; with primary, alternate and standby at 25, 25 and 120 bps it is `max(50, 145, 145) + 50 = 195`, so a `setFeed` raising the standby feed to 120 bps reverts `LivenessBound` while the stored tolerance is 150, although the standby is not in force. Checked by: MATH-UO-23, MATH-UO-24, MATH-UO-68, MATH-UO-69. (Source: Q-112, Q-184, Q-196)
- `REQ-PSTORE-009` — `setFeed` and every per-feed setter MUST revert with `OracleConfigRejected(lpOracle, failedChecks)` when the LPOracle of any market whose routes use the feed returns a non-zero `checkConfig` for the configuration the change gives it; the same holds for every setter that changes a field of `OracleConfig` (tolerances, `twapWindow`, the USD band, `cachedWindow`, `disagreementPauseMax`, `graceDuration`, `secondSource`, the sequencer configuration). A per-feed setter for a feed with no definition (`feedHeartbeat == 0`) reverts `UnknownFeed(feed)`. The affected LPOracles are those of every Registered, Active or Offboarding market: all of them for a chain value, those holding the token for a token value, and for a feed value those with a token whose recorded routes (primary, alternate, standby) or recorded or standby oracle-network second source use the feed. A tighten setter that re-runs `checkConfig` (`tightenBorrowPriceMaxAge`, `tightenConsistencyToleranceBps`, `tightenFeedAgreementToleranceBps`) reads each affected bitmap before and after its write, once with the recorded second sources and once with the standby second source of every token of the market in force (as a guardian's `useStandbySecondSource` would put it; skipped for a market with no standby to switch in, and switched back within the call), and reverts `OracleConfigRejected(lpOracle, after & ~before)` only for a check its own write breaks in either configuration, so a tightening never leaves a configuration that fails once a standby is switched in; and runs no tolerance re-check besides its own value's bound: a check that already failed is not the tightening's doing and never blocks an incident response; every other setter requires a zero bitmap. Each setter writes first and then passes the bytes `getOracleConfig(lpOracle)` returns to `checkConfig` unchanged, so the checked configuration is exactly the one the change gives that LPOracle; a reverting or malformed call counts as every check failing (`failedChecks = 2²⁵⁶ − 1`). (Source: Q-091, Q-184, Q-191)

### Debt-reserve parameters

- `REQ-PSTORE-006` — No buy-leg slippage parameter exists: the liquidation caller funds the debt asset itself (and `deleverage` flash-borrows it through the chain's IFlashSource), and LPVaultSwap's swap routes convert each pool token straight into that debt asset, so no liquidation spends GHO buying another debt asset. The market's `slippageAllowanceBps` bounds every leg of a liquidation whatever the debt asset, with the per-leg oracle `minOut` of [2.11](11-lpvaultswap.md). A debt reserve's listing therefore writes no per-reserve allowance; `enableDebtReserve` instead checks the liquidation inequality of `REQ-PSTORE-021` for the new reserve against every Active or Offboarding market of the Spoke, and the swap routes from each pool token into the new debt asset ([2.12](12-settlement-routes.md)). (Source: Q-233, Q-235, Q-317, Q-404)
- `REQ-PSTORE-007` — No buy-route depth threshold exists, for the reason in `REQ-PSTORE-006`; the depth a liquidation needs is the depth of the swap routes from each pool token into the debt asset, held as `routeDepthThreshold` per swap-route slot (`REQ-CONFIG-070`). (Source: Q-084, Q-235, Q-317)
- `REQ-PSTORE-015` — The lower side of liquidation liveness MUST be `slippageAllowanceMinBps(m)`, set per market to cover the real cost of every swap route the market's liquidations use, into every debt asset enabled against the market (`REQ-CONFIG-041`): an allowance below a route's real cost makes every swap on it revert, which stops liquidation of every account in that market while borrowing continues. No setter MAY take `slippageAllowanceBps` below it, and `enableDebtReserve` for a debt asset whose routes cost more than the current floor of a market MUST be preceded in the same batch by `setSlippageAllowanceMinBps` for that market. `REQ-PSTORE-021` is the upper side. Example: market 4 (USDC/USDT) has a floor of 30 bps for GHO debt; enabling USDC debt whose USDT→USDC route costs 5 bps of fee plus 30 bps of impact needs the floor raised to 35 bps in the same batch, and the raise passes `REQ-PSTORE-021` with `minLB = 10,200` and `maxFlashFeeBps = 10`. Checked by: TEST-245, TEST-225. (Source: Q-235, Q-261, Q-317)
- `REQ-PSTORE-021` — For every Active or Offboarding market `m` of a CDP Spoke and every enabled debt reserve `r` of that Spoke, liquidation MUST stay feasible: `minLB × (10⁴ − slippageAllowanceMinBps(m)) ≥ 10⁴ × (10⁴ + maxFlashFeeBps)`, with `minLB = 10⁴ + ⌊(maxLiquidationBonus − 10⁴) × liquidationBonusFactor / 10⁴⌋` ([2.1](01-avana-hub-and-spokes.md) `SPEC-HUB-005`) from the Spoke's `getLiquidationConfig()` and the latest dynamic key of `m`'s reserve. `liquidationLivenessHolds(spoke, m, r)` evaluates it with the stored `slippageAllowanceMinBps(m)` and `maxFlashFeeBps`, and each setter evaluates the same inequality with its new value in place of the stored one; it resolves `m`'s reserve as `spoke.getReserveId(hub, IHub(hub).getAssetId(vaultToken))` with `hub` the market's Hub from the MarketRegistry, so it answers for a market before activation records its reserve; it returns false for an unknown market, a Spoke other than the market's, a debt reserve the MarketRegistry does not approve, a Spoke or Hub read that reverts, a `maxLiquidationBonus` below 10⁴, or a floor or flash ceiling of 10⁴ or more. All pairs of one market share `minLB`, the floor and the ceiling, so a setter evaluates the inequality once per market that has at least one enabled debt reserve on its Spoke. The setters run it at execution and revert `LivenessBound` on the first failing pair: a raise by `setSlippageAllowanceMinBps(m, v)` of an Active or Offboarding market against every enabled debt reserve of its Spoke; a raise by `setMaxFlashFeeBps` for every such pair on every CDP Spoke of the chain. The MarketRegistry's `enableDebtReserve` calls the view for the new reserve against every Active or Offboarding market of the Spoke, and `activateMarket` for the market being activated against every enabled debt reserve of its Spoke ([2.8](08-market-registry.md) `REQ-MREG-032`). Units: every term in bps; both sides are exact integers below `2⁶⁴`; the only rounding is the floor in `minLB`, which lowers the left side. Why: the bonus at a health factor just below 1 is all the value a liquidation has to pay the swap legs (whose slippage can be tightened down to `slippageAllowanceMinBps`). LPVaultSwap takes no flash loan, so the recovery floor of a liquidation needs only `minLB × (10⁴ − s) ≥ 10⁸` ([2.11](11-lpvaultswap.md) `SPEC-LIQ-016`); the check keeps the stronger right side `10⁴ × (10⁴ + maxFlashFeeBps)` so that a caller holding no debt asset, which borrows it through the flash liquidation helper at a premium up to `maxFlashFeeBps`, still recovers its loan and premium at the routes' best, and a `deleverage` still covers its own premium (`Q-404`). If `minLB × (1 − s)` falls below 1, the recovery floor cannot be met and every liquidation of that pair reverts while borrowing continues; between 1 and `1 + f`, only callers that borrow the debt asset lose money at the worst allowed slippage. The pair check is per debt reserve because each debt reserve's swap routes are listed against the market, and a reserve enabled later must pass it before borrowing starts; an Aave bonus cut after activation is drift that stops new borrowing (`REQ-HUB-108`). Example: `minLB = 10,200` (`maxLiquidationBonus = 10,500`, `liquidationBonusFactor = 4,000`), `slippageAllowanceMinBps = 30`: the left side is `10,200 × 9,970 = 101,694,000`; with `maxFlashFeeBps = 10` the right side is `10⁴ × 10,010 = 100,100,000` and the check holds; the inequality admits `f = 169` (`101,690,000`) and refuses `f = 170` (`101,700,000`), so at this floor the hard bound of 100 bps binds first (`setMaxFlashFeeBps(101)` reverts `OutOfBounds`); with a floor of 100 bps the left side is `10,200 × 9,900 = 100,980,000 = 10⁴ × 10,098`, so `setMaxFlashFeeBps(98)` passes with equality and `setMaxFlashFeeBps(99)` (`100,990,000`) reverts `LivenessBound`. Checked by: TEST-245, TEST-225. (Source: Q-261, Q-317, Q-404)
- `REQ-CONFIG-070` — Each swap-route slot `(marketId, token, debtAsset, kind)` ([2.12](12-settlement-routes.md) `REQ-ROUTE-006`; `kind` 0 primary, 1 backup, any other `OutOfBounds`) MUST carry `routeDepthThreshold(marketId, token, debtAsset, kind)`, stored under `keccak256(abi.encode(marketId, token, debtAsset, kind))`: the USD notional (8 decimals) the slot's route must convert from `token` into `debtAsset` within the market's slippage allowance in the stress case published at listing. For a concentrated-liquidity market the stress size is the full position value at either range edge, where the position is 100% one token, not half of it: in a constant-product route ten times deeper than the position, two half-value legs each lose 4.76% while one full-value leg loses 9.09%. `tightenRouteDepthThreshold` (short delay) MUST revert unless the new value is strictly higher, and `loosenRouteDepthThreshold` (normal delay) unless strictly lower. The threshold is a monitoring and listing criterion; a swap route does not check it. (Source: Q-084, Q-187, Q-228, Q-317)

### Circuit breakers

- `REQ-PSTORE-016` — The ParameterStore MUST hold the on-chain breaker values of `Q-399` in the table, within these bounds and change directions; a tightening runs at the short delay and a loosening at the normal delay, each reverting `NotStricter` or `NotLooser` and `OutOfBounds` as for every parameter. The RiskModule reads them in its new-activity checks and in `pokeBreakers` ([2.7](07-risk-module.md)). No exit, eligible liquidation, pending settlement or rescue top-up reads any of them, so no allowed value can stop those paths. There is no `breakerPriceDropBps`, `breakerSeizureBps`, `breakerRouteFailureCount`, `breakerCooldown` or `breakerPoolShareBps`: price drops, seizure surges and swap-route failures are monitoring alerts whose thresholds (3 % in 2 hours; 20 % of a market's credited units in 1 hour; 3 failures in 1 hour) live in the monitoring configuration, and the pool-share threshold is `poolShareMaxBps` itself, one concentration threshold for pledges and borrowing: 10,000 bps (off) by default, with a per-pool cap where a listing sets one; Avana's combined share of a pool above 25 % is a monitoring alert (`Q-403`). `breakerDeficitMax(hub, asset)` is in the asset's base units and is 0, which trips on any deficit, until the `enableDebtReserve` batch of the first reserve of the asset funded by `hub` raises it: 10,000 GHO (`10_000e18`) for the GHO reserve of each affected CDP Spoke, and a per-reserve materiality set at listing for every other asset, each a proposed default whose final value is set in the listing ARFC; `tightenBreakerDeficitMax` and `loosenBreakerDeficitMax` revert `UnknownHub` for an unrecorded Hub, and `loosenBreakerDeficitMax` reverts `UnknownDebtReserve(address(0), 0)` while no approved debt reserve of the asset is funded by `hub`, and `OutOfBounds` above the smallest `firstLossReserveMinimum()` of those reserves' Coverage Spokes, so new borrowing freezes before an uncovered deficit could exceed what the reserve is funded to absorb. Example: `tightenBreakerDeficitMax(stableHub, GHO, 5_000e18)` executes 12 hours after scheduling, and from then a 5,000.01 GHO deficit freezes GHO borrowing on that Spoke; `loosenBreakerDeficitMax(stableHub, GHO, m + 1)` reverts against a Coverage Spoke minimum `m`. Checked by: TEST-228, TEST-225. (Source: Q-241, Q-399)

- `REQ-PSTORE-030` — `gateRecoverySeconds` MUST be stored per chain in seconds within `[600, 7,200]`, launch 1,800 (30 minutes, a provisional launch setting), raised by `tightenGateRecoverySeconds` at the short delay and lowered by `loosenGateRecoverySeconds` at the normal delay. A temporary gate (`ORACLE`, `POOL_SHARE`, `POOL_DEPTH`) of a key is open only when its condition is false now and `block.timestamp ≥ lastBreachAt(key) + gateRecoverySeconds`, with `lastBreachAt` the latest breach the RiskModule's `pokeBreakers` recorded ([2.8](08-market-registry.md) `REQ-MREG-026`); for recovery from an Expired price state the LPOracle's own `graceDuration` applies on top. Units: seconds; exact integer comparison. Why: a price or depth breach that clears for one block and returns the next would otherwise reopen borrowing against a pool that is still unstable; 30 minutes of healthy observations, with Avana's keeper poking every block (150 blocks on Ethereum, 900 on Base), shows the breach has passed, while a security freeze (deficit, issuer, drift, manual) waits for an authorized reset instead. Example: Avana's share of a pool rises to 10.4 % at 09:00 and `pokeBreakers` records it; outside liquidity returns at 09:12 and the share falls to 9.6 %; new borrowing against the market stays blocked until 09:42 (the last breach recorded at 09:12 plus 1,800 s), and a new breach at 09:30 would move that to 10:00. Checked by: TEST-228. (Source: Q-399)

### Chain parameters

- `REQ-PSTORE-023` — Each chain's ParameterStore MUST hold the chain's sequencer-uptime check `sequencer = SequencerConfig{feed, gracePeriod}`: on a chain with no sequencer (Ethereum) `feed == address(0)` and `gracePeriod == 0`; on an L2 (Base) `feed` is the chain's Chainlink sequencer-uptime feed and `gracePeriod` within `[600, 7,200]` s, launch 3,600 s. Whether the chain is an L2 is the implementation immutable `HAS_SEQUENCER`. `initialize` leaves the check empty (`feed = address(0)`, `gracePeriod = 0`, Ethereum's value) and emits `SequencerSet(address(0), 0)`; on an L2 the first batch writes it. `setSequencer` (normal delay) MUST revert `InvalidSequencerFeed(feed)` on an L2 unless `feed` holds code and `latestRoundData()` returns an answer of 0 (up) or 1 (down) with `startedAt > 0`, and `OutOfBounds` unless `600 ≤ gracePeriod ≤ 7,200`; on Ethereum it reverts `InvalidSequencerFeed(feed)` unless `feed == address(0)` and `OutOfBounds` unless `gracePeriod == 0`; on an L2 it also reverts `OutOfBounds` unless the grace covers every TWAP window (`REQ-PSTORE-034`); it re-checks every LPOracle (`REQ-PSTORE-009`). The LPOracle and the RiskModule read it through `getOracleConfig`: while the feed reports down, or for `gracePeriod` seconds after `startedAt` of the restart round, every borrow-side price check fails closed; liquidation is not gated by the grace period, and no transaction is sequenced while the feed reports down. Units: seconds. Why: while an L2 sequencer is down borrowers cannot top up, so prices that moved during the outage must not open new debt the moment it returns; one hour lets them act first. Example: Base feed `0xBCF85224fc0756B9Fa45aA7892530B47e10b6433`, restart round `startedAt = 1,000,000`: a borrow at `1,003,599` reverts, one at `1,003,600` passes the sequencer check; a `setSequencer` on Ethereum naming that address reverts `InvalidSequencerFeed`. - `REQ-PSTORE-033` — `getOracleInputs(lpOracle, tokens, withSecondSources)` MUST return the words of `OracleInputsLayout`, `10 + n × (37 + 9·withSecondSources)` of them for `n = tokens.length`: the head `marketId = MARKET_REGISTRY.marketOfLpOracle(lpOracle)`, the market's `twapWindow` and `consistencyToleranceBps`, the chain's `usdBandLow`, `usdBandHigh`, `cachedWindow`, `disagreementPauseMax`, `graceDuration`, `sequencer.feed` and `sequencer.gracePeriod`; then per token of `tokens`, in that order, the stored `feedAgreementToleranceBps`, `MARKET_REGISTRY.priceRouteVersion(token)`, the replaced slot and the leg counts of the primary and alternate in force as `MARKET_REGISTRY.activePriceRoutes(token)` returns them, and four legs of 8 words (primary legs 0 and 1, alternate legs 0 and 1: aggregator, pinned `decimals`, `minAnswer`, `maxAnswer` as two's-complement words, `feedHeartbeat`, `heartbeatMargin`, `borrowPriceMaxAge`, `liquidationPriceMaxAge`), zero beyond a route's leg count and for a route of more than two legs; and, when `withSecondSources`, the second source in force (the standby while `onStandby[token]`) as `kind`, `source`, `poolRef`, `maxAge`, `twapWindow`, `toleranceBps` and, for an oracle network, the source's pinned `decimals`, `minAnswer` and `maxAnswer`. A `lpOracle` that is no market's LPOracle gets `marketId = 0` and zero words. The registry is read in the same static call, so the routes in force and the version are the registry's in that block; a registry read that reverts reverts the view, which the LPOracle reads as a failed configuration. Unlike `getOracleConfig`, the bounds are not saturated into `int128`: the LPOracle compares the answer with the stored `int256` bounds. Example: a two-token market with one-leg primaries and two-leg alternates returns 84 words, 102 with second sources. (Source: Q-240, Q-248, Q-317)
- `REQ-PSTORE-011` — Every view MUST be `view`, never revert for a listed market, token, feed or debt reserve, and return the values in force at the current block; a view for an unknown key returns zeros, which makes every age and usability check fail closed. `getOracleConfig` for an address that is no market's LPOracle returns a configuration with `marketId = 0` and empty routes, which the LPOracle treats as failed. A market-scoped setter reverts `UnknownMarket(marketId)` for an identifier the MarketRegistry never assigned, so no value is written for a market that does not exist. (Source: Q-056, Q-119, Q-240)
