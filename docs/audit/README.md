# audit

Audit scope, external reports and verification evidence for Avana. The official findings register is [5.3 Audit Findings](../spec/05-verification/03-audit-findings.md). [`findings-register.md`](findings-register.md) in this folder is the internal-review view: every finding from Avana's internal review and verification runs, open or resolved, with the run that found it. This folder also holds each run's report, run log and models, and the material the findings and proofs cite. Every check Avana runs on its code and its design has a folder here with how it runs and its latest results; the [index](#internal-verification) lists them all.

## Scope (`Q-115`)

The audit covers the code written from the specification:

| In scope | Notes |
|---|---|
| Every Avana contract in `contracts/src/` | LPVault, Collateralization, vault tokens and factory, PositionProxy and ProxyManager, AaveAdapter, RiskModule, MarketRegistry, ParameterStore, LPOracle, DebtOracle, LPVaultSwap, the settlement routes (DexPath, WrapperThenDex, PegModule), the Aave V3 flash source, the Coverage Spoke, the flash liquidation helpers, PayoutEscrow, Lock, AvanaTimelock and AvanaRoles |
| Deployment scripts and AvanaTimelock operations | Including deployment and initialization order, the role map, the short-delay list and the listing batches |
| Configuration review of the Aave DAO deployment and listing payloads | The Hub and Spoke settings Avana depends on; Aave V4 code itself is out of scope |
| `packages/protocol` calldata building | Targets, approvals, receivers and amounts |
| Keeper, Convex backend and Lens | Reviewed separately, with a lighter review |

The unmodified Aave V4 contracts are not audited here; the deployment check proves their bytecode equals the audited Aave release named in the manifest.

### How the review process works

1. **Test first, one contract at a time.** The checklist generator (`contract_checklist.py`) lists the contract's REQ/SPEC, TEST, PROP, INV and ATTACK rows. A design check sets the file split, storage layout, external calls, reentrancy entries, rounding directions and failure modes against the ATTACK rows; a gap in the spec stops the work until the spec and its Z3 model are fixed. Tests come first: one unit test per `TEST` row, fuzz tests for every formula and bound, a Halmos check per Halmos `PROP`, an Echidna/Medusa property per `INV`, the Certora conf compiling, golden vectors from the Z3 and SymPy models for the math libraries. Then the implementation, with `/// @custom:spec` on every function.
2. **Contract gate.** `forge build --force -D warnings`; `forge test` green (fuzz at 1,000 runs, 10,000 on the contract's math); file sizes; `trace.py` with 0 errors and every ID of the contract linked; the fast tier with zero untriaged findings; every Halmos check; the Certora conf compiling (a full prover run needs `CERTORAKEY`); the differential run for math contracts; the independent review.
3. **Independent review per contract.** It starts as soon as the contract compiles. The reviewer receives only the spec page and the code, writes PoC tests, and every finding is fixed or answered in the record ([`reviews/`](reviews/)).
4. **Triage rule, approval by pattern.** A real finding is fixed. A false positive is accepted only by a triage entry with a one-line reason; the gate fails on an entry without one. On 2026-11-10 Josue approved every entry and inline suppression recorded so far (218 entries, 151 suppressions) by pattern; a later entry in an approved pattern is accepted "by pattern" once the independent review agrees, and a new pattern or a higher-severity detector is approved entry by entry.
5. **Slow tier at the end of each layer.** After each layer (2.1 foundations, 2.2 AMM integrations, 2.3 flash source, 2.4 proxies, 2.5 core contracts that use them, 2.6 periphery): Echidna, Medusa, hevm, Mythril, the SMTChecker and `certoraMutate` at full budget over every contract of the layer; Foundry-suite mutation testing and Necessist; integration tests across the layer on the local Aave V4 fixture; `run_all.sh` and the three `formal-verification/*/run.sh`; the size check over everything. AvanaRoles, the Lock and the AvanaTimelock also ran the slow tier at their own contract gate.
6. **Before audit.** The properties move into one harness shared by Echidna, Medusa, Foundry invariants and Halmos, and each layer gets a 24-hour Echidna and Medusa campaign, with the corpus kept and replayed in CI.

## Keeping the record current

1. **Every run appends to its folder's `RUNS.md`.** The entry gives the date, the exact command, tool versions, seeds and bounds, result counts and exit code, the finding IDs it produced and the decision range of the spec it ran against. Earlier entries are not edited. A new kind of review gets its own folder with a report and a `RUNS.md`, and a row in the table above.
2. **Every finding gets a register row** in [`findings-register.md`](findings-register.md) when the run that found it is logged, with the ID its report uses, the source run, severity, title and the spec rules involved. It starts as Open.
3. **A finding becomes Resolved in spec only when both hold:** the spec rule it names has changed (a decision in [4.4](../spec/04-security/04-design-decisions.md) and the changed rule text in the spec pages), and the check that proves the fix passes against the changed rule in a run logged in `RUNS.md`. The Resolution column then names the decision and the changed rule IDs, and "Verified by" names the check. A recorded decision alone leaves the finding Open, with the decision named in its Resolution. When the changed rule text is in the spec pages but no logged run has yet passed the proving check against it, the finding is Resolved in spec — re-verification pending until that run passes.
4. **Accepted risk and Rejected** each need a recorded decision or a written re-examination, named in the Resolution.
5. **Mirroring to 5.3.** A finding that is Resolved in spec or Accepted risk is added to [5.3 Audit Findings](../spec/05-verification/03-audit-findings.md) as a `FINDING-NNN` entry, and the register row names that entry.
6. **Summary tables** at the top of the register and the Status column above are updated in the same change as the rows they count.

## Findings

Every failed check and every attack the design does not fully block is a `FINDING-NNN` in [5.3](../spec/05-verification/03-audit-findings.md), citing the requirement, flow step or invariant it affects and the test or property that confirms the fix. Findings from the internal runs in this folder are recorded first in [`findings-register.md`](findings-register.md) with the statuses Open, Resolved in spec — re-verification pending, Resolved in spec, Accepted risk and Rejected, and are mirrored into 5.3 once they are resolved in spec (re-verification pending or done) or Accepted risk. External auditors' findings are added in the same format, with the raw report kept here.

| Severity | Meaning |
|---|---|
| Critical | Loss of collateral or unbacked debt with no precondition beyond an upgrade or a public call |
| High | Loss or protocol-wide halt under a plausible condition |
| Medium | Bounded loss, griefing or liveness loss in one market |
| Low | Dust-level loss or a narrow condition |
| Informational | Confirms a decision; no loss |

Statuses in 5.3:

| Status | Meaning |
|---|---|
| Resolved in design | A decision removes it; the verification proves the fix on code |
| Accepted risk | Residual risk accepted by a decision; the verification monitors or bounds it |
| Launch condition | Resolved once a value, configuration or agreement is in place before launch; the verification checks it |

5.3 holds 295 findings: 75 resolved in design, 99 resolved in spec, 83 resolved in spec with re-verification pending, 3 resolved, 28 accepted risks and 7 launch conditions. The seven launch conditions are the minimum liquidation bonus set through the bonus factor (`FINDING-019`), cap sizing from the worst LP drop during a pause (`FINDING-027`), backup-route depth under a USDC depeg (`FINDING-049`), First-Loss Reserve sizing against tail collapse at high pool risk factors (`FINDING-052`), feed cadence against silent feed stalls (`FINDING-053`), the keeper reimbursement agreement (`FINDING-057`) and debt-reserve listing against a debt-asset price rally (`FINDING-102`). The per-pool manipulation-cost study and TWAP backtest are reviewed documents recorded with these launch conditions.
