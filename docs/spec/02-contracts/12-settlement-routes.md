# 2.12 Settlement Routes

> **Status:** In review · **Owner:** Avana Labs · **Last reviewed:** 2026-11-10
>
> **Requirement prefix:** `REQ-ROUTE-NNN`

## Purpose

Swap routes move value from a token released by an unwind into the debt asset of the liquidation, inside one LPVaultSwap call, along a path fixed when the route contract is deployed. Every liquidation settles in the debt asset it repays (`Q-333`), so there is one kind of route: a **swap route** converts one released token of a market into one debt asset (`ISettlementRoute`, `swap`). For each market, each of its tokens and each debt asset approved on its CDP Spoke, the MarketRegistry records a **primary** and an independent **backup** swap route. A token that is itself the debt asset needs no route. The same swap routes serve liquidations, repays with collateral and the settlement of a pending-settlement balance (into the market's pending-settlement asset).

There are no buy routes and no sell-back routes: the liquidation caller funds the repayment in the debt asset itself ([2.11](11-lpvaultswap.md#funding)), and `deleverage` flash-borrows the debt asset itself ([2.11](11-lpvaultswap.md#flash-source)), so LPVaultSwap never buys the debt asset with another token and never sells a leftover back.

Route contracts execute the legs; route records name which route contract fills each slot and whether it is Active. The MarketRegistry ([2.8](08-market-registry.md)) stores the route records; the ParameterStore ([2.9](09-parameter-store.md)) stores the published depth thresholds.

Routes are not responsible for:

- computing the minimum output a swap must return: LPVaultSwap derives it from oracle values (`SPEC-LIQ-018`) and passes it in; a route only enforces the `minOut` it receives (`REQ-ROUTE-042`), and LPVaultSwap's aggregate floors still apply over the whole call;
- choosing between primary and backup at run time (LPVaultSwap does that);
- unwinding liquidity (Collateralization and the market's LPVault do) or valuing tokens (the LPOracle, the DebtOracle and the AaveOracle do).

CoW Swap and every off-chain or batch-settled swap path are out of scope: every leg completes inside the LPVaultSwap call, because a swap that settles later would leave the waterfall unpaid, and a helper's or `deleverage`'s flash loan unrepaid, when the transaction ends.

## Inputs

- From LPVaultSwap, inside `liquidate`, `settlePending` or `deleverage`: `swap(amountIn, minOut)` with `amountIn` of the route's input token, pulled by `transferFrom` against an exact allowance, and the oracle-derived minimum output `minOut ≥ 1` in the route's output token.
- From the external contracts a route calls: the output token and intermediate tokens returned by AMM pools (Uniswap v3, Aerodrome Slipstream, Curve StableSwap-NG, pinned legacy Curve pools), the Sky LitePSM and DAI/USDS converter, and, on Ethereum, the GHO Stability Modules (GSM) with their static aToken wrappers.
- From governance, through the chain's AvanaTimelock as `APPLICATION_ADMIN`: route records (set, disable, restore) on the MarketRegistry and depth thresholds on the ParameterStore.

## Outputs

- The output token (the debt asset) sent to LPVaultSwap.
- Any unconsumed input or intermediate token sent back to LPVaultSwap (forwarded to the caller in a liquidation, to `feeRecipient` in `settlePending` and to the borrower's wallet in `deleverage`).
- Route-record events from the MarketRegistry and threshold events from the ParameterStore.
- No change in the route's balance of any token over a call and no allowance outstanding after it; a token sent to a route outside a call stays there and is never used (`REQ-ROUTE-016`).
- Every hop's output, the debt asset included, is the route's measured balance rise, never a pool's return value: a legacy Curve pool that returns no data and one that returns a wrong amount deliver the same measured output (`REQ-ROUTE-046`).

## Route types

| Route type | Interface | Input → output | Legs (in order) | External contracts |
|---|---|---|---|---|
| `PegModule` (0) | `ISettlementRoute` | A token into the debt asset through a peg module of the pair, where its live capacity covers the leg; never the only route of a token | GSM (Ethereum, backup slot of a GHO debt reserve only): (1) `IERC4626(staticAToken).deposit(amountIn, route)` → shares; (2) `Gsm.sellAsset(shares, LPVaultSwap)` → GHO; (3) unsold shares and any input the static aToken did not take to LPVaultSwap. LitePSM (Ethereum, DAI or USDS into USDC): (1) for USDS, `DaiUsds.usdsToDai(route, amountIn)`; (2) `LitePSM.buyGem(LPVaultSwap, gemAmt)` (`REQ-ROUTE-012`); (3) leftover DAI to LPVaultSwap | The peg module the chain's address book lists for the pair; static aToken; Sky LitePSM and DAI/USDS converter |
| `DexPath` (1) | `ISettlementRoute` | Any listed token → any enabled debt asset | One to three fixed hops ending in the debt asset, each on the whole output of the one before. Uniswap v3 or Slipstream hop: `pool.swap(route, zeroForOne, int256(amount), limit, "")` with the extreme price limit (`MIN_SQRT_RATIO + 1` or `MAX_SQRT_RATIO − 1`), paying in `uniswapV3SwapCallback`. Curve StableSwap-NG hop, or legacy Curve hop on a pinned pool (`REQ-ROUTE-046`): `exchange(i, j, amount, 0)`. Output forwarded to LPVaultSwap; `minOut` checked on LPVaultSwap's balance delta (`REQ-ROUTE-009`) | Fixed pools |
| `WrapperThenDex` (2) | `ISettlementRoute` | A wrapped or rate token → any enabled debt asset | (1) one unwrap or redeem step: `IERC4626(tokenIn).redeem(amountIn, route, route)` (a static aToken, a savings-rate token such as sUSDS) or `DaiUsds.usdsToDai(route, amountIn)`; (2) up to three `DexPath` hops on the step's output, none when the step yields the debt asset | The wrapper; fixed pools |

Each route also reports the token classes it was tested for, `supportsTokenClass(tokenClass)` (1 stable, 2 correlated, 3 volatile), at a fully one-sided unwind of a concentrated range (`REQ-ROUTE-006`).

Route records (in the MarketRegistry; `kind` is the slot, `PRIMARY = 0` or `BACKUP = 1`):

| Record set | Key | Fields | Written by |
|---|---|---|---|
| Swap routes | `(marketId, token, debtAsset, kind)` | `route`, `status` (`Active`, `Disabled`), `approvedBefore[route]` (the slot's current route; a replaced route leaves it) | `setRoute`, `disableRoute`, `restoreRoute` |

Depth thresholds (in the ParameterStore): `routeDepthThreshold(marketId, token, debtAsset, kind)`, the USD notional the route must swap within `slippageAllowanceBps` under the stress case of `REQ-ROUTE-006`.

## Permissions

Every route-record and threshold change is an `APPLICATION_ADMIN` call reached only through the chain's AvanaTimelock ([2.15](15-governance-and-timelock.md)): the chain's governance Safe schedules it, and every `CANCELLER_ROLE` holder can cancel it during the delay, except an operation made only of `restoreRoute` calls, which only `DAO_CANCELLER_ROLE` can cancel (`Q-263`).

| Action | Delay | Why that delay |
|---|---|---|
| Add or change a route (`setRoute`) | Normal (5 days) | A new route is new code holding liquidation proceeds; reviewers simulate it on a fork |
| Disable a route (`disableRoute`) | Short (12 hours) | Only removes a path; the other slot keeps working |
| Restore a previously approved route (`restoreRoute`) | Short (12 hours); DAO-only cancel | Only returns to code that already passed the normal delay |
| Raise / lower a depth threshold | Short / normal | Raising makes the requirement stricter |
| `swap` | None | LPVaultSwap only, under the Lock |

No guardian can suspend or quarantine a route (`Q-227`). A route that fails at run time reverts and LPVaultSwap falls back to the other slot. Every route is in the address-freeze protected set (`Q-242`), and no pause, breaker or freeze is read by a route. Route failures are not counted on-chain: a reverted call cannot persist a count, and a counter that callers feed can be gamed. Monitoring alerts at 3 route failures of a market in 1 hour, and a guardian freezes new borrowing only when the approved routes are confirmed unable to settle valid liquidations at the required size (`Q-399`); neither ever stops liquidation.

## Route selection at listing

- `REQ-ROUTE-001` A market can be activated only if, for every token of the market and every debt asset approved on its CDP Spoke, the token is that debt asset or the market has an Active primary and an Active backup route with `tokenIn()` the token and `tokenOut()` the debt asset. A debt reserve can be enabled on a Spoke (`enableDebtReserve`) only if every listed market of the Spoke has both routes of every token into that debt asset. Routes are set in the listing batch with `setRoute` at the normal delay. (Source: Q-058, Q-062, Q-084, Q-187, Q-233, Q-339)
- `REQ-ROUTE-002` Route classes per token class (`Q-339`). For each (token, debt asset) pair the primary route is the deepest audited on-chain path whose measured depth meets `REQ-ROUTE-006`: a `DexPath` through fixed pools for every class; a `PegModule` route through the Sky LitePSM for DAI or USDS into USDC on Ethereum. Stable-class tokens may route through stable pools (Curve StableSwap-NG, Uniswap v3 or Slipstream 0.01 % pools); Correlated-class tokens (an LST into WETH, a wrapped BTC into WBTC) route through their correlated pool and then, if the debt asset differs, through a deep pool into it; Volatile-class tokens route through a deep pool of the token against WETH or USDC and then into the debt asset. The GSM is never a primary route; a `PegModule` route through a GSM may fill only the backup slot of a token into GHO on Ethereum (`Q-341`). Why: routes existed only for stablecoins into GHO, so Correlated and Volatile markets could neither list nor liquidate at size; settling in the debt asset lets each market route straight into what it owes. Example: a Slipstream WETH/cbETH market on Base with a USDC debt reserve routes cbETH through the cbETH/WETH pool and then the WETH/USDC pool (primary) and through a Uniswap v3 cbETH/WETH pool and a Curve WETH/USDC pool (backup); WETH routes directly through a WETH/USDC pool. (Source: Q-058, Q-062, Q-339, Q-341)
- `REQ-ROUTE-003` The backup route of a slot MUST share no entry of `dependencies()` with the primary of the same (market, token, debt asset), and the two MUST share no entry of `intermediates()` other than the debt asset itself. A backup MUST NOT call a GSM, static aToken or PSM of the market's own tokens when the primary does. A token whose issuer can switch on a transfer fee is a dependency both routes would share if either paid it into a contract that requires the exact amount it was sent; `REQ-ROUTE-008` keeps every such token out of those contracts in both slots, so switching the fee on can stop neither. Why: one external failure (a frozen GSM, a halted PSM, a drained pool, the pause of a shared intermediate token such as USDC, or an issuer switching on a transfer fee) must not disable both routes of any slot; with a shared intermediate, a USDC pause stopped the WETH routes of markets that hold no USDC (`Q-342`). Checked by: SIM-01C. (Source: Q-187, Q-084, Q-273, Q-342)
- `REQ-ROUTE-004` A route of a market MUST NOT call that market's own pool on any hop. The liquidation is removing liquidity from that pool in the same transaction, and a pool whose state the LPOracle and Collateralization guard must not also price the swap. (Source: Q-085, Q-128, Q-144)
- `REQ-ROUTE-005` `setRoute` and `restoreRoute` MUST revert with `InvalidRoute` unless `route.tokenIn() == token`, `route.tokenOut() == debtAsset`, `debtAsset` is the asset of a debt reserve approved on the market's Spoke, the route's `LP_VAULT_SWAP` is the chain's LPVaultSwap, the route type is admitted in that slot (`REQ-ROUTE-002`), and its `dependencies()` and `intermediates()` satisfy `REQ-ROUTE-003`, `REQ-ROUTE-004` and `REQ-ROUTE-043` against the market record and the other slot. A route calls a GSM when `routeType()` is `PegModule` and `pegModule()` returns kind `Gsm`; the module MUST be an entry of `dependencies()`, and a `routeType()` or `pegModule()` answer that reverts or is not exactly one word (two for `pegModule()`) in range refuses the route. For a route that calls a GSM, they MUST also revert unless `!gsm.getIsSeized()`, `!gsm.getIsFrozen()` and `gsm.getExposureCap() > 0` (`Q-341`). They MUST revert with `InvalidRoute` when any token of `route.exactAmountInputs()` is a listed token whose issuer probe reads `basisPointsRate()`, `UsdtFeeRate` or `UsdtFeeRateAndPaused` ([2.8](08-market-registry.md) `TokenDef.issuerProbe`), whatever its current rate (`REQ-ROUTE-008`). They MUST revert with `InvalidRoute` when `token`, `debtAsset` or an entry of `route.intermediates()` has an ERC-1820 `ERC777Token` implementer, read as `getInterfaceImplementer(t, keccak256("ERC777Token"))`; a read that reverts or does not return exactly one zero word refuses the route, and on a chain whose ERC-1820 registry address has no code no token has one (an ERC-777 token registers itself there in its constructor). (Source: Q-043, Q-151, Q-187, Q-228, Q-273, Q-341, Q-342)
- `REQ-ROUTE-006` Each route slot has a published `routeDepthThreshold(marketId, token, debtAsset, kind)`, set in the listing batch and changed only by `tightenRouteDepthThreshold` (short delay) and `loosenRouteDepthThreshold` (normal delay). Listing requires the measured depth of the route to be at least the threshold, and the threshold to be at least the stress size of the token: the full single-token value of the largest position the market's caps allow at each edge of its range, not half of it (`Q-340`). Monitoring re-measures depth daily at the same stress size; when depth falls below the threshold governance schedules `disableRoute`, and, if exposure must stop growing, `setMarketOffboarding` with an Aave reserve freeze; a guardian's freeze of new borrowing stops new activity at once (`Q-399`). Market caps are sized to what the routes, the Aave V3 Pool liquidity behind the flash liquidation helper and the committed operators' inventory can settle (`SPEC-LIQ-021`). Why: a concentrated position at or beyond its range edge is 100 % one token, so stressing two half legs understates price impact. In a constant-product pool of depth `10V` (in value), two legs of `V/2` lose `0.5 / 10.5 = 4.76 %` each, while one leg of `V` loses `1 / 11 = 9.09 %`; with `slippageAllowanceBps = 500` the half-leg stress passes and the real one-sided unwind fails every leg minimum. Example: a USDC/USDT market whose largest capped position is worth $2,000,000 must show each token's route swapping $2,000,000 within the allowance, not $1,000,000. Checked by: MATH-ST-103. (Source: Q-058, Q-084, Q-119, Q-186, Q-187, Q-228, Q-340, Q-404)

## Conversion

- `REQ-ROUTE-007` `swap` MUST revert with `NotLPVaultSwap` unless `msg.sender == LP_VAULT_SWAP`, and with `NotLocked` unless the Lock is held by LPVaultSwap or by `AAVE_ADAPTER`. (Source: Q-148, Q-062, Q-255)
- `REQ-ROUTE-008` `swap` MUST request `amountIn` with `TOKEN_IN.transferFrom(LP_VAULT_SWAP, route, amountIn)`, measure `inRecv` as the rise of its `TOKEN_IN` balance, revert with `TransferMismatch` if `inRecv == 0` or `inRecv > amountIn`, and run every leg on `inRecv`. `minOut` is not reduced for a transfer fee. A token whose issuer can switch on a transfer fee (USDT: it answers `basisPointsRate()`, read by the `UsdtFeeRate` issuer probe of [2.8](08-market-registry.md) and by the combined `UsdtFeeRateAndPaused` probe USDT on Ethereum is listed with) MUST NOT be paid into a contract that requires the exact amount it was sent: the input of a Uniswap v3 or Slipstream hop (the pool checks its balance after the callback, so a fee reverts the hop) or of a GSM route (the static aToken supplies the amount it pulled to the Aave Pool, so a fee reverts the deposit). The constructor refuses a route whose concentrated-liquidity hop input or GSM input answers the probe, with the fee on or off (`REQ-ROUTE-045`), the route lists those inputs in `exactAmountInputs()`, and listing refuses a route whose listed exact-amount input carries a probe that reads the fee rate, `UsdtFeeRate` or `UsdtFeeRateAndPaused`, exactly alike (`REQ-ROUTE-005`); a token listed with `None` because it has no fee switch on its chain (bridged USDT on Base) may enter such a hop, and the constructor check of `REQ-ROUTE-045` still refuses it if it answers `basisPointsRate()`. Such a token reaches a pool only through a Curve hop (StableSwap-NG, or a pinned legacy pool, `REQ-ROUTE-046`), which the route pays by `transferFrom` of exactly the leg's input and whose output the route measures, as an input, as an intermediate or as the debt asset; a fee on the output of a concentrated-liquidity hop or on the debt asset only lowers the measured rise. Measured input: a rise above `amountIn` (a token that credits more than it was asked for, such as a rebasing token rounding up) reverts `TransferMismatch`, so a route never counts units LPVaultSwap did not send, and LPVaultSwap uses the other slot; a rise below it (a fee, or a rebasing token rounding down by a unit) is what the legs swap. Why: with the fee switched on, every swap of USDT through a concentrated-liquidity pool would revert, possibly in both slots at once; Curve's measured transfer handles it. Example: with USDT's fee at 10 bps, LPVaultSwap sends 6,211,300,000 USDT units to a USDT → USDC route over a Curve pool, the route swaps `inRecv = 6,205,088,700`, and the fee is a cost inside the leg's slippage allowance; the same route over a Uniswap v3 USDT/USDC pool is refused at deployment. Checked by: TEST-221. (Source: Q-052, Q-058, Q-075, Q-124, Q-271)
- `REQ-ROUTE-009` Every route MUST run with the minimum output LPVaultSwap passes as `minOut`, checked once after the last leg against `out`, LPVaultSwap's balance rise in `TOKEN_OUT` over the whole call, which counts both the output the route forwards after a final pool hop and the output a GSM or LitePSM pays LPVaultSwap directly. The route MUST revert with `MinOutNotMet(out, minOut)` when `out < minOut`. Every hop runs with a zero minimum (Curve `min_dy = 0`) and the extreme price limit; any value lost on a hop lowers the final output, which the final check catches. Why: one check on what LPVaultSwap received covers every route type and a transfer fee on the debt asset, and always reverts with `MinOutNotMet`, where a pool's own minimum reverts with the pool's error. Checked by: TEST-232, TEST-227, PROP-068. (Source: Q-085, Q-131, Q-250, Q-333)
- `REQ-ROUTE-010` Before each leg whose contract pulls its input with `transferFrom` (a Curve hop, the static aToken `deposit`, the GSM `sellAsset`, the DAI/USDS converter, the LitePSM `buyGem`) the route MUST `forceApprove` that contract for exactly the leg's input and reset the allowance to 0 after it. A concentrated-liquidity hop pays in its callback (`REQ-ROUTE-013`) and an ERC-4626 `redeem` of the route's own shares needs no allowance, so neither approves. `forceApprove` handles tokens that return no `bool` and revert on a non-zero to non-zero change (USDT). (Source: Q-119, Q-124, Q-342)
- `REQ-ROUTE-011` A GSM leg of a `PegModule` route MUST approve the static aToken for exactly `inRecv` and `deposit(inRecv, route)`, reset the allowance, measure the shares minted as the rise of the route's static-aToken balance, approve the GSM for exactly those shares and call `sellAsset(shares, LP_VAULT_SWAP)`, which sells the largest amount its price strategy and lot size allow and pays GHO to LPVaultSwap directly, then reset the allowance; any unsold shares and any input the static aToken did not take return to LPVaultSwap as residues (`REQ-ROUTE-015`). The route reverts with `MinOutNotMet` unless LPVaultSwap's GHO balance rose by at least `minOut`; no shares minted means no sale and `MinOutNotMet(0, minOut)`. A seized or frozen GSM, a full exposure cap, a paused static aToken or a GSM price below the minimum makes the leg revert. The GSM's input must have no transfer-fee switch (`REQ-ROUTE-008`). (Source: Q-062, Q-084, Q-250, Q-341)
- `REQ-ROUTE-012` A LitePSM leg of a `PegModule` route MUST compute `gemAmt` as the largest gem amount whose LitePSM DAI cost `cost(g) = g·c + ⌊g·c·tout/10¹⁸⌋` (as `DssLitePsm.buyGem` charges, `c = 10^(18 − gemDecimals)`, 10¹² for USDC) is at most the DAI available `D`, approve the LitePSM for exactly `D` and call `buyGem(LPVaultSwap, gemAmt)`; a USDS route first calls `usdsToDai`. The route computes `g₀ = ⌊D·10¹⁸/((10¹⁸ + tout)·c)⌋` and takes `g₀ + 1` when `cost(g₀ + 1) ≤ D`, else `g₀`; the fee's floor can admit `g₀ + 1` but never `g₀ + 2` (MATH-ST-120). When `tout ≥ 10³⁶` (the LitePSM's `HALTED` value is `type(uint256).max`) or `gemAmt = 0`, the route does not call the LitePSM: no output arrives, `swap` reverts `MinOutNotMet(0, minOut)` and LPVaultSwap uses the other slot. Example: with `tout = 0` and 1,000.0000005 DAI, `gemAmt = 1,000,000,000` and the 0.0000005 DAI below one USDC unit returns to LPVaultSwap; with `tout = 10¹⁵` (0.1 %) and 1,001 DAI, `g₀ = 1,000,000,000` costs exactly 1,001 DAI and `g₀ + 1` does not fit. Checked by: MATH-ST-120. (Source: Q-062)
- `REQ-ROUTE-013` During a concentrated-liquidity hop the route MUST store the hop's pool, input token, amount and direction in transient storage, and the swap callback MUST revert with `InvalidCallback` unless a hop is in progress, `msg.sender` is that pool, and the amount owed on the input side of the hop's direction is positive and at most the hop's amount; it pays exactly that amount in the hop's input token, once (the payment clears the stored pool), and the context is cleared after the hop. (Source: Q-045, Q-062, Q-148)
- `REQ-ROUTE-014` `swap` MUST send all output it obtained to LPVaultSwap and return `out`, LPVaultSwap's balance rise in `TOKEN_OUT` over the call (`REQ-ROUTE-009`); LPVaultSwap measures its own delta and never trusts the return value. (Source: Q-085, Q-124, Q-271)
- `REQ-ROUTE-015` Any input or intermediate token left by a leg MUST be transferred to LPVaultSwap in the same call; a zero leftover is skipped. Leftovers are measured as the rise of the route's balance of `TOKEN_IN` and of each intermediate over the call, so a residue can be the input a thin pool did not take, an intermediate between hops, a GSM's unsold shares or DAI below one gem unit. LPVaultSwap forwards each residue to the call's residue recipient or escrows it in the PayoutEscrow ([2.11](11-lpvaultswap.md)). Example: a cbETH → WETH → USDC route whose cbETH/WETH pool runs out of liquidity at the extreme price limit after taking 9.8 of 10 cbETH sends 0.2 cbETH back to LPVaultSwap with the USDC. (Source: Q-124, Q-097, Q-217)
- `REQ-ROUTE-016` A route MUST end every call with no change in its balance of any token and no allowance outstanding, and MUST have no owner, setter, rescue, sweep or arbitrary-call function. Legs spend only what the call produced, so no balance ends below its starting value; a token sent to a route outside a call stays there and never counts toward an output, a residue or `minOut`. For a rebasing token, whose transfers round shares, the residue the route forwards is its measured rise, and the transfer's own rounding can leave the route's balance up to one unit away from its start; that unit is never counted toward an output or `minOut`, and a rebasing input that credits more than `amountIn` reverts (`REQ-ROUTE-008`). (Source: Q-104, Q-124)

## Funding the debt asset

- `REQ-ROUTE-031` No route buys the debt asset. The liquidation caller funds the repayment with the debt asset itself, from its own balance or through a flash liquidation helper ([2.11](11-lpvaultswap.md) `REQ-SWAP-088`, `Q-333`, `Q-404`). (Source: Q-333, Q-404)
- `REQ-ROUTE-032` No route takes a maximum-input limit; every route takes only `minOut`. (Source: Q-333)
- `REQ-ROUTE-033` The callback rules of `REQ-ROUTE-013` apply to every pool hop of every route. (Source: Q-045, Q-148)
- `REQ-ROUTE-034` Output delivered above `minOut` belongs to the call's recovery `R` (or, in `deleverage`, the borrower's `assetOut`); intermediate tokens left by a leg go to LPVaultSwap (`REQ-ROUTE-015`). (Source: Q-124, Q-333)
- `REQ-ROUTE-035` LPVaultSwap `forceApprove`s a route for exactly `amountIn` and resets the allowance after the call, whether it succeeded or reverted; every swap therefore has an exact input and an oracle-derived minimum output. Checked by: TEST-232, PROP-068. (Source: Q-119, Q-124, Q-250)

## Route changes and status

- `REQ-ROUTE-017` Adding or changing a route record MUST go through `MarketRegistry.setRoute` (normal delay) and MUST mark the route in `approvedBefore` for that key; when the call replaces a different route, it MUST clear that route from `approvedBefore` for the key. A route contract is never modified in place. Why: `restoreRoute` exists to undo a `disableRoute` of the slot's own route at the short delay; a route that governance replaced was retired by a normal-delay review, often because it was found unsafe, and bringing it back is a change that needs the same review again (`ATTACK-201`). Example: `setRoute(R)`, later `setRoute(R')` because R's pool drained; `restoreRoute(R)` then reverts `NotPreviouslyApproved`, and only `setRoute(R)` at the normal delay can bring R back. (Source: Q-062, Q-151, Q-228)
- `REQ-ROUTE-018` `disableRoute` (short delay) MUST set the slot Disabled until `restoreRoute` or a new `setRoute` executes. (Source: Q-151, Q-227, Q-228)
- `REQ-ROUTE-019` `restoreRoute` (short delay, DAO-only cancel) MUST revert with `NotPreviouslyApproved` unless `approvedBefore[route]` is true for that key, and set the slot Active only after re-running `REQ-ROUTE-005`, including the GSM health check. (Source: Q-151, Q-228, Q-263)
- `REQ-ROUTE-020` Route quarantine does not exist (`Q-227`); a suspect route is disabled at the short delay while guardians stop new activity with a freeze or a pause, never liquidation. (Source: Q-227, Q-228, Q-241, Q-252, Q-399)
- `REQ-ROUTE-021` A route is usable only if `getRoute` returns `usable = true` (status Active). (Source: Q-084, Q-151, Q-227)
- `REQ-ROUTE-022` When both routes of a token into the debt asset are unusable or failing, `liquidate` reverts with `NoRouteAvailable` for that market against that debt asset; Avana has no in-kind settlement (`Q-401`). Governance restores settlement by adding or changing a route (`setRoute`, normal delay) or by `restoreRoute` of a disabled one, and guardians freeze new borrowing on the market meanwhile so exposure stops growing. When a token's issuer pauses it or blocklists LPVaultSwap, every route that takes that token as input fails; the markets holding the token wait for the issuer or are handled by the token-issuer playbook, Aave reserve freeze and `Offboarding` ([3.6](../03-operations/06-emergency-operations.md)), and the no-shared-intermediate rule of `REQ-ROUTE-003` keeps every other market's routes working. Why: settling in kind needs a caller to take the underlying tokens at a governance-set valuation, which adds a payout split, a time-limited window and an automatic trigger to every liquidation path; with two independent routes per token and market caps sized to route depth, the case is rare enough to handle by route replacement. (Source: Q-084, Q-163, Q-213, Q-227, Q-251, Q-342, Q-401, Q-404)

## Debt-asset routes

- `REQ-ROUTE-036` Enabling a debt reserve on a CDP Spoke (`enableDebtReserve`) MUST be batched with a primary and backup route, and their depth thresholds, from every token of every listed market of the Spoke into the reserve's asset (except tokens equal to it), so a debt reserve is never enabled with a missing route. (Source: Q-233, Q-339)
- `REQ-ROUTE-037` No sell-back route exists: the debt asset LPVaultSwap holds after `liquidationCall` beyond what Aave pulled, `Kf − D`, is already the settlement asset and returns to the caller inside `keeperOut` (`SPEC-LIQ-017`). (Source: Q-333, Q-404)
- `REQ-ROUTE-038` `disableRoute` and `restoreRoute` apply to every route slot alike. (Source: Q-151, Q-228)
- `REQ-ROUTE-039` A GHO debt reserve on a chain without deep GHO pools (Base, about 0.13M idle GHO in the V3 Pool) is enabled only with routes into GHO whose measured depth meets `REQ-ROUTE-006`; otherwise its `drawCap` is sized to the depth that exists, and to the Aave V3 Pool liquidity of `REQ-FLASH-008` that the flash liquidation helper borrows, unless the committed operators hold the GHO themselves. Example: a Base GHO reserve whose best GHO route absorbs $150,000 within 100 bps can be enabled only for markets whose largest capped position is at most $150,000. (Source: Q-186, Q-187, Q-339, Q-404)

## Minimum output and pool isolation

- `REQ-ROUTE-042` Every route MUST implement `swap(uint256 amountIn, uint256 minOut) returns (uint256 out)` and MUST revert with `MinOutNotMet(uint256 out, uint256 minOut)` when the output delivered, measured as LPVaultSwap's balance delta of `TOKEN_OUT` (`REQ-ROUTE-009`), is below `minOut`. Units: `amountIn` in base units of `TOKEN_IN`, `minOut` and `out` in base units of the debt asset. LPVaultSwap passes `minOut ≥ 1` on every call: `SPEC-LIQ-018` with the call's `sLeg`; a route MUST revert with `ZeroMinOut` when `minOut = 0`, checked after `NotLPVaultSwap`, `NotLocked` and the zero-amount `TransferMismatch` and before any transfer, so a swap never runs without a minimum. Why: the route is the only contract that sees the swap's output before it is final. Example: a USDT leg of 6,211.3 USDT at $0.9995 into USDC at `s = 100` with one swapped leg gets `minOut = 6,145,112,406` (6,145.112406 USDC); a primary returning 6,205 USDC passes, a sandwiched backup returning 6,100 USDC reverts. Checked by: TEST-232, PROP-068. (Source: Q-250, Q-255, Q-333)
- `REQ-ROUTE-043` A backup `DexPath` of a market MUST NOT trade through that market's own pool on any hop, and its `dependencies()` MUST list every pool it trades through; the market listing verifies on a fork that the hops match `dependencies()` and `intermediates()`. Example: for a USDC/USDe market with USDC debt, a USDe backup through a Curve USDe/USDC pool is accepted; one through the market's own USDe/USDC pool reverts `InvalidRoute`. Checked by: TEST-252. (Source: Q-273, Q-187)

## Deployment checks

- `REQ-ROUTE-045` A route's constructor MUST revert with `InvalidRouteConfig` unless: `LP_VAULT_SWAP`, `LOCK`, `AAVE_ADAPTER`, `TOKEN_IN` and `TOKEN_OUT` are non-zero, `LP_VAULT_SWAP ≠ AAVE_ADAPTER` and `TOKEN_IN ≠ TOKEN_OUT`; the Lock's `LP_VAULT_SWAP()` and `AAVE_ADAPTER()` equal the route's; the token-class mask sets only bits 1 to 3 and at least one; `TOKEN_IN`, every intermediate and `TOKEN_OUT` are distinct; every pool, wrapper and peg module is non-zero and distinct from the other contracts and from every token of the path, except an ERC-4626 wrapper that is the input token and a GSM's static aToken, which is also the intermediate. Per type: a `DexPath` has one to three hops and a `WrapperThenDex` up to three; the hops connect the path start to `TOKEN_OUT`; a Uniswap v3 or Slipstream pool's `{token0, token1}` is the hop's input and output (the swap direction is derived from it); a Curve pool's `coins(i)` and `coins(j)` are the hop's input and output, `i ≠ j`, both non-negative; an ERC-4626 step's wrapper is `TOKEN_IN` and its `asset()` the step's output; a GSM route's static aToken has `asset() == TOKEN_IN`, and the GSM's `UNDERLYING_ASSET()` is that static aToken and its `GHO_TOKEN()` is `TOKEN_OUT`; a LitePSM route's `TOKEN_OUT` has at most 18 decimals, and it names the DAI/USDS converter and DAI together or neither; the LitePSM's `gem()` is `TOKEN_OUT`, its `dai()` is the DAI the route spends (`TOKEN_IN`, or the intermediate after the converter) and its `to18ConversionFactor()` is `10^(18 − decimals(TOKEN_OUT))`; a DAI/USDS converter's `usds()` is `TOKEN_IN` and its `dai()` is the step's output. Every concentrated-liquidity hop pool MUST be the pinned Uniswap v3 factory's `getPool(token0, token1, pool.fee())` or the pinned Slipstream factory's `getPool(token0, token1, pool.tickSpacing())`, every Curve StableSwap-NG pool MUST be known to the pinned Curve StableSwap-NG factory, whose `get_coin_indices(pool, input, output)` returns the hop's `i` and `j` with no underlying coin, and every legacy Curve pool MUST be on the pinned list of `REQ-ROUTE-046`; the factories are constructor arguments that the deployment verification compares with the chain's address book, and a zero factory refuses every hop of its family. A concentrated-liquidity hop's input and a GSM route's input MUST NOT answer the fee-switch probe `basisPointsRate()` (`REQ-ROUTE-008`). A named contract that has no code, reverts or returns too little data for a read the constructor makes fails the check, and every failed check, including those, reverts `InvalidRouteConfig`. Why: a route is immutable and holds liquidation proceeds, so a mis-wired leg must fail at deployment, before any review or listing, rather than at the first liquidation; the listing fork test of `REQ-ROUTE-043` then checks the same hops on live pools. A pool with the right tokens that no pinned factory deployed could take the whole input and pay only `minOut`, so provenance is checked, not only the token pair. Example: a USDT/USDC look-alike contract reporting the right `token0` and `token1` is refused because `getPool(USDC, USDT, 100)` on the Uniswap v3 factory names another address; a LitePSM whose `gem()` is USDT in a DAI → USDC route is refused instead of failing at its first liquidation. Checked by: TEST-054, TEST-221. (Source: Q-062, Q-148, Q-273)
- `REQ-ROUTE-046` Legacy Curve hops. A `DexPath` hop, or a hop of a `WrapperThenDex` route, MAY trade through a legacy (pre-NG) Curve plain pool, hop kind `CurveLegacy`, only when the pool is on the chain's pinned list `RouteConfig.curveLegacyPools`: at most 8 addresses from the chain's address book, each admitted by review of that pool's code, because a legacy pool has no factory to pin. The constructor MUST revert with `InvalidRouteConfig` when the list has more than 8 entries, when a legacy hop's pool is not on it (checked before any read of the pool, so an unpinned pool is never called), when `i < 0`, `j < 0` or `i = j`, or unless the pool's `coins(uint256 i)` is the hop's input and `coins(uint256 j)` its output; the two kinds never stand in for each other, so a pinned legacy pool named as a StableSwap-NG hop needs the NG factory's indices, and an NG pool named as a legacy hop needs to be pinned. Only pools with the `coins(uint256)` getter are supported: the oldest pools, whose getter is `coins(int128)`, answer no `coins(uint256)` read and are refused, and a pool holding ETH lists the ETH placeholder, which no ERC-20 input or output equals. The hop calls `exchange(int128 i, int128 j, uint256 amount, 0)` after `forceApprove` of exactly `amount` and resets the allowance to 0 after it (`REQ-ROUTE-010`); the call is declared with no return value, so a pool that returns nothing (the 3pool) and one that returns the amount both succeed, and the hop's output is the route's balance rise (`REQ-ROUTE-009`, `REQ-ROUTE-015`). Every rule of the StableSwap-NG hop applies: `min_dy = 0` with the route's single minimum after the last leg, no `exchange_underlying`, the hop is not an exact-amount input (`REQ-ROUTE-008`), and a token that answers the fee-switch probe may enter it. The review that pins a pool checks that its `exchange` pulls `dx` with `transferFrom` and pays `msg.sender`; that a fee-switch coin is measured on receipt or, if the pool credits the full `dx`, that the over-credit falls on the pool's own balances and never on the route's measured output; and that the pool has no admin path that could change its coins. Deployment verification compares the list argument with the address book and checks that every `dependencies()` pool no pinned factory lists is on the chain's legacy list. Why: a legacy pool can be the deepest path between two stablecoins, and pinning by address after review gives it the provenance a factory gives an NG pool. Example: the Ethereum 3pool (`0xbEbc44782C7dB0a1A60Cb6fe97d0b483032FF1C7`; DAI 0, USDC 1, USDT 2) pinned on the list admits a USDT → USDC hop with `i = 2`, `j = 1`; 10,000 USDT in yield LPVaultSwap's measured USDC rise although `exchange` returns nothing; the same hop with `i = 0` (DAI) is refused, as is any legacy hop when the list is empty. Checked by: TEST-054, TEST-221, TEST-232, PROP-068. (Source: Q-062, Q-148, Q-273)

## Restrictions

- `REQ-ROUTE-023` Neither a liquidation caller, a flash liquidation helper nor a borrower can name a route, a pool, a leg or a minimum output; the caller's `maxShortfall` can only widen a leg's slippage within `maxShortfallBps`, paid from its own funds. A caller can still sandwich the legs of its own liquidation, moving each route's pool so the leg returns just `minOut`, and keep at most `oracleValue − minOut` of each leg, the slippage allowance; this is an accepted trade-off, the same as the fee-share bound of [2.11](11-lpvaultswap.md) `SPEC-LIQ-009`: the allowance exists so honest liquidations settle in moving markets, the borrower's recovery floor and Avana's fee are computed from oracle values, and LPVaultSwap's aggregate floor counts the residues paid to the caller at their oracle value, so a sandwich cannot take the recovery below its floor. (Source: Q-062, Q-151, Q-250, Q-251, Q-404)
- `REQ-ROUTE-024` Every route MUST complete inside the LPVaultSwap call that uses it. (Source: Q-062, Q-022, Q-213)

Preserved invariants (no Avana balances or allowances between transactions) are stated in [4.1 Global Invariants](../04-security/01-global-invariants.md).
