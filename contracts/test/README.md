# contracts/test

Foundry tests for the Avana contracts. Every test implements a `TEST-NNN` row of [5.1 Test Requirements](../../spec/05-verification/01-test-requirements.md) and checks global invariants defined only in [4.1 Global Invariants](../../spec/04-security/01-global-invariants.md). Symbolic properties (`PROP-NNN`, [5.2 Formal Properties](../../spec/05-verification/02-formal-properties.md)) marked Halmos live in `halmos/`; those marked Certora live in [`contracts/certora/`](../certora/) (`Q-041`); SMTChecker properties run through the `smt` profile. Toolchain: Foundry 1.9.0, solc 0.8.28, EVM `cancun`, dependencies installed by Soldeer into `contracts/dependencies/` and pinned in `soldeer.lock` (among them OpenZeppelin Contracts and Contracts Upgradeable 5.1.0 per `EXT-018`, and Solady 0.1.26 for CREATE3).

Tests import Avana interfaces from the contract's folder `src/<domain>/<contract>/`: the aggregate `I<Name>` when a test drives the whole contract, or only the piece it uses, such as `I<Name>Events` for `vm.expectEmit`, `I<Name>Errors` for `vm.expectRevert` selectors and `I<Name>Views` for reads. Structs and enums of one contract come from its `types/` folder (`src/liquidation/lp-vault-swap/types/LiquidationParams.sol`); types shared by several contracts come from `src/types/`.

Uniswap v3-core and v3-periphery are pinned at `=0.7.6` / `<0.8.0` and the workspace compiles only solc 0.8.28 (`auto_detect_solc = false`), so their contracts cannot be built here. The dependencies supply interfaces; local suites use the Uniswap v3 and Slipstream mocks, which implement concentrated-liquidity position math for a market's exact range in 0.8.28, and real pool bytecode comes only from the Ethereum and Base forks. Each mock has a fork counterpart (`TEST-005`), listed in `MockCounterparts.sol`:

**Transactions in a test.** Foundry 1.9 runs each top-level call of a test as its own transaction (`isolate = true` is the default), so transient storage, such as the Lock holder, is cleared between the calls of a test. A suite that must keep several calls in one transaction, as one Avana call tree does, sets `/// forge-config: default.isolate = false` on the contract, as `LockUnitTest` does; the cross-transaction behaviour is tested with isolation on.

**No dynamic test linking.** `dynamic_test_linking` is off in `foundry.toml`. With it on, `new C(...)` in a test became `deployCode`, and a `vm.expectRevert()` before a reverting `new` ended the test there: every later statement, assertions included, was skipped and the test passed. Off, every statement runs, and the same build serves Halmos and crytic-compile, which do not support `deployCode` or resolve its `foundry-pp/` helper sources.

## 2. Naming and traceability tags

**Files.** `<Subject>[.<Aspect>].<kind>.t.sol`, where `Subject` is the contract or flow under test, `Aspect` the function or concern, and `kind` one of `unit`, `fuzz`, `integration`, `invariant`, `fork`, `hostile`, `differential`, `halmos`. Examples: `AaveAdapter.Pledge.unit.t.sol`, `Backing.invariant.t.sol`, `Routes.Gsm.fork.t.sol`. The kind suffix repeats the folder so a file path read in a log or a `--match-path` glob is unambiguous. The contract inside is `<Subject><Aspect><Kind>Test`, for example `AaveAdapterPledgeUnitTest`; handlers are `<Actor>Handler`; Halmos harnesses `<Subject>HalmosTest`.

**Functions** (`TEST-008`):

| Kind | Pattern | Example |
|---|---|---|
| Unit, fork, integration, hostile | `test_TEST_NNN_<behavior>` | `test_TEST_027_failedBorrowKeepsNonce` |
| Fuzz (any folder) | `testFuzz_TEST_NNN_<behavior>` | `testFuzz_TEST_014_chargeIndependentOfSplit` |
| Invariant | `invariant_TEST_NNN_<name>` | `invariant_TEST_083_supplyEqualsCredited` |
| Halmos | `check_PROP_NNN_<behavior>` | `check_PROP_017_effectiveSlippageCoversCosts` |

`NNN` is the zero-padded ID; `<behavior>` is lowerCamelCase. A row with several assertions gets several functions sharing the prefix, so `--match-test 'TEST_057_'` runs the whole row.

Halmos functions carry the `PROP` ID, not a `TEST` ID: every Halmos row in 5.2 is a `PROP-NNN` (Tool = Halmos) and no `TEST-NNN` row is symbolic, and `trace.py` files a link under the kind of its check prefix, so a `check_PROP_…` function tagged `PROP-NNN verifies:` lands in the matrix as a formal property, next to the Certora rules with the same prefix. Where a `TEST` row re-proves the same arithmetic by fuzzing (for example `TEST-078` and `PROP-018`), the two stay separate checks.

**Tags** (`Q-173`). [`spec/05-verification/trace.py`](../../spec/05-verification/trace.py) scans `contracts/test/**/*.sol` for `<CHECK-ID> verifies: <ID>, <ID>` in any comment. Each test function is preceded by one tag line for its row (one line per `TEST` ID per file is enough; repeats are harmless):

```solidity
// TEST-010 verifies: Q-066, Q-076, Q-094, Q-223, Q-224, Q-225, Q-240, INV-001, INV-006, INV-009
// Sources: 5.1 TEST-010, FLOW-001
function test_TEST_010_pledgeHappyPath() public { ... }
```

Rules the parser imposes:

- The list after `verifies:` must hold only IDs defined in `spec/01`–`spec/04`: `REQ-<AREA>-NNN`, `SPEC-<AREA>-NNN`, `INV-NNN`, `ATTACK-NNN`, flow steps `DEP|BOR|REP|WDR|LIQ|EMG|FEE|MKT|DEF-NNN` (with optional `F-`/`POST-`), and `Q-NNN` from the decision log. An undefined ID fails `trace.py`.
- The list is comma-separated on one line and stops at the first token that is not an ID, silently dropping everything after it. `default …` sources, `FLOW-00N`, `FINDING-…` and spec-stage check IDs (`MATH-`, `QNT-`, `HYP-`, `SIM-`, `SYM-`) never go after `verifies:`; they go on the `// Sources:` line. Some default IDs (`LIQ-005`, `LIQ-030`) match the flow-step pattern and would link to an unrelated liquidation step.
- `REQ-…`, `SPEC-…` and flow-step IDs of the contract and operation pages are added to a file's tags as those pages are linked (5.1 "Covers"). `trace.py --strict` fails when `contracts/src` exists and any `REQ-`, `SPEC-` or `INV-` has no `TEST-` or `PROP-` link.
- Off-chain tests (sections H and I) name their cases `TEST_NNN_<behavior>` and carry the same tag text, but `trace.py` does not scan outside `contracts/`; their coverage is checked by the owning service's CI.

## 3. Shared fixtures

### 3.1 Local Aave V4 (`AaveV4Fixture`, `TEST-002`)

Avana deploys its own Aave V4 from `dependencies/aave-v4-a3ef63e/` (commit `a3ef63ea6415d25237a9775bf66e76e9993561c2`) with Aave's own deployment procedures, so tests run the code path an operator runs:

1. `vm.etch` the CREATE2 factory `0x914d7Fec6aaC8cd542e72Bca78B30650d45643d7` (Safe Singleton Factory runtime) when it has no code. On the mainnet fork and on Sepolia it already exists; on Anvil the deploy script sets it with `anvil_setCode`.
2. Build Aave once with `FOUNDRY_PROFILE=aave forge build`. The `aave` profile compiles the pinned source into `out-aave/` with Aave's own settings: 44,444,444 optimizer runs without via-IR for every source, `HubInstance` via-IR at 22,300 runs and `SpokeInstance` via-IR at 750 runs, `bytecode_hash = "none"`. Fixtures never import Aave sources, so these settings stay separate from Avana's build; they load artifacts with `deployCode("out-aave/<File>.sol/<Contract>.json", args)` and `vm.getCode` (`fs_permissions` grants read on `out-aave/`).
3. Deploy in the order of Aave's deployment orchestration, using the batch contracts from `out-aave/` (each batch deploys its contracts in its constructor): `AaveV4AuthorityBatch` (the Aave-side `AccessManagerEnumerable`, admin role held by the `aaveDao` actor) → `AaveV4ConfiguratorBatch` (`HubConfigurator`, `SpokeConfigurator`) → `AaveV4TreasurySpokeBatch` (the vault-token fee receiver, `addCap = drawCap = 0`) → `AaveV4HubInstanceBatch` (the Avana Stable LP Hub and its interest-rate strategy) → `AaveV4SpokeInstanceBatch` for the Lend Spoke and each Coverage Spoke (one per covered asset: GHO, and USDC in the multi-asset fixture), and one standard, unmodified CDP Spoke per (Hub, AMM protocol, risk tier), starting with the Uniswap v3 Stable CDP Spoke; each Spoke has its own `AaveOracle` (8 decimals) linked to it. Per-instance salts derive from a fixed root salt, so addresses repeat across runs. Aave's test orchestration under `tests/` is not used.
4. Roles: the fixture holds `ACCESS_MANAGER_ADMIN_ROLE` only while it runs Aave's role procedures (unchanged, through `aave-deploy/AvanaAaveV4Roles.sol`, which the `aave` profile compiles next to the Aave sources and the fixture calls by `delegatecall`, so the AccessManager sees the fixture as the deployer) for the Hub, Spokes and configurators, grants configurator roles to `aaveDao`, `HUB_DEFICIT_ELIMINATOR_ROLE` to each Coverage Spoke and each Coverage Spoke's `COVERAGE_ROLE` (for `coverDeficit`) to the `coverageCaller` actor, then renounces. These are Aave-side roles in Aave's own access manager; Avana's roles live in the AvanaTimelock and the Avana contracts (3.2).
5. Debt reserves and credit lines, with the values of the deployment AIP in [`governance/README.md`](../../governance/README.md): GHO asset with Aave's fixed GHO price source, Lend Spoke `addCap = creditLineGho` (2,000,000 GHO) supplied by the `daoTreasury` actor, CDP Spoke `drawCap` within the line, the GHO Coverage Spoke funded to `firstLossReserveMinimum` (100,000 GHO) before the `drawCap` rises above 0; in the multi-asset fixture also a 6-decimal USDC asset and an 18-decimal WETH asset, each priced by its DebtOracle through the AaveOracle, supplied through the Lend Spoke, with its own Coverage Spoke funded first; on every vault-token reserve the three required settings (`receiveSharesEnabled = false`, `liquidationFee = 0`, no reinvestment controller, `INV-093`); one `LiquidationConfig` with `targetHealthFactor = 1.10`, the bonus curve, `riskPremiumThreshold` and `spokeUserReservesLimit` (counting collateral and debt reserves).
6. `LiquidationLogic`: `SpokeInstance` calls it as an external library. The library step CREATE2-deploys `LiquidationLogic` (from `out-aave/`) with salt 0 through the factory; its address depends only on its init code, so it is the same on Anvil, Sepolia and every fork. The step writes `FOUNDRY_LIBRARIES=dependencies/aave-v4-a3ef63e/src/spoke/libraries/LiquidationLogic.sol:LiquidationLogic:<address>` to `deployments-local/libraries.env`, and `FOUNDRY_PROFILE=aave forge build --force` is rerun with it so the `SpokeInstance` artifact is linked. Fixtures deploy the library at that address (CREATE2 through the etched factory) before deploying Spokes. The manifest records the address. `TEST-002` asserts that the Spoke calls a contract whose runtime code is `LiquidationLogic` at the CREATE2 address.
7. Bytecode identity: `TEST-002` and `TEST-134` compare the runtime hashes of `HubInstance`, `SpokeInstance`, `AaveOracle`, the configurators, `TreasurySpoke`, `AccessManagerEnumerable` and `LiquidationLogic` built by the `aave` profile with the Aave build of the same commit (and, on the fork, with the DAO deployment when one exists).

### 3.2 Avana on top (`AvanaFixture`, `MarketFixture`)

Avana deploys in the deploy-plan order. Every immutable is wired by address, so contracts that reference each other use predicted addresses and the fixture asserts each predicted address equals the deployed one:

1. AvanaTimelock (immutable, `SHORT_DELAY` 43,200 s, `MAX_DELAY` and `normalDelay()` 432,000 s, `GRACE_PERIOD` 1,209,600 s, public execution on), holding its own `DEFAULT_ADMIN_ROLE`; `PROPOSER_ROLE` to the `governanceMultisig` actor (4-of-7); `CANCELLER_ROLE` to `governanceMultisig`, `emergencyGuardian` (3-of-5), `aaveGuardian` and `aaveGovernanceExecutor`; `DAO_CANCELLER_ROLE` to `aaveGovernanceExecutor`. The fixture's temporary grants are renounced before any market activates.
2. Predict the addresses of the AaveAdapter, MarketRegistry, ParameterStore, RiskModule and LPVaultSwap proxies and of the immutable LPVault of each AMM protocol, Collateralization, ProxyManager and Lock from the deployer and fixed salts. The Lock fixes its two members (AaveAdapter, LPVaultSwap); each vault token fixes its integration ID and LPVault, market key, Hub, CDP Spoke, market ID, LPOracle, AaveAdapter, LPVaultSwap, Collateralization and decimals.
3. Upgradeable contracts as an implementation (constructor `_disableInitializers`) behind an ERC-1967 UUPS proxy whose `_authorizeUpgrade` requires `APPLICATION_ADMIN`: MarketRegistry, ParameterStore (launch parameters, `minPledgeUsd` $10 = `10e8` per market), RiskModule, AaveAdapter and LPVaultSwap with its initial keepers (at least `keeperFloor`). Each `initialize(timelock, …)` grants `DEFAULT_ADMIN_ROLE` and `APPLICATION_ADMIN` to the AvanaTimelock; the MarketRegistry grants `APPLICATION_PAUSE_GUARDIAN` to `emergencyGuardian` and `aaveGuardian` and `APPLICATION_FREEZE_GUARDIAN` to the same two. No ProxyAdmin exists.
4. Lock, the LPVault of each AMM protocol, Collateralization and the ProxyManager at their predicted addresses (immutable; each LPVault's `TIMELOCK` is the AvanaTimelock).
5. VaultTokenFactory (immutable, `TIMELOCK` caller); `AaveV3FlashSource` over the Aave V3 Pool, set on LPVaultSwap; PayoutEscrow (the payout escrow); the Lens.
6. Swap routes per (market, pool token, debt asset), a primary and a backup, each from the token directly into the debt asset; there are no buy or sell-back routes (`Q-379`).
7. CDP Spoke and debt reserves as one normal-delay timelock batch: the CDP Spoke's registration in the MarketRegistry with its home Hub, AMM integration and risk tier, and `enableDebtReserve` for GHO (and USDC and WETH in the multi-asset fixture); `vm.warp` past `normalDelay()` and execute.
8. Markets (`MarketFixture.addMarket`), steps `MKT-018` to `MKT-026`: deploy and initialize the market's LPOracle proxy and seed its feed rounds; schedule as `governanceMultisig` one normal-delay batch with `deployVaultToken` (CREATE3, salt `keccak256(abi.encode(spoke, marketKey))`), `listToken`, `listCollateralMarket`, `setInitialMarketParams`, `setInitialMarketCaps`, `setInitialTokenCap` and `setRoute`; `vm.warp` past the normal delay; execute (any address may, public execution); refresh feed rounds made stale by the warp and `poke` until Live; `aaveDao` executes the listing payload on the configurators (`addAssetWithDecimals`, fee receiver caps 0, `addSpoke` with the `SPEC-HUB-002` `addCap` and `drawCap = 0`, `addReserve` with the LPOracle source, CF, `maxLiquidationBonus`, `liquidationFee = 0`, not borrowable, `collateralRisk`; on the first listing the `FLASH_BORROWER` grant on the Aave V3 Pool for the flash source); schedule `activateMarket` at the short delay, warp 43,200 s and execute.

PositionProxies are not deployed by the fixture: the AaveAdapter has the ProxyManager create each one (a logic-free immutable contract, CREATE2 salt `keccak256(abi.encode(wallet, spoke, marketId))`) on the wallet's first pledge to that market and registers it in the market's vault token; the fixture labels `predictProxy(actor, spoke, marketId)` in advance. The first fixture is one Uniswap v3 stable market at its exact range, the Uniswap v3 Stable CDP Spoke on the Stable LP Hub with the GHO debt reserve, the Lend Spoke and the GHO Coverage Spoke (`TEST-009`); later fixtures call `addMarket`, add the Aerodrome Slipstream Stable CDP Spoke on the Base fork, a second Hub, or the USDC and WETH debt reserves on top of it instead of replacing it.

### 3.3 Mainnet fork (`ForkFixture`, `TEST-003`)

`setUp()` selects the fork first, `vm.createSelectFork("mainnet", ForkConstants.mainnetForkBlock())` (the Base fixture uses `baseForkBlock()`), then runs 3.1 and 3.2 on it; deploying before the fork is selected loses the contracts. `TEST-003` asserts the block equals `ForkConstants.MAINNET_FORK_BLOCK` (and `BASE_FORK_BLOCK` on Base), so a pin changes only by a reviewed commit of that file, and CI keys its RPC cache (`~/.foundry/cache/rpc`) on the file's hash. The environment variables of the same names override a pin for local experiments only; `TEST-003` fails while an override is in effect, and a suite skips while its chain's pin is 0 and no override is set. Taken from the fork, with addresses and code hashes in `ForkConstants.sol`: UniswapV3Factory `0x1F98431c8aD98523631AE4a59f267346ea31F984`, NonfungiblePositionManager `0xC36442b4a4522E871399CD717aBDD847Ab11FE88` and the launch pools; the Chainlink primary and alternate aggregators per launch token; GHO `0x40D16FC0246aD3160Ccc09B8D0D3A2cD28aE6C2f`; the Aave V3 Pool behind `AaveV3FlashSource`; GSM USDC `0xFeeb6FE430B7523fEF2a38327241eE7153779535` and GSM USDT `0x535b2f7C20B9C83d70e519cf9991578eF9816B7B` with waEthUSDC and waEthUSDT; the Sky LitePSM and DAI/USDS converter; Aave V3 ACLManager `0xc2aaCf6553D20d1e9d78E365AAba8032af9c85b0`, whose admin is pranked to grant the flash source `FLASH_BORROWER`. The Base fork takes the Slipstream factory, position manager and pools, the Base Aave V3 Pool and the sequencer-uptime feed the same way. Tokens come from `deal`; LP NFTs are minted through the real position manager. Prices move with `PriceStateDriver` (`vm.mockCall` on collateral aggregators while every debt price source stays live; debt-asset feeds such as Chainlink USDC/USD and ETH/USD move separately) and pools move by real swaps from a test caller across `twapWindow` with `vm.warp`.

### 3.4 Manifests

- **Write.** `Deployments.sol` serialises every local or Anvil deployment to `contracts/deployments-local/<chainId>-<label>.json` (the only read-write path in `fs_permissions`). ## 6. Hostile-component tests

A hostile test installs a hostile implementation of an upgradeable Avana contract and measures what it can reach. For the RiskModule, MarketRegistry, ParameterStore, LPOracle and LPVaultSwap the test shows that every "any implementation" invariant still holds, because the immutable contracts (vault tokens, Collateralization, each LPVault, ProxyManager, PositionProxies, Lock, PayoutEscrow) and the reviewed AaveAdapter enforce it. The AaveAdapter is trusted for custody of proxy positions, so its tests assert the blast radius instead: the measured loss stays within the stated bound, the NFT never leaves to anyone but its depositor, and inside the delay every canceller can cancel and every borrower can repay and withdraw (`TEST-195`). Section F of 5.1 (`TEST-130`–`TEST-133`, `TEST-154`, `TEST-156`, `TEST-210`) and the hostile invariant suite (`TEST-107`) share the implementations in `hostile/impl/`.

**Upgradeable Avana contracts** are replaced only through the real AvanaTimelock, with the real normal delay:

```solidity
bytes memory upgrade = abi.encodeCall(UUPSUpgradeable.upgradeToAndCall, (address(new HostileAaveAdapter()), ""));
vm.prank(governanceMultisig);
timelock.schedule(address(adapter), 0, upgrade, bytes32(0), SALT, NORMAL_DELAY); // 5 days
vm.expectRevert(); // TimelockUnexpectedOperationState: not ready
timelock.execute(address(adapter), 0, upgrade, bytes32(0), SALT);
vm.warp(block.timestamp + NORMAL_DELAY);
timelock.execute(address(adapter), 0, upgrade, bytes32(0), SALT); // public execution: any caller
```

The ProxyManager and every PositionProxy are immutable, so no proxy code can be replaced; `TEST-210` drives every proxy through a hostile AaveAdapter installed as above. Scheduling an upgrade at the 12-hour short delay reverts `DelayBelowRequired`. After the warp the fixture refreshes feed rounds so price states are what the test intends, then runs every `AttackerHandler` action in a fixed order and as a fuzzed sequence.

**External venues and tokens.** Each AMM protocol's position manager and factory are immutables of its LPVault and are never replaced; a hostile pool is a real factory pool (on the fork) or a `MockUniswapV3Pool` or `MockClPool` (locally) with a hook-calling token as one leg, which re-enters during `decreaseLiquidity`, `collect` and route transfers. GSM and LitePSM failures (frozen, full, short-paying, reverting) come from `vm.etch` of a hostile implementation at the venue address on the fork, and from `MockGsm`/`MockLitePsm` modes locally. A hostile swap route is a new route contract registered through the timelock at the normal delay. Flash premiums above `maxFlashFeeBps` come from `vm.mockCall` on the Aave V3 Pool's `FLASHLOAN_PREMIUM_TOTAL`; a foreign caller or `initiator` comes from a hostile lender calling the flash source's callback. Feed faults come from `GasBurningAggregator` and `MockAggregator` modes. Aave V4 code is never etched; Aave-side hostility is configuration changed by `aaveDao` through the configurators (`TEST-114`).
